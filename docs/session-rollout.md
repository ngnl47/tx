# Login、Agent、MsgQ 持续流量发布验收指南

本页维护现行 schema v2 的统计契约、恢复边界和执行方式。实施进度见[总计划](IMPLEMENTATION_PLAN.md)，每次实测结果保存在日期化报告中；指南不替代运行证据。

验收复用两组应用的正式包、客户端流量及进程编排，每个测量窗口固定 180 秒。保留全部计划请求，分别报告全窗口与正常运行阶段完成率，发布中断及在途未知结果单列。生产 Login、Agent、MsgQ 不增加自动重试、上行重放或邮箱迁移能力。

契约依据：[会话设计](design.md#客户端协议与-agent)、[工程约定](engineering-conventions.md)。

## 1. 工具职责

以下路径相对于所列仓库根目录。两组示例分别维护，复用各自既有入口，不互相 import。

```text
txgame/、txgameslg/
├── cmd/cluster-e2e.sh                 # 正式包与集群验收入口
└── server/cmd/
    ├── cluster-e2e/                  # 场景选择与参数
    └── internal/
        ├── clustere2e/
        │   ├── session_lifecycle*.go # 正式包、身份取证与阶段边界
        │   └── session_rollout*.go   # 持续流量编排、统计和持久化核验
        └── ops/                     # 打包与进程生命周期

txclient/、txclientslg/
└── src/cli/
    ├── session-rollout.ts            # 准备、阶段控制与收尾
    ├── session-rollout-endpoint.ts   # 正式协议及显式恢复
    └── session-rollout-meter.ts      # 固定分母、期限及结果统计
```

Go 工具负责正式包、进程和存储证据；TypeScript 工具负责固定时间轴发流、响应关联及显式恢复。txgame 使用带 ProbeID 的 System_Ping/Pong；txgameslg 使用返回实际名称的 Role_Rename。两者都走客户端→Agent→业务 Actor→MsgQ→Agent→客户端，不横向比较两种业务的容量，不增加业务协议或旁路服务。

## 2. 范围与最小拓扑

- 复用普通正式包，在脱离源码目录的位置运行；记录各仓提交、工作区差异、二进制摘要及配置快照。
- 每组保留 2 Login、2 Agent、2 MsgQ；Game/SLGGame/World 按现有会话验收拓扑启动，全程不发布业务进程。
- 每组分别执行 Login、Agent、MsgQ 三个独立的 180 秒窗口，每个窗口只替换该类的一个实例，另一个保持在线。六个窗口共 18 分钟净测量，准备、恢复与清理另计；不是六次重新构建。
- 默认每窗口 40 个连接、每连接 5 次/秒、TCP/WS 各半、每连接最多 1 个在途请求。该值是低负载验收参数，不是容量结论。准备期若本机不能稳定承载，停止并报告，不事后改分母或删失败轮次。
- 正式计时前记录每个客户端的 Agent 与 MsgQ owner。目标和对照组提前固定，覆盖 TCP/WS 及受影响/不受影响的 owner；不要求通过私有接口强行指定 MsgQ。现有分配无法形成所需分组时，准备失败，不空跑场景。
- SLG 全程核对 Role/World 的 owner、generation 和 WorldID 不变；沿用有限 World 路径检查，不声称本轮验证 World 持续流量、在线迁移或停服合服。
- 不混入故障杀进程、独占借号、配置回滚、额外下行扇出或云端压测；这些已有证据独立保留。

## 3. 正常运行、发布中断与完整分母

### 原始统计不变

对窗口内每个预定请求计数；断连、恢复、排水或发生器赶不上均不暂停时间轴。错过的请求不补发、不顺延，已尝试请求不重投。

```text
P = 所有连接在 180 秒内的计划请求数
A = 已尝试发送的计划请求数
N = P - A                       # 未发送：离线、在途额度或调度错过
C = 各自期限内收到匹配成功响应的唯一请求数
F = A - C                       # 已尝试但未取得成功结果
U = outcomeUnknown = F          # 当前探针的发送错误、断连和超时，不证明业务未执行
P = N + C + F
全窗口完成率 = C / P
```

P=40×5×180=36,000 时，全窗口达到 99.99% 最多允许 3 个未完成请求。此结果保留在 `completion` 和 `traffic.total/groups`，不会因为发布被改写。`failed` 保留原有计数名，当前探针未提供业务明确拒绝分类，不能把 F 解读为服务端确定未执行；`outcomeUnknown` 使这一边界显式可见。

关联继续使用 ProbeID 或 Role_Rename 唯一名称，不使用 UpSeq/DownSeq。180 秒后不产生新计划，只等待在途样本各自期限；期限内尾部响应计入原计划，超时后的迟到响应不改判成功。控制探针、离线通知和最终标记不进入 P/C。

### 发布边界必须先登记

```text
第 30 秒：Go 写 publication-begin.command.json
  → 客户端用单调时钟登记起点并回复 publication-begin.json
  → Go 收到确认后才停止旧进程
  → Agent 原地址重启，逐连接 Restore + 离线通知/业务探针成功
  → 该连接恢复可用，后续计划重新归入正常运行阶段
```

Agent、MsgQ 的受影响连接按以下规则分区，对照组始终全部属于正常运行：

- 发布阶段包含起点（含）至该连接恢复可用（不含）之间的计划，以及起点时已经在途、跨边界的请求；发送时已进入发布阶段的样本也归发布。
- 其余计划属于正常运行，包括正常期间未发送、超时或断连的损失。不能事后只剔除失败样本或整个发布秒。
- 每个计划恰归一个阶段，`normal + publication = 原始 total`，总计与 affected/control 分组分别对账。
- Login 发布不切断既有业务连接，所有计划仍属于正常运行，没有发布阶段排除样本。
- 受影响连接未恢复时，其区间保留至测量结束，恢复时间和中断时长为 null，恢复契约失败；不得补写成功时间。

`traffic.publication.sessions` 记录每个受影响连接的 `disconnectedMs`、`resumedMs` 和 `interruptionMs`：客户端首次观察到断开/连接错误，至恢复握手、所需离线通知及业务探针完成、重新允许发流的时间差。没有观察到断开不伪造 0；Go 验收要求 Agent/MsgQ 受影响连接具备完整证据。`startedMs/finishedMs` 是整体发布编排边界，不等于某条连接的不可用时长；其中可能包含通知探针、工具轮询与新登录检查，不能直接当作纯进程或 Pod 启动耗时。

### 独立判定

schema v2 的 `normalCompletion` 要求正常运行总计及两个分组都达到 99.99%，仍使用整数阈值 `planned-completed <= floor(planned/10000)`；零计划为 not-measured，不能冒充通过。`completion` 保留原始全窗口判定。

客户端总体 `status` 与退出码依据正常运行完成率、恢复及清理；Go 另外核验 owner、CID、退出与持久化。全窗口未达 99.99% 可以与这些项目通过同时成立，报告必须同时展示，不能称为“发布全过程 99.99% 达标”。发布中断时长暂无新增性能阈值，仍受既有恢复/进程控制期限约束；后续如有可用性 SLA 再单独定义。

旧 schema v1 的真实报告缺少停服前标记，不倒推新阶段、不改判历史失败。新统计不增加业务重投、自动恢复或补偿，不改变普通 cluster-perf 的验收口径。

## 4. 三类恢复边界

| 发布对象 | 受影响会话应发生什么 | 恢复方式与判定 | 不保证的内容 |
| --- | --- | --- | --- |
| Login | 已建会话不依赖 Login 在线，业务连接保持 | 一台停止期间，经另一台完成有限新登录；替换实例就绪后也能签票接入。原会话 SID/CID/MsgQ owner 不变 | 不假设客户端自动故障转移 Login HTTP 地址；不对停止端点做无界重试 |
| Agent | 原物理连接关闭，MsgQ 尚存的逻辑邮箱保留 | 同地址替换 Agent 就绪后，以验签有效且仍被 MsgQ 接纳的原票据显式 reconnect；SID 不变、CID 更新、Agent InstanceID 更新、MsgQ owner 不变；离线有限通知可续接，发送新业务请求成功 | 不把 InstanceID 变化直接解释为必须重登；恢复不依赖首次接入票据到期，但必须原会话有效；不承诺任意不同地址均可达。不重放旧上行 |
| MsgQ | 其 owner 释放，旧邮箱不可继续恢复；其他 MsgQ 的会话保持 | 对旧 SID 做一次显式恢复检查，必须得到应用拒绝；随后正常 Login，以同角色新 SID 接入存活 MsgQ，业务初始化完成后继续未来计划请求；替换 MsgQ 就绪不搬回现有会话 | 不迁移旧邮箱或未确认下行，不把拒绝恢复解释为可重投旧业务，不因普通流重连成功推断邮箱存在 |

Agent 场景增加少量已知内容的离线通知，验证旧邮箱续接，与持续流量样本分开。首次接入须在票据有效期内，恢复须在原邮箱有效边界内；本轮不增加票据过期或邮箱溢出场景。

MsgQ 场景的旧恢复检查沿用现有有限工具的显式 close/reconnect，不预设停掉 MsgQ 必然主动关闭客户端 socket。流量期间观察到的断连、错误或响应超时按实际记录；确认 owner 正常释放后，工具驱动这次恢复检查及重新 Login。此为验收编排，不等于生产客户端已经具有同样的自动恢复策略。

Ready 只证明接入完成。恢复完成点是正式业务响应到达；新 Session 还必须执行应用既有的 Ready 后初始化。恢复前后不得同时用两条连接驱动同一测试角色。未知执行结果只记失败，不重投；SLG 的 Rename 可能已生效，即使响应丢失也不得称为“未执行”。

## 5. 每个窗口的顺序与证据

```text
工具准备正式包、依赖和会话，采集实例/owner/票据与连接身份
  → 客户端报告准备完成，固定目标和对照组
  → 客户端启动 180 秒固定计划，报告实际起点
  → 第 30 秒：先确认客户端发布起点，再对目标实例 DrainAndStop
      → 等待真实退出和目录变化
      → 按该类场景执行恢复检查、启动替换实例
      → 等待 Ready 及首条成功业务响应，记录恢复完成点
  → 第 180 秒：停止新计划，等待已有样本各自到期
  → 汇总全量/分组/分阶段数据及契约断言
  → 正常关闭剩余进程，核对存储、退出记录与专用资源残留
```

MsgQ 先检查旧恢复拒绝、在存活 MsgQ 建新 Session，再启动替换 MsgQ；Agent 必须等旧实例退出后在原地址启动替换实例，再恢复原 Session；不使用新增第 N+1 个实例承接本轮旧连接。三类顺序不合并成一套错误的通用恢复流程。

计时使用客户端单调时钟；控制文件带窗口/阶段标识并只触发一次。原始每秒样本按计划时刻归桶，正常/发布阶段用精确时间分区，两者不是按秒近似切分。报告同时保留双方墙钟，不能靠不同进程各自 sleep 推断准确切点。各秒损失归到原计划时刻，阶段边界不重复计数。

沿用现有停止 35 秒、启动就绪 25 秒、客户端阶段 45 秒的上界；它们是失败终止界限，不是可接受中断时间或延迟目标。阶段失败保留当前窗口及所有计划损失，停止后续发布并清理；不得无限等待或自动开始一轮“替代成功”窗口。按需等待清理不会延长流量分母。

每窗至少输出：参数与构建身份、P/A/N/C/F、尾部完成/迟到/重复数、按秒计数、每组 owner、成功请求延迟、调度迟到、阶段开始结束、断连到 Ready/首条业务响应时间、SID/CID 变化、实例退出码及清理结果。清理失败独立失败，不能因吞吐达标忽略。服务端/客户端逐消息日志维持现行级别，不额外开启高频画像。

SLG Rename 沿用正式持久化链路。停止发流并结算样本期限后，每个角色执行一次独立最终标记改名并等待匹配响应，全部窗口结束后，保持 Fusion 消费在线，在总计 45 秒内只读等待 Mongo 最终标记，再正常排水并独立读回该确定值；不用“最后一个成功流量响应”推断最终状态。当前没有角色名称只读协议，因此此处是最终业务确认，不新增生产协议，也不证明所有超时请求都执行过。World 保持原实例，复用两条行军完成路径及既有移动/最终保存检查，不扩展 World 玩法。

## 6. 执行与产物

分别在 txgame、txgameslg 仓库根目录执行：

```sh
./cmd/cluster-e2e.sh --session-rollout
```

默认总期限 15 分钟，不能与其他故障、合服模式混用。依赖准备与选项以各工程 README 为准：[txgame](https://github.com/ngnl47/txgame/blob/main/README.md)、[txgameslg](https://github.com/ngnl47/txgameslg/blob/main/README.md)。

输出包含 `session-rollout-summary.json`、`session-rollout-windows.json`、各窗口的 `server-evidence.json`、客户端 `result.json` 和 `processes/*.rollout-exit.json`。SLG 另外保留 `session-rollout-persistence.json`，核对 120 个角色的最终标记、RoleID、OriginServerID，以及 World 最终数据和非零文档版本。退出证据来自真实进程 Wait，期限耗尽不能记为正常退出。

完成率不足仍保留窗口结果；恢复契约失败停止后续发布，外层期限耗尽明确失败，不补跑“替代成功”窗口。失败保留专用数据，成功才按 ownership 清理。专用范围沿用 txgame Redis DB12、txgameslg DB13，以及各自 ownership 标记的 Mongo/etcd 前缀与精确 SessionID 发号键；没有标记的数据仍须按仓库规则确认，不能扩大清理范围。
