# Login、Agent、MsgQ 持续流量滚动发布验收计划

状态：2026-11-04 六个本地正式包窗口已执行并结算，整体验收未通过；结果和后续边界见[本轮报告](session-rollout-acceptance-20261104.md)。

目标：复用两组应用的正式包、客户端流量及进程编排，验证接入服务逐实例替换时的请求损失、恢复边界和正常退出。每个测量窗口固定 180 秒，99.99% 按全部计划请求计算。

架构：Go 工具负责正式包、进程和存储证据；TypeScript 工具负责固定时间轴发流、响应关联及显式会话恢复。生产 Login/Agent/MsgQ 不增加自动重试、上行重放或邮箱迁移能力。

技术栈：现有 Go 运维入口、TypeScript 客户端、TCP/WebSocket、etcd、Redis、MongoDB；不增加旁路服务。

契约依据：[独占接入](exclusive-session-plan.md)、[重连修复与补验](reconnect-window-acceptance-20261104.md)、[工程约定](engineering-conventions.md)。本轮按本计划运行本地正式包验收，不跑云测试、不提交；保留所有失败窗口及原始统计。

## 2. 范围与最小拓扑

- 复用普通正式包，在脱离源码目录的位置运行；记录各仓提交、工作区差异、二进制摘要及配置快照。
- 每组保留 2 Login、2 Agent、2 MsgQ；Game/SLGGame/World 按现有会话验收拓扑启动，全程不发布业务进程。
- 每组分别执行 Login、Agent、MsgQ 三个独立的 180 秒窗口，每个窗口只替换该类的一个实例，另一个保持在线。六个窗口共 18 分钟净测量，准备、恢复与清理另计；不是六次重新构建。
- 初始建议每窗口 40 个连接、每连接 5 次/秒、TCP/WS 各半、每连接最多 1 个在途请求。该值是低负载验收参数，不是容量结论。准备期若本机不能稳定承载，停止并报告，不事后改分母或删失败轮次。
- 正式计时前记录每个客户端的 Agent 与 MsgQ owner。目标和对照组提前固定，覆盖 TCP/WS 及受影响/不受影响的 owner；不要求通过私有接口强行指定 MsgQ。现有分配无法形成所需分组时，准备失败，不空跑场景。
- SLG 全程核对 Role/World 的 owner、generation 和 WorldID 不变；沿用有限 World 路径检查，不声称本轮验证 World 持续流量、在线迁移或停服合服。
- 不混入故障杀进程、独占借号、配置回滚、额外下行扇出或云端压测；这些已有证据独立保留。

## 3. 99.99% 统计口径

### 固定分母与唯一完成

对窗口内预定的每一个请求时刻计数；断连、恢复、排水或发生器赶不上均不暂停时间轴。错过的请求不补发，也不顺延。

```text
P = 所有连接在 180 秒内的计划请求数
A = 已实际尝试发送的计划请求数
N = P - A                       # 未发送，包括断连、在途额度及调度迟到
C = 在各自期限内收到匹配成功响应的唯一请求数
F = A - C                       # 发送错误、业务拒绝、超时等，收尾后无未决项

P = N + C + F
完成率 = C / P
通过条件：P - C <= floor(P / 10000)
```

建议参数对应 P=40×5×180=36,000，最多允许 3 个未完成请求；4 个即不达标。不能四舍五入百分比后判通过。上行写入流、socket send 成功或服务端执行计数都不是端到端完成。

关联使用现有 ProbeID 或 Role_Rename 唯一名称，窗口及重新登录之间不复用样本标识；不使用 UpSeq、DownSeq 或收到顺序推断请求响应关系。迟到、重复和旧会话响应单列，不能完成另一条请求。诊断字段不要求服务端排序或重投。

建议请求期限 2 秒，从实际尝试时刻起算。180 秒后停止产生新计划，最多再等待剩余请求自己的期限；期限内跨窗口结束的完成计入原请求，同时单列尾部完成。已经超时或明确失败的样本即使随后收到响应也不改判成功。恢复握手、离线通知和新登录检查单独统计，不加入业务流量的 P/C。

### 发布损失不能被隐藏

Agent 正常停止会断开连接，MsgQ 正常停止会使其旧邮箱失去恢复资格。若 20 个受影响连接断开 1 秒，每连接 5 次/秒，仅这段就可能损失 100 个计划请求，明显超过 36,000 请求的容错额度。当前契约不保证此类全窗口达到 99.99%。本轮测量是量化这一差距，不预设通过，更不以补偿重发换取通过。

报告必须分别给出：

1. **全窗口完成率与 99.99% 判定**：保留全部损失，作为主指标。
2. **预先固定的对照组完成率**：同样以该组完整计划数为分母，目标 99.99%，用于识别发布影响是否扩散；不能代替主指标。
3. **恢复契约判定**：身份、邮箱、票据、下行续接、正常退出是否满足下一节；与完成率独立。

若恢复正确但全窗口不达标，应写“恢复契约通过，全窗口完成率未达标”，整体验收不得笼统写通过。禁止只统计在线时段、删掉发布秒、将新 Session 当新样本清零，或通过加长稳定流量稀释损失。若后续要求发布全过程也达到 99.99%，需另行决定可用性目标与实现范围，不在工具中偷偷补保证。

## 4. 三类恢复边界

| 发布对象 | 受影响会话应发生什么 | 恢复方式与判定 | 不保证的内容 |
| --- | --- | --- | --- |
| Login | 已建会话不依赖 Login 在线，业务连接保持 | 一台停止期间，经另一台完成有限新登录；替换实例就绪后也能签票接入。原会话 SID/CID/MsgQ owner 不变 | 不假设客户端自动故障转移 Login HTTP 地址；不对停止端点做无界重试 |
| Agent | 原物理连接关闭，MsgQ 尚存的逻辑邮箱保留 | 同地址替换 Agent 就绪后，以仍有效旧票据显式 reconnect；SID 不变、CID 更新、Agent InstanceID 更新、MsgQ owner 不变；离线有限通知可续接，发送新业务请求成功 | 不把 InstanceID 变化直接解释为必须重登；也不承诺任意不同地址/过期票据都可恢复。不重放旧上行 |
| MsgQ | 其 owner 释放，旧邮箱不可继续恢复；其他 MsgQ 的会话保持 | 对旧 SID 做一次显式恢复检查，必须得到应用拒绝；随后正常 Login，以同角色新 SID 接入存活 MsgQ，业务初始化完成后继续未来计划请求；替换 MsgQ 就绪不搬回现有会话 | 不迁移旧邮箱或未确认下行，不把拒绝恢复解释为可重投旧业务，不因普通流重连成功推断邮箱存在 |

Agent 场景增加少量已知内容的离线通知，验证旧邮箱续接，与持续流量样本分开。提前使用足够有效期的票据并保持邮箱容量边界；本轮不测票据过期或邮箱溢出。

MsgQ 场景的旧恢复检查沿用现有有限工具的显式 close/reconnect，不预设停掉 MsgQ 必然主动关闭客户端 socket。流量期间观察到的断连、错误或响应超时按实际记录；确认 owner 正常释放后，工具驱动这次恢复检查及重新 Login。此为验收编排，不等于生产客户端已经具有同样的自动恢复策略。

Ready 只证明接入完成。恢复完成点是正式业务响应到达；新 Session 还必须执行应用既有的 Ready 后初始化。恢复前后不得同时用两条连接驱动同一测试角色。未知执行结果只记失败，不重投；SLG 的 Rename 可能已生效，即使响应丢失也不得称为“未执行”。

## 5. 每个窗口的顺序与证据

```text
工具准备正式包、依赖和会话，采集实例/owner/票据与连接身份
  → 客户端报告准备完成，固定目标和对照组
  → 客户端启动 180 秒固定计划，报告实际起点
  → 第 30 秒：Go 编排器对一个目标实例 DrainAndStop
      → 等待真实退出和目录变化
      → 按该类场景执行恢复检查、启动替换实例
      → 等待 Ready 及首条成功业务响应，记录恢复完成点
  → 第 180 秒：停止新计划，等待已有样本各自到期
  → 汇总全量/分组/分阶段数据及契约断言
  → 正常关闭剩余进程，核对存储、退出记录与专用资源残留
```

MsgQ 先检查旧恢复拒绝、在存活 MsgQ 建新 Session，再启动替换 MsgQ；Agent 先启动替换实例，再恢复原 Session。三类顺序不合并成一套错误的通用恢复流程。

计时使用客户端单调时钟；控制文件带窗口/阶段标识并只触发一次。报告同时保留双方墙钟，不能靠不同进程各自 sleep 推断准确切点。各秒损失归到原计划时刻，阶段边界不重复计数。

沿用现有停止 35 秒、启动就绪 25 秒、客户端阶段 45 秒的上界；它们是失败终止界限，不是可接受中断时间或延迟目标。阶段失败保留当前窗口及所有计划损失，停止后续发布并清理；不得无限等待或自动开始一轮“替代成功”窗口。按需等待清理不会延长流量分母。

每窗至少输出：参数与构建身份、P/A/N/C/F、尾部完成/迟到/重复数、按秒计数、每组 owner、成功请求延迟、调度迟到、阶段开始结束、断连到 Ready/首条业务响应时间、SID/CID 变化、实例退出码及清理结果。清理失败独立失败，不能因吞吐达标忽略。服务端/客户端逐消息日志维持现行级别，不额外开启高频画像。

SLG Rename 沿用正式持久化链路。停止发流并结算样本期限后，每个角色执行一次独立最终标记改名并等待匹配响应，排水后用该确定值核对 Mongo；不用“最后一个成功流量响应”推断最终状态。当前没有角色名称只读协议，因此此处是最终业务确认，不新增生产协议，也不证明所有超时请求都执行过。World 保持原实例，复用两条行军完成路径及既有移动/最终保存检查，不扩展 World 玩法。

## 8. Go 发布编排实施进度

两组现有 `cmd/cluster-e2e.sh` 新增 `--session-rollout`，默认总期限 15 分钟，排斥其他故障/合服模式。复用有限生命周期入口中的包构建、双实例接入拓扑、进程控制和 ownership 清理，不修改生产运行时。窗口使用不同角色和样本区间，准备完成后固定分组；客户端 Ready 不替代 Redis 绑定证据。恢复后、第 170 秒均采集 CID/owner；SLG 同步验证业务槽位身份及代次。MsgQ 重登额外核对旧 owner 已释放、新 generation、旧 SID 未重绑及本轮应用恢复拒绝日志。

## 9. 离线通知、新登录与 SLG 持久化取证

```text
Agent 窗口
旧 Agent 正常退出 → 存活 Agent 上的独立角色发送有限业务通知
  → 新 Agent 启动 → 原 SID 恢复 → 收到指定通知并推进下行序号
  → 另一独立角色经 Login 实际选中新 Agent → 业务探针 → 关闭探针连接

SLG 每窗收尾
停止发流 → 等待样本期限 → 封存统计
  → 全部角色最终标记改名并确认 → 查询 World 归属
  → 直达 World / Role→World 完成通知 → 专用网格单位移动确认
三窗结束 → 保持 Fusion 消费在线，限时等待角色 Mongo 最终标记
  → 全部服务正常排水退出 → Mongo 再读回角色与 World → 成功才清理专用数据
```

- 两组通知分别使用既有 `GlobalNotify` / `System_Notify`，通过 `System_PublishNotify` 发布；发布响应不等于收到通知，恢复阶段必须等到指定内容。所有操作使用正式客户端与协议，不修改生产自动恢复。
- Agent 选点使用真实 Login 候选，阶段命令只提供当前实际 InstanceID；不重写票据。发布者与新登录角色独立于 40 个流量角色。通知、新登录、最终标记和 World 探针不增加或缩小固定分母。
- SLG `finalState` 保存每个角色的最终标记，以及两条 World 完成通知和移动响应。Go 核对角色集合与 World 宿主，正常排水后读取 120 个角色的 Mongo 名称、RoleID、OriginServerID，以及最后一窗口专用 World 单位坐标和非零文档版本，写入 `session-rollout-persistence.json`。缺少最终状态、旧值、未写回版本均失败。
- 本地回归覆盖通知延迟/缺失、序号推进、新 Agent 选点、旧响应不能充当最终值、错误 World 宿主、Mongo 角色旧值/World 未写回和收尾期限。工具测试使用内存传输及持久化读取夹具；没有启动真实集群，没有新产生 99.99% 或真实 Mongo 写回结论。

## 11. 接入拒绝语义修复与补验（已完成）

根因：MsgQ `ErrRouteUnavailable` 没有对应的接入结果帧，Agent 直接关闭 WebSocket；客户端把 Ready 前断线／传输错误构造为 HandshakeRejectedError，导致 TCP 的历史通过也不是明确拒绝证明。

- 新增无载荷 HandshakeRejected 控制帧，仅表示本次接入未被接受，不宣称票据永久失效；SessionEnded 保留永久失效语义。Agent 不向客户端泄露内部错误文本。
- 客户端只从明确结果帧创建应用拒绝错误；断线及网络错误保持结果未知，不重投、不自动重新登录。明确拒绝后到达的关闭事件不能覆盖已收到的结果。
- 先跑真实 WebSocket 和客户端错误分类回归，再复用两组现有 session-rollout 全套入口补验 MsgQ，SLG 同时核对全部120角色及World最终持久化。不新增窗口选择配置，保留六窗完整计划分母与正常退出证据。
- 本轮不提交、不跑云测试；99.99% 与恢复、持久化独立判定，Agent 发布空窗不在本轮扩展修复。

补验发现并修正工具的持久化完成边界：WriteBack 按 GD mode 保存，Fusion 排水保证 Redis 写入及持久化任务发布，不承诺延迟 Mongo 消费已经完成。首轮第三窗 40 个最终标记均在 Redis，Mongo 尚旧；工具在关停消费者前增加总计 45 秒的只读等待，随后仍正常排水并独立读取全部角色和 World。没有缩短生产延迟、人工写库或修改流量分母；旧值等待超时、身份不符或数据库错误均失败。

最终两组 MsgQ 恢复与 SLG 120 角色、World 完整持久化通过；全计划完成率仍有未达标窗口。测试、失败与最终结果见[补验报告](session-rejection-acceptance-20261104.md)。本阶段不再扩大实现范围。
