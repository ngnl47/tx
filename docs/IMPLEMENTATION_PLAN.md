Agent 单机吞吐诊断接续（2026-09-26）：四机万连×10/s 短测将 Agent `Rec` 的长尾拆成 `SessionID % 64` lane 等待和流 `Send+Recv`：配对样本 P99 分别约 146.2ms 与 147.4ms（两阶段之和），完整 `Rec` P99 147.5ms；MsgQ `mailbox.Rec` 独立采样 P99 仅 7µs。Agent P8 平均约 7.3 核，八个客户端 worker 事件循环利用率约 92%，两侧都接近饱和。定位结果并不证明增加 lane 能提升端到端吞吐，先前 64→256 对照没有收益。复核 9 月 25 日历史 CPU profile 时，Agent 客户端 socket 的 `writev` 栈约占 CPU 样本 15%，但它来自 16 lane 的扰动构建；现实现已用 `net.Buffers.WriteTo`，不能据此直接重写。保留 64 lane、关闭租约候选，不继续 rate/lane 盲扫；下一项在 64 lane 同类负载下采集短 CPU profile，并对齐 TCP 收发与客户端事件循环，确认当前主要 CPU 路径后再做短 A/B。完整数据、采样限制和归档见[RecStream 等待拆分报告](audits/2026-09-26-recstream-lane-wait-isolation.md)。

当前接续点（2026-09-20）：NATS 正式迁移、T5 可靠任务工程闭环及 T6 整合收益已完成阶段验收。上下行保持直连 gRPC，实体间 RPC 使用 Core NATS，可靠任务使用可选 JetStream；MsgQ 与 etcd 保留现有职责。生产同步策略、目标任务负载、长期稳态和物理故障域验收尚待部署条件，运维工具及远程脚本暂缓。

单机 P2 长尾定位（2026-09-25）：2,000 会话×10/s 下，低比例双端采样确认 Ping Handler 耗时可忽略；Actor `Call` 的邮箱入队到执行 P99 约 1.33 ms，而 Agent→MsgQ `Rec`、`Call` 请求抵达与响应返回更长。只改 Agent P2→P4→P2 的同档回退使端到端 P99 约 85→27→86 ms，通信区间同步缩短再变长；gRPC Binary Log 明显扰动负载，不采纳其分段值。随后无采样普通构建三轮均完成 600,000/600,000、零错误/未发送，P99 为 85.48→27.11→80.72 ms；P4 Agent 平均多用约 0.37 核，整机仍约 28% 空闲。当前目标是消除单机通信链路的明显开销、降低部署成本，**不以增加 Agent 宿主机代替优化**。已无吞吐收益的 `recLeaseInterval` 候选继续默认关闭。不从单机样本推断四机万连 20/50 容量。见[单机分段报告](audits/2026-09-25-single-host-agent-parallelism.md)。

同机直连长流对照（2026-09-25）：同一普通构建、四服务各 P2、2,000 TCP 会话×10/s、30 秒窗口，仅 Agent 切换 `directCallStream`，Unary→Stream→Unary 的 P99 为 81.38→29.28→82.24ms，Agent CPU 约 1.83→1.52→1.83 核；独立 Stream 复测 P99 28.49ms、Agent 1.52 核。前三轮中两次 Unary 和 Stream 复测均 600,000/600,000、零错误/未发送；首次 Stream 少发 3 条，已发请求全部完成。固定实例数下已见明确的单机 CPU 和延时收益，但仍需较长稳态及断流/排水验收才能决定是否默认启用；不以增租 Agent 宿主机作为当前优化方向。原始归档和限制见[单机分段报告](audits/2026-09-25-single-host-agent-parallelism.md#同机直连长流对照)。

双向长流模板启用（2026-09-25）：同机四服务各 P2、2,000 TCP 会话×10/s 的 Stream 三分钟测试完成上下行各 360 万条，零失败/未发送，P99 29.29ms，Agent 平均约 1.52 核；排水定向测试覆盖关闸后新请求拒绝和已接受调用继续完成，20 轮 `-race` 通过。`txgame`、`txgameslg` 部署资产及集群验收模板显式启用 `directCallStream`；tx 库仍保留默认 Unary 及配置回退。现有单机的真实进程集群验收已通过 Agent、Game、MsgQ、Login 的排水与重启，Agent 新实例用新连接续接原 SessionID 和 MsgQ 邮箱，结束后恢复原四服务压测夹具。下一项回到单机吞吐主线：评估 Agent→MsgQ `Rec` 以保持原确认契约的长流传输做同机 A/B；跨机故障、有状态节点及万连 20/50 不对称负载分别验收，不能从本次单机功能验收外推容量。见[稳态与进程验收证据](audits/2026-09-25-single-host-agent-parallelism.md#三分钟稳态与默认启用)。

会话租约可行性证明（2026-09-24）：Agent 本地推进上行游标并异步同步 MsgQ 的薄层方案，在普通断线重连时可能重复分派已执行消息，或使恢复 Ack 回退；`Rec` 还承担下行 Ack 与会话续期，不能只计算省去的一次调用。新建 Session 重新认证与授权，Seq/Ack、未确认下行与旧会话无关；Role Actor 与 GD 是否重载取决于各自生命周期。同址 Agent 重启的原 Session 恢复现允许已签名旧票据经新运行实例验签，以 MsgQ 原邮箱存在为恢复前提，客户端限次自动重连并保留未确认上行；仍不支持旧地址变化后的目标发现，也未改变逐条 `Rec` 契约。`txclient` 对旧会话未确认请求仍阻止新登录，不自动放弃结果不明的请求。真实八进程验收已覆盖同址 Agent 排水重启后原 Session、MsgQ owner、Seq/Ack 与待发下行续接，以及原邮箱明确终止后的恢复拒绝。下一项评估是否进入租约受控原型，或先只试验保持当前契约的 `Rec` 长流传输。见[会话租约证明](audits/2026-09-24-session-lease-proof.md)。

Seq/Ack 简化（2026-09-24）：上行 Seq 改为严格递增、允许跳号，旧号由 MsgQ 幂等忽略；两套参考客户端移除未确认上行重放队列，恢复原 Session 时不自动重投结果未知的请求，新登录始终建立独立 Session。下行在业务回调成功后推进最大 Seq，空闲时每 5 秒检查并发送尚未捎带的独立 Ack；两套示例的 MsgQ 单会话 1024 条、8 MiB 配额不变。逐条 `Rec`、下行 StreamFetch 与当前分机拓扑不变。本轮先完成契约与本地回归，不据此宣称万连性能收益；下一项沿既有 1:1 上下行档位做同版对照，再决定是否评估 `Rec` 长流或新的控制流/数据流拆分。

上行邮箱接纳边界（2026-09-26）：客户端不维护上行重放队列，也不接收服务端上行 Ack；客户端只用 UpSeq 表达递增顺序（允许跳号），只在上行携带已处理的最大 DownSeq。服务端 Ready/DownMsg 的 Ack 固定为 0，FrameAck 仅由客户端确认下行。Agent 按 socket 读取顺序，经 Agent→Game 双向流逐条等待 Actor 邮箱接纳后再读取下一条；不同连接并行，同一流内不等待业务执行，同一 Actor 邮箱仍按序处理。入队成功后，Agent 才推进 MsgQ Rec 或本地 Rec lease；业务返回与错误仍由 Actor 发布到 MsgQ 下行邮箱。失败或结果未知时不自动重投上行。客户端双栈全套测试、tx/txgame 相关 Go 包测试通过；性能收益尚未重新测量，且当前仅验证单流顺序接纳，不代表跨实例故障下的 exactly-once。

## 待决策能力

下列事项在进入实现前必须重新评审需求、边界和成熟依赖，不能以占位配置或兼容接口提前进入主线。

### 外部业务配置生成

txgame 当前使用项目维护的类型化配置最小契约；txgameslg 的 Login 列表从项目资产加载。
后续扩展 txgen 的外部配置生成前，需明确 Excel 输入、类型推导、JSON 输出与加载契约；两套示例分别生成和维护，不相互引用。

### getter 触发的懒加载

当前已加载字段状态只描述读取结果，getter 不执行 I/O。若要支持 getter 懒加载，需要先确定：

- loader 由谁持有，是否允许数据对象依赖运行时；
- getter 如何返回 I/O error；
- Actor、Procedure 和普通请求三种所有权边界下是否允许隐式读取；
- 并发加载、失败重试和部分字段定位如何保持一致。

在这些问题决策前，不生成隐式 I/O getter。

### 可靠业务消息

可靠任务需要发布确认、业务执行后确认、重试与死信处置；已接受成功后结果/ACK 丢失的重复窗口，不建设完成表或要求 GD 记录幂等字段。`modules/msgq` 是客户端会话邮箱，它不能代替可靠业务消息。

按上述试验计划验证 JetStream；永久加载拒绝转死信，业务明确无法处理并结束任务则确认，暂时故障重试。ACK 不等待 GD 刷盘。MQ 产品最终采用以真实链路验证为准。

### 控制面认证与 TLS/mTLS

当前控制面和内部 gRPC 只要求调用方显式选择 TLS credentials 或本地 insecure。生产认证、证书加载、轮换和权限模型尚未实施。后续设计必须保持 `Sender`、`Delivery`、`Drain` 和槽位交接的业务 API 稳定，并优先适配本地研发与云私网部署。

### 异常接管与执行者归属

逻辑槽位支持受控排水后的 generation CAS 交接；Mongo 文档版本只拒绝已经过时的写入基线，不识别实例或槽位，也不能阻止错误路由的执行者重新读取版本后发起新写入。
异常宕机、网络分区和自动接管的通用租约与调度策略仍需独立评审。不能假定 `WaitGroupContext`、etcd 成员过期或 Mongo 条件更新已经独立保证全局只有一个业务执行者，不将此待决策能力提前作为当前存储方案的承诺。

### 可选存储 backend

RedisJSON/ReJSON、SQL 和其他存储后端不进入当前主线。评审时必须先确认目标云服务支持、本地测试方式、分片路由、部分读写收益和运维成本；通用 Store、`change.Source` 和变更文档契约不能依赖具体后端。

### 可选业务工具替换

`util.EventBus` 和 `util.DelayQueue` 是面向业务的可选工具。只有候选成熟库完整覆盖现有并发、顺序、取消和 transactional async 语义，并通过回归与 benchmark 后才替换；不能因为 tx runtime 当前未直接引用而删除。

## 明确不做

- 不在 tx 内实现分布式事务、跨实例锁或 Redis/Mongo 原子双写。
- 不为 Fusion 热写与延迟任务发布增加同槽持久交接索引、启动全槽扫描或容量闸门；进程存活期由本地去重重试和结构化错误日志保障任务发布。
- 不允许 Fusion 根记录物理删除；业务使用状态字段逻辑删除。
- 不把 Store、StoreView、变更文档声明为业务协议字段。
- 不把 Actor 与 GD、Store、Procedure 或持久化 Runtime 强绑定。
- 不在普通持久化链路重新引入字符串路径变更批次或操作重放日志。
- 不为尚未确定的 backend、协议或运维能力保留无效配置。
