# Submit 本地短时突发负载验证

日期：2026-10-29。以下保留接纳额度 256/1024/4096 的原始实测结果。当前默认已按配置决策改为执行并发 **64**、总接纳额度 **8192**；8192 未纳入本次负载验证，不能将下表作为该配置的性能结论。

## 测量方法

- 本机 Intel Core i9-9880H 2.30GHz，darwin/amd64，Go 1.27.0，`GOMAXPROCS=4`。非独占性能实验机，不与云端 P8 直接换算。
- 每轮 1 秒，每 50ms 注入 512 项，共 10,240 项；8 个提交协程按绝对时间计划发压，不等待 Future，也不重投。每轮结束等待所有 Future 与 Runtime 排水结束。
- 执行并发 16/64/256 × 总接纳额度 256/1024/4096 × 三类负载，每组重复三次，共 81 轮，独立期限均为 10s。总接纳额度含执行与排队；256/256 不留等待队列。
- CPU：独立锁，业务体执行 128 次 SHA-256；I/O：独立锁，持锁等待 2ms；热点：输入中约 20% 争用同一锁，其他独立，也持锁等待 2ms。计时器等待是模拟 I/O，不访问 Redis/Mongo。
- 使用真实 `Runtime.Submit`、Procedure 加锁/释放及排水路径；没有 Store 修改、EntityCache 或 WriteBack I/O。仅基准记录时间，不给生产路径增加探针。

```text
计划发起 → Submit 前 → Procedure.Locks → Process → OnFinish → Future 完成
         发生器迟到     准入/排队/调度     锁等待      事务完成回调

统计吞吐：成功 Future 数 ÷（一秒注入窗口 + 超出窗口的尾部排空时间）
```

“入口 P99”是 Submit 前到 Locks，包含准入、FIFO 等待和 Go 调度，**不等于纯队列等待**；“锁 P99”是 Locks 到 Process，包含锁获取前的少量事务准备；“事务 P99”到 OnFinish，不包含 Future 发布的最后收尾。延时只统计实际经过相应阶段的请求，必须同时看拒绝率，不能用拒绝大量慢请求后的低延时表示性能更好。各阶段 P99 不能直接相加。

发生器迟到由所有尝试记录。三类负载的每组发生器 P99 见表；81 轮范围 0.89～44.67ms，完整注入窗口 1.000～1.033s。个别轮存在本机调度抖动，因此不对毫秒级差别做过度归因。热点比例指输入，拒绝后的实际接纳比例可能变化。所有接纳项最终成功，执行失败与期限超时均为 0；这不代表全部尝试成功。

## 对默认值的判断

1. **1024 有吸收突发的依据。** 固定 64 并发时，2ms I/O 的 256 总接纳额度拒绝 50%，1024 则三轮均无拒绝，事务 P99 约 18.6ms；4096 没有增加本轮完成吞吐。这里的 512 突发是实验输入，不能据此推广任意峰值都足够。
2. **64 比 16 更适合本轮 I/O 等待负载。** 总接纳 1024 时，16 并发拒绝约 27.5%，入口 P99 约 151ms，完成吞吐约 6,719/s；64 并发达约 10,217/s、无拒绝。64 已跟上输入，不能将 10,217/s 当作它的吞吐上限。
3. **256 存在延时收益，但不是通用替代值。** 同一 I/O 负载、总接纳 1024 下，事务 P99 从约 18.6ms 降至 6.1ms；短 CPU 负载没有吞吐增益。更大并发的资源占用与真实业务混合负载尚未验证，不自动把默认值改成 256。
4. **扩大队列不能解决处理能力不足。** I/O 的 16/4096 虽无拒绝，事务 P99 升至约 548ms，含排空吞吐仍约 6,769/s。不能仅按接纳率选额度。
5. **热点锁使更多任务在执行额度内等待。** 总接纳 1024 时，16/64/256 并发的完成吞吐均约 2,100/s，但锁 P99 约 28/145/607ms。64/1024 的拒绝率仍约 68.2%，事务 P99 约 594ms；它不能满足这种持续热点过载。应先检查持锁工作与业务竞争域，而不是单纯扩大并发和队列。

配置时先测真实事务持有执行额度的时间，包括等锁、I/O 与同步后续过程；以到达率乘平均占用时间估计必要并发，再用突发与可接受等待预算核对接纳额度。本轮没有测定生产内存预算、长时间稳定性或 99.99% 游戏端到端完成率。
