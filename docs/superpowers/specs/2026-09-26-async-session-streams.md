# 上下行异步流重构设计

## 目标

在 tx 当前 Agent、MsgQ、Game 的 N×M 直连实例拓扑中，减少逐消息同步 RPC 等待，同时保留同一客户端会话上行顺序和 MsgQ 下行邮箱的 Seq/Ack 裁剪语义。每条 gRPC 流都连接到路由选定的具体服务实例；不引入代理负载均衡或定时等待合批；只有明确未入邮箱的旧归属拒绝允许重新寻址单次投递，未知结果不重投。

## 已确认的消息语义

- 客户端同一 socket 的写入顺序是该连接上行顺序。Seq 只要求递增，可跳号；Agent 忽略不大于已见游标的旧消息，不要求客户端回拨或重放上行消息。
- Agent 是活动 Session 的 Seq/Ack 权威。Agent 将上行消息写入已选定 Game 实例的 RPC 流，不等待逐条邮箱接纳或业务完成回执。
- Game 顺序读取该流，并按接收顺序将消息投递到对应 Actor 邮箱。不同 Actor 可并行。目标关闸、邮箱拒收或流断开可导致消息丢失，不自动重投。
- Game 等业务服务向 MsgQ 发布下行消息时不等待逐条入队回执。MsgQ 为实际接收的下行消息分配序号并保存在会话邮箱；Agent 报告客户端已收取的最高 Ack 后，MsgQ 可据此裁剪已确认消息。
- Agent 重启后的新登录创建独立 Session，不迁移旧 Agent 的 Session 状态。MsgQ 的会话邮箱仍按现有 Session 标识和 Ack 规则管理。
- Mailbox 仍是 MsgQ 进程内状态，沿用现有限额；gRPC 流不增加磁盘持久化保证。消息未到达 MsgQ 或 MsgQ 丢失内存状态时，不承诺恢复。

## 流拓扑

### Agent 到 Game

复用现有直达具体 Game 实例的 `CallStream` 传输。Agent 对同一连接按 socket 读取顺序串行写入；Game 的流接收循环按接收顺序同步调用 Actor 邮箱的内存投递入口，不为每条请求另起并发分派 goroutine，也不等待逐条响应。Actor 邮箱在投递后独立串行处理该 Actor 的消息。

### Agent 与 MsgQ

新增 `MailboxStream` 双向流。每个 Agent 进程对每个实际承载其会话的 MsgQ 实例建立一条流，并在应用协议中复用多个 Session；不通过服务名负载均衡已建立的流。客户端到服务端方向承载带 `SessionHeader` 的会话建立/结束、上行接收游标与下行 Ack 更新、会话活动 Touch；服务端到客户端方向承载带 `SessionHeader`、下行序号及负载的消息。当前每次上行提交及客户端 Ack 都同步游标和 Ack，不逐条等待 MsgQ 响应；没有 Agent Rec lease 或定时低频同步。协议保留 Touch 续期入口，正式 Agent 不独立定时调用。MsgQ 保存最近同步的上行游标，以便原 Session 在同一或经授权的其他 Agent 上恢复。Agent 将返回消息按 Session 分派回本地连接。此版不合并多条会话控制更新为一个应用层批次。

每条 gRPC 流仅有一个串行写入者和一个串行读取者；两方向可同时工作。断流后不重投上行或已写出的控制消息。活动会话的邮箱流失败会关闭对应 socket；客户端恢复同一 Session 时重新登记，新的连接可重建到同一 MsgQ 实例的流；MsgQ 仍持有的未确认下行可按客户端 Ack 重发。

### 业务服务到 MsgQ

业务发布使用连接到具体 MsgQ 实例的 `PublishStream` 双向流。Game、SLGWorld 等业务服务通过流发送角色或 Session 下行发布；MsgQ 按实际接收顺序为该 Session 分配下行序号并写入邮箱，不逐条返回成功确认。仅当角色归属版本明确遭拒且消息尚未进入邮箱时，MsgQ 异步回报被拒的完整 `RoleBinding` 与载荷；发送方清除匹配旧缓存，并仅对这条确定未入邮箱的消息重新寻址、单次投递。结果未知或部分投递不重试。来自不同实例的并发发布只按 MsgQ 接收顺序排序，不承诺额外的跨实例先后关系。流写入错误或断开不触发业务消息重投。现有 Unary 发布 API 仅在仍有明确调用方时保留，不将其作为本次异步业务路径。

## 排水与错误边界

- 本地流写入错误、目标服务关闭准入或邮箱拒收按已确认的 best-effort 语义处理，不伪装成业务成功，不自动重投。
- 正常排水先关闭业务准入并停止新投递；已有邮箱工作按 tx 现有 Actor 排水规则完成。Session 流与 MsgQ 下行邮箱之间的最终 Ack 同步仍由 Agent/MsgQ 流协议负责。
- gRPC `Send` 成功只表示本地传输栈接受了写入，不表示对端业务已收到或执行。

## 验收

1. 对同一 Session 连续发送带间隔 Seq 的上行命令，Game 邮箱观察顺序与 Agent 写入顺序相同；不同 Session 可交错处理。
2. Agent→Game 路径不等待逐条接纳/业务响应；Game→MsgQ 发布路径不产生逐条成功应答。角色归属明确拒绝且未入任何邮箱时，失效旧缓存并重新寻址单次投递；未知结果不重投。
3. 一个 Agent→MsgQ `MailboxStream` 可交错服务多个 Session；Ack 只裁剪对应 Session 的已确认下行，服务端返回消息也能正确路由回相应连接。
4. MsgQ 下行沿每 Session 的邮箱序号递增；断流重建后，仅重发 MsgQ 仍保留且 Ack 未覆盖的下行消息。
5. 运行现有功能测试，并以同口径短时压测比较重构前后的吞吐、P99、错误和未发送计数；不将性能收益当作未测事实。
