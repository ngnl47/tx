# tx 架构审计标准

本文定义 `tx` 在重要里程碑、核心架构调整和发布前重复执行的架构审计基线。审计以数据正确性、长期维护和面向使用者的 API 质量为最高目标；性能判断必须有可复现证据，不能仅凭数据结构外观或经验下结论。

本标准不以包层级深度、import 路径长短或代码行数评价架构。包结构仍需检查职责内聚、依赖方向和导出边界。

## 最高原则

优先级从高到低如下：

1. 不产生脏数据、不丢失已受理状态、不把失败伪装成成功。
2. 公共 API 清晰、简洁、强类型，框架可代理的细节保持黑盒。
3. 核心计算与并发、I/O、具体存储和网络实现正交。
4. 性能优化有 benchmark、逃逸分析或 profile 证据。
5. 低频路径优先正确性和可维护性，不为追求表面零分配增加复杂度。

## 依赖层级基线

依赖层级使用设计文档的 L0-L4；它与后文性能路径 H0/H1/H2 无关。架构审计按以下方向判断职责是否倒置：

```text
L0 纯算法与通用契约
  -> L1 backend / transport adapter
  -> L2 可复用运行时组件
  -> L3 CMod 与进程级 server 装配
  -> L4 可选服务
  -> txgame 项目组合根与业务 facade
```

- 高层只能通过下层公开契约组合能力，不能读取下层实现字段或接管其生命周期。
- 契约优先由能力所有者声明。例如 RPC 注册契约属于 `modules/rpc`，只读实例目录属于
  `modules/discovery`，后台任务契约属于 `lifecycle`。
- 两个同级实现需要复用逻辑时，先把稳定契约或中立 adapter 下沉；禁止一个
  `server/services/<name>` 直接导入另一个 `server/services/<name>` 的实现。
- `server.Server` 是进程资源的唯一 owner。Redis/Mongo client、gRPC Host、Actor Runtime、事务 Runtime、
  discovery 快照和根 `WaitGroupContext` 的 Start/Stop/Shutdown/Replace/Flush 权限不能透传给服务。
- `txgame` 只负责配置转换、业务回调、业务 facade 和服务选择，不复制 tx 的 runtime/host/service
  生命周期实现。
- L4 服务只能声明直接 CMod 依赖；Redis/Mongo、RPC Host、Scheduler、Transaction Runtime 等资源由 L3
  依赖图按闭包唯一装配。未进入闭包的配置不得被语义校验，也不得创建外部资源。
- 包名或目录深度不是层级证据；实际判断依据是依赖方向、接口所有权和资源生命周期。

## 审计严重级别

- **P0 正确性**：可能产生脏数据、丢数据、重复写入、并发覆盖、错误成功或无法恢复的状态。
- **P1 架构/API**：职责错位、依赖倒置、生命周期不完整、公共 API 泄露框架细节或强类型契约失效。
- **P2 性能**：已处于热点路径，并有证据表明存在显著分配、复制、锁竞争或复杂度退化。
- **P3 维护性**：命名、文档、包内组织、低频冗余或可读性问题，不直接影响正确性。

审计报告必须先列 findings，并按 P0 到 P3 排序。每条 finding 至少包含文件与行号、触发条件、实际影响、证据和建议方向。没有发现问题时，也要说明未覆盖的测试和残余风险。

## 1. 内存逃逸与内联

### 路径分级

- **L0 高频内核**：例如生成 Store 投影、路径拼接、队列游标推进、帧编解码。目标是零分配或接近零分配。
- **L1 请求链路**：例如 Store 操作、Agent 转发、RPC 中间件和存储文档构建。要求分配次数和字节数有明确上限，并通过 benchmark 验证。
- **L2 低频路径**：例如启动装配、配置解析、服务注册和错误构造。优先清晰与正确，不要求零分配。

### 检查规则

- 固定数组、值类型和连续 slice 只有在基准证明受益时才能作为优化依据。大值对象复制可能比少量受控分配更昂贵。
- 检查热点中的 `any`、闭包、反射、字符串拼接、临时 map/slice、格式化和接口装箱。
- 内联是编译器优化结果，不得为了内联破坏合理的抽象边界。
- 结构体布局需要结合 `unsafe.Sizeof`、字段对齐、复制频率和缓存行为判断，不能只看字段字节数相加。
- 优化前后必须在相同机器、Go 版本、参数和数据规模下运行基准。

### 证据

```sh
go test ./tests -run '^$' -bench '<目标基准>' -benchmem -count=5
go test ./... -gcflags='all=-m=2' 2> /tmp/tx-escape.txt
go test ./tests -run '^$' -bench '<目标基准>' -memprofile /tmp/tx-mem.pprof
go tool pprof /tmp/tx-mem.pprof
```

只有热点基准确认问题后才使用 profile 深挖。逃逸分析中的输出必须关联到真实调用频率，不能把所有 heap escape 都当成缺陷。

## 2. 纯计算内核与并发隔离

本标准使用“纯计算内核无共享可变状态”，不把“代码里没有 Mutex”误称为严格意义上的 lock-free 算法。

### 检查规则

- `change`、路径转换、文档投影等纯算法不应持有进程级共享锁，也不应依赖存储、RPC 或服务生命周期。
- 队列、连接、事务运行时、状态管理器可以使用同步机制，但锁必须靠近被保护状态的所有者。
- 检查锁顺序、持锁 I/O、持锁回调、重复加锁、锁内序列化、超时退出和失败释放。
- 单线程所有权可以替代锁时，应明确 owner 和调用线程契约；不能仅靠注释假设调用方不会并发访问。
- 并发组件必须覆盖关闭、排水、取消、重试和外部服务失败场景。

### 证据

```sh
go test -race ./... -count=1
go vet ./...
```

必要时补充阻塞 profile、mutex profile 和可重复的竞争测试。race 通过不等价于并发语义正确，仍需审查状态机和 happens-before 关系。

## 3. 强类型与编译期契约

### 检查规则

- GD、Store、集合包装、事务锁键、命令描述和路由描述优先由泛型或 txgen 生成强类型 API。
- 公共入口不得依赖未经检查的类型断言，也不得把类型不匹配转换为 panic。
- `any` 只允许存在于真实动态边界，例如 Delta 值、序列化适配器和插件扩展点；进入强类型内核前必须完成显式校验。
- 生成代码优先直接调用、具体类型方法和可验证的类型分支，不使用反射模拟本可在生成期确定的关系。
- 生成输入中的冲突、缺失和非法组合应在 txgen 阶段失败，不能推迟到业务运行时。
- 不为伪需求保留动态兼容层；已经废弃的中间接口、迁移结构和旧测试应持续清理。

## 4. 边界防御与语义保持降级

系统只能执行两类行为：明确失败，或者执行能够保持原始业务语义的显式降级。

### 允许的降级

- Mongo 路径无法安全表达动态 map key 时，提升为整个字段写。
- Delta 路径超过最大深度时，提升为最近可完整表达的祖先字段写。
- Snapshot diff 发现 map/slice 长度或元素身份变化时，提升为能够保持容器语义的整元素或整字段写。

降级必须可观测，并有测试证明降级后的最终数据与当前 GD 一致。

### 禁止的自愈

- 自动修复数据库中的异常类型或拓扑。
- 把类型错误的父字段替换成新容器后继续执行。
- 猜测缺失字段、未知返回值或不完整响应的业务含义。
- 外部服务异常、未知状态或无有效写入时默认成功。

### Flush 与高危写回

- 写回前检查对象身份、记录键、路由信息、依赖装配和 Delta 可解析性。
- 成功前不得清理 dirty 状态；失败必须保留可定位或可重试的状态。
- 检查旧批次、旧 revision、并发回源和延迟任务是否可能覆盖更新的数据。
- 外部服务波动以 `error` 返回并保留状态，不得触发业务进程 panic 或后台 worker 静默退出。

## 5. 依赖正交性与数据不可变性

### 依赖规则

- 核心计算包不得反向依赖具体 Redis、Mongo、gRPC、Actor 或项目业务实现。
- 存储 adapter 依赖通用 change/storage 契约；通用契约不能依赖 adapter。
- `tx` 不依赖 `txgen`，生成代码只依赖 `tx` 的稳定公开契约。
- 可选 module 不能把自身生命周期或配置要求注入不使用该 module 的核心路径。
- 禁止循环依赖，也要检查通过全局 registry、回调或 `any` 形成的隐式反向依赖。

### 跨协程所有权

Go 没有语言级只读 slice。零拷贝分发必须通过明确的所有权转移契约保证安全：

```go
err := queue.Publish(payload)
```

发布成功后，调用方不得修改、追加或复用 `payload` 的底层数组；消费方只能读取。无法保证该契约时必须复制，不能把共享可变引用称为不可变数据。

审计队列、广播、异步网络发送和缓存时，需要检查：

- 谁创建数据、谁拥有数据、何时转移所有权。
- 是否有多个 goroutine 读写同一 backing array、map 或业务对象。
- 是否在只读发送阶段执行 `append`、原地编码或复用缓冲区。
- 广播是否只共享不可变 payload，而不是复制或共享可变消息对象。

## 6. 公共 API 与信息隐藏

`tx` 是给业务开发者使用的库。默认 API 必须清晰、简洁、强类型；框架能够代理的装配与运行细节不得泄露。

### API 分层

1. **业务层**：默认推荐入口，稳定、简短，不要求理解 runtime 内部结构。
2. **扩展层**：供项目装配、adapter 和业务 facade 使用，暴露必要接口但不暴露实现状态。
3. **内核层**：供高级用户和框架扩展使用，允许精细控制，并明确所有权、并发、生命周期和错误契约。

高级接口也必须是受控 SPI，而不是把具体 runtime 暴露出去。第一版允许复用已经装配的 Redis 路由和
逻辑槽位 Store，但不允许关闭连接、替换 discovery 快照、停止共享 gRPC Host、取得 Actor 生命周期所有权，
或主动 Flush/Shutdown 事务 Runtime。

### 检查规则

- 常规业务优先使用 `db.Save(role)` 这类 facade，不接触 Writer、backend、Fusion 内部对象或装配细节。
- GD 保持纯数据职责；Store 只在受控标脏、投影或高级存储路径中显式出现。
- 公共 API 不要求调用方传入框架可静态生成或运行时维护的 loader、record key、mode 等信息。
- 常见操作不依赖布尔参数组合、过长 options 链或未在类型中表达的成对调用约定。
- 同一语义只保留一个推荐入口；不因历史兼容保留重复 facade、别名方法和迁移 API。
- Redis、Mongo、etcd、RPC 等外部服务错误通过稳定且可识别的错误返回，不得 panic。
- 高级 API 单独归类并记录契约，不能混入新手主路径示例。
- 普通服务应接收受控能力门面；它可以执行已授权业务操作，但返回的动态值不能通过类型断言重新取得 owner API。
- `Start/Stop/Shutdown/Close/Replace/Flush/Cancel/Wait` 等所有权方法默认只存在于装配层，除非该服务
  明确拥有对应资源。
- 接口应围绕使用方需要定义，避免只有单一实现、没有替换价值的装饰接口。

## 包结构审计

包层级深度不是评价指标。每个包必须能回答：

1. 它唯一负责什么？
2. 普通用户如何使用，或为什么不应直接使用？
3. 它依赖哪些下层契约？
4. 修改内部实现时会影响哪些调用者？

需要重点识别：

- 同一包同时承担算法、I/O、装配和业务 facade。
- 只有转发作用、没有稳定契约价值的过渡包。
- 为测试方便而扩大生产导出面。
- 可选 module 反向污染核心包。
- 全局可变状态造成的隐式耦合。

## 成熟依赖替代评估

审计自研基础能力时，必须检查是否已有维护活跃、许可证清晰、语义契合的成熟库。引入第三方不是默认正确答案，也不能仅以“少写代码”为依据：

- 网络协议、数据库驱动、服务发现、标准编解码等通用基础设施优先使用成熟实现，并在 `tx` 外围保留最小适配层。
- Delta、Store、事务锁顺序、Fusion 回写等承载项目一致性语义的内核，只有第三方能够完整表达现有契约时才允许替换。
- 不为了复用局部工具而把第三方的数据模型、全局生命周期或动态类型系统扩散进核心 API。
- 候选库必须评估维护状态、Go 版本、许可证、依赖体积、可观测性、失败语义、性能证据和退出成本。
- 热点替换需要同规模 benchmark；并发组件还需要 race、取消、关闭和故障注入测试。
- 如果自研实现仅剩很薄的领域适配，且成熟库不能降低总复杂度，则保持自研并记录原因。

## 重复审计触发点

以下节点必须重新执行本标准：

- Store 树、同步投影、事务、状态刷盘等核心模型发生重构后。
- 新增存储 backend、RPC/Actor 基础设施或跨协程队列后。
- 公共 API、生成代码契约或模块装配方式发生重要变化后。
- 发布第一个稳定版本前，以及之后每个重大版本前。
- benchmark、race、线上 profile 或故障回放暴露架构性问题后。

普通 bugfix 不要求全量审计，但应检查受影响标准。

## 标准审计流程

1. 记录 Git revision、Go 版本、运行环境和工作区状态。
2. 生成包、导出符号和依赖拓扑清单，识别核心与可选 module 边界。
3. 从业务常用写法反查公共 API，确认框架细节没有泄露。
4. 审查 Delta、Store、事务、队列和 Flush 的数据所有权与失败语义。
5. 运行全量测试、race 和 vet；外部服务集成测试使用明确的本地环境。
6. 对已声明的 L0/L1 路径运行 benchmark、逃逸分析和必要 profile。
7. 按 P0-P3 输出 findings、证据、残余风险和建议实施顺序。
8. 审计结论经确认后再写实施计划；审计阶段不直接进行大规模重构。
