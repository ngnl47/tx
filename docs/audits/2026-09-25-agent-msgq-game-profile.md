# 万连 1:1 链路的 Agent、MsgQ、Game 同窗画像

## 测量边界

沿用 [Agent 双机扩容对照](2026-09-25-agent-horizontal-scale.md) 的同版服务端：两台 Agent 宿主机各运行一个 `GOMAXPROCS=8` 进程；MsgQ 与 Game 各两个 `GOMAXPROCS=2` 进程，分别位于各自的 8 核宿主机。一个独立的 8 核客户端宿主机运行八个 Node worker，以 TCP 建立 10,000 个 Session，计划每 Session 每秒 10 个 Ping，每个 Ping 对应一个 Pong。每 Session 最多四条在途；延迟按同 Session 的 Pong 顺序关联，仅用于诊断。正式窗口为 3 分钟，服务端六进程在同一窗口内各采集 20 秒 CPU pprof；系统 vmstat/pidstat 与客户端事件循环指标由旁路脚本采集，生产路径未添加采集逻辑。

第一次 100 会话准备因 `discovery: slot runtime is unavailable` 失败，**没有进入正式测量**。专用测试 etcd 的 1,024 个 role 槽位仍指向已退出的两个 Game InstanceID，而 Redis 测试角色归属为零。停止压测专用 Agent/Game 后，先备份、再仅清理 `/tx/e2e/txgame/discovery/slots/actor-v1.cm9sZQ.p` 前缀；新进程冷分配后的 100 会话冒烟完成上下行各 10,000 条，失败和未发送均为零。此步骤消除本次环境残留，不计作吞吐改进，也不代表正常排水交接策略。

## 正式窗口结果

| 计划上行与下行 | 实际上行与下行完成 | 失败 | 未发送 | 诊断 P50/P95/P99 |
| ---: | ---: | ---: | ---: | ---: |
| 各 18,000,000 条，100,000/s | 各 14,640,767 条，81,338/s | 0 | 3,359,233 条 | 487.85/611.85/702.11 ms |

这档没有完整供给计划流量，且延迟远高于讨论中的 P99≤60 ms 目标，不能称为万连 10/s 容量达标。八个客户端 worker 的事件循环利用率为 85.7%–86.8%，P99 停顿为 71–89 ms；总跳过计划槽位约 335 万。相较五 worker 对照，事件循环占用下降，却没有提高完成吞吐（五 worker 当时约 84,633/s）。两次不是严格 A/B：本次有 20 秒 pprof 采样，且各只运行一次；但“只增加客户端 worker 就能补齐计划负载”未得到支持。发生器仍可能限制更高吞吐，不能从本轮完成量反推服务端的精确上限。

20 秒 pprof 总 CPU 样本及测量期 pidstat 平均 CPU 如下。`GOMAXPROCS` 仅限制 Go 可同时执行的计算数，整机空闲不等于该进程仍能继续并行。

| 进程 | 20 秒 pprof 折算占核 | 测量期进程平均占核 | 宿主机测量期平均空闲 |
| --- | ---: | ---: | ---: |
| Agent A / C，均 P8 | 4.57 / 4.86 | 4.22 / 4.59 | 45.1% / 40.3% |
| MsgQ A / B，均 P2 | 1.57 / 1.56 | 1.47 / 1.46 | 59.5% |
| Game A / B，均 P2 | 2.00 / 2.00 | 1.85 / 1.85 | 53.1% |

Game 的两个进程在画像窗口均触及 P2；其较长时间的平均值也接近两核。这是比 MsgQ CPU 饱和更强的当前限制线索，但 CPU 画像本身不能证明每一次长尾都由 Game 排队造成。MsgQ 两进程均未达到 P2；仅凭 Agent 宿主机仍有空闲就断言 MsgQ 数量不足，与本次证据不符。

Agent A/C 的 pprof 中，`grpcConnection.Rec` 累计分别占 15.3%/16.2% CPU，Actor 直连 `Sender.Call` 约占 20.1%/20.3%，下行 `writeDownMsgs` 约占 17.2%/17.4%。MsgQ 的 gRPC `Rec` 入口累计约占各自 CPU 的 9.6%/10.6%，其内部 `Server.Rec` 约占 2.6%/3.1%。这些是**调用栈累计占比**，会与上层 gRPC 和业务栈重叠，不能相加或当成移除一次 RPC 后的实际收益。画像指出逐条 `Rec` 有可测成本，同时显示 Game 发布下行、Agent→Game 直连与客户端调度仍占有明显成本。

## 租约的下一步

可以开始设计并隔离试验 Agent 会话租约，但本轮数据不足以直接替换生产 `Rec`，更不能把租约视作同时移除整个下行链路。当前下行由 Game/World 直写 MsgQ、MsgQ 保留有序邮箱并经 `StreamFetch` 推给 Agent；这部分是独立于上行游标的职责。租约最直接能移出热路径的是 Agent→MsgQ 的**逐条上行接受确认**，同时必须接管本地 Seq 去重、客户端下行 Ack 的低频同步及纯上行会话续期。

设计试验时以当前代码语义为准：客户端上行 Seq 只需严格递增，参考客户端已经移除未确认上行重放队列；不能沿用早期文档中的“连续 Seq、客户端自动重放”假设。`Rec` 仍在业务调用前推进接受游标，且正常同 Session 断线恢复、同址 Agent 重启恢复都需能解释该游标。Agent 本地租约若仅靠定时写回 MsgQ，会在普通重连或排水时产生游标回退窗口；参见[会话租约可行性证明](2026-09-24-session-lease-proof.md)。受控原型应先固定同一 Session 的旧/新连接交接、游标刷新和 MsgQ owner 失效边界，再用同版三分钟 A/B 测量 `Rec` 被移出数据流的净收益。测试前还应把 Game P2 触顶和客户端供给单独排除，否则即使租约降低 Agent CPU，也难解释整体完成量不变的原因。

原始报告、四机系统采样、六份 pprof 与客户端八 worker 摘要保存在工程外 `tx-artifacts/cloud-20260925-agent-scale/profile8-10ps-3m/`。该轮结束时测试角色归属和旧 role 槽位均清零，六个被画像的服务曾恢复原配置；随后按下节约定改为 P4 复测。

## 每进程 P4 的部署复测

上面的 Game P2 是沿用早期四机基线的配置，不是两个 Game 进程共享 8 核宿主机时的满配对照。按新的部署约定，两台 Agent 宿主机仍各运行一个 P8；共享宿主机上的 Login、MsgQ、Game 均为两个 P4 进程。相同客户端、万连×10/s、1:1、3 分钟窗口与六进程 20 秒 pprof 口径下，100 会话冒烟仍完整通过，正式结果如下：

| 配置 | 上下行各完成/s | 未发送/计划 | 失败 | 诊断 P99 |
| --- | ---: | ---: | ---: | ---: |
| Login/MsgQ/Game P2，Agent P8 | 81,338 | 3,359,233/18,000,000 | 0 | 702 ms |
| Login/MsgQ/Game P4，Agent P8 | 99,042 | 172,433/18,000,000 | 0 | 223 ms |

完成吞吐提高约 21.8%，未发送减少约 95%；但 P4 档仍未完整供给计划流量，诊断 P99 仍高于 60 ms，**不能认定万连 10/s 已达标**。这次同时改变 Login、MsgQ、Game 的 P 值，所以只能证明原共享服务配置限制了整体吞吐，不能把收益单独归给 Game。两个 Login 在测量窗口基本空闲；六进程画像中，Game 各约用 3.55 核，MsgQ 各约用 2.64/2.67 核，Agent 各约用 6.52/6.56 核。测量期 Game 宿主机平均空闲 18.3%，MsgQ 宿主机 34.4%，两台 Agent 宿主机 23.7%/22.4%。客户端八 worker 的事件循环利用率约 90.6%–91.3%，跳过 172,391 个计划槽位，仍可能限制更高负载。

当前证据修正了“MsgQ P2 没有打满，因此扩 MsgQ 不重要”的过早推论：提高共享服务 P 值后，整体吞吐确实明显改善，但无法区分 MsgQ 与 Game 的各自贡献。租约仍可作为独立设计候选，P4 档 Agent 的 `Rec` 调用栈约占各自 CPU 的 12.9%/13.3%；它只能直接削减逐条上行确认，不会消除 Game/MsgQ 下行或客户端发压成本。下一轮若要量化租约净收益，应固定当前 P4/P8 配置、解决客户端供给，并分别采集上行 `Rec`、Game 执行和下行发布的延迟/排队证据，避免再次把同时调参的改善归因于单一路径。

P4 原始材料保存在工程外 `tx-artifacts/cloud-20260925-agent-scale/shared-p4-10ps-3m/`。测量后已清理测试角色归属与旧 role 槽位，八个服务以 Agent P8、其余 P4 的配置运行，临时 pprof 环境已撤销。
