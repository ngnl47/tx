# Agent 水平扩容三分钟对照（2026-09-25）

本轮目标是为后续优化上下行链路取得参考值，不寻找单台 8 核 16 GiB 实例的极限。远期目标是万连每会话上行 20 次/s、下行 50 次/s，允许增加 Agent 宿主机；本轮仅测万连 1:1 Ping/Pong、每会话计划 10 次/s。所有正式窗口均为 3 分钟，固定两台 MsgQ、一台承载两 Game 的实例及一台客户端实例；Agent 比较两种布局：两台宿主机各一个 `GOMAXPROCS=8` 进程，或各两个 `GOMAXPROCS=4` 进程。另保留旧的单宿主机双 Agent P4 基线。Login 仍按原分配流程分流，测试使用同一服务端二进制和两台 Agent 宿主机的私网。

## 单在途闭环结果

原压测入口每条 Session 等 Pong 后才发下一条 Ping。当往返耗时超过 100 ms 的计划间隔时，测试端会跳过发送时槽，因此这组数字同时受客户端闭环模型限制，不能解释为 Agent 或网络的原始吞吐上限。

| Agent 布局 | 上下行各完成/s | 未发送/计划 | P99 | Agent 宿主机测量期 CPU 空闲 |
| --- | ---: | ---: | ---: | --- |
| 单机 2×P4 | 66,340 | 6,058,873/18,000,000 | 264 ms | 0.7% |
| 双机 2×P8 | 82,875 | 3,082,561/18,000,000 | 215 ms | 37.1%、37.6% |
| 双机 4×P4 | 80,790 | 3,457,885/18,000,000 | 226 ms | 42.9%、43.7% |

在这个闭环负载下，双机 P8 比单机基线完成量高 24.9%，双机四进程比单机高 21.8%；P8 比四进程高 2.6%。三组都没有完整发出 100,000 次/s 的计划负载；不能据此推断“增加一倍 Agent 宿主机只增加约四分之一服务容量”。

## 多在途参考探针

为区分闭环等待与服务承载，`txclient` 的旁路 `cluster:perf` 入口增加可选 `--max-in-flight 4`；默认仍为 1。它沿同一计划时间轴发送、复用正式 AgentClient/Session/TCP 与 Ping/Pong，单 Session 最多保留四条在途，窗口结束等待尾部 Pong。Pong 没有请求 ID，按同 Session 回复顺序关联的延迟仅供诊断；主要看实际发送、完成和未发送。客户端仍为一台 8 核机器、五个 Node 负载进程。该探针不进入生产路径，也不改服务端二进制。

| Agent 布局 | 上下行各完成/s | 未发送/计划 | 诊断 P99 | Agent 宿主机测量期 CPU 空闲 |
| --- | ---: | ---: | ---: | --- |
| 双机 4×P4 | 82,268 | 3,191,715/18,000,000 | 642 ms | 43.7%、44.4% |
| 双机 2×P8 | 84,633 | 2,766,012/18,000,000 | 605 ms | 37.2%、39.1% |

两组均零请求错误；正式截止后约有 10,000 条尾部 Pong 才完成，约占全部完成数 0.07%，结果的每秒完成值包含这部分尾部收尾，不能当作严格窗口内速率。两布局前 50 秒与后 50 秒完成量没有持续下降，但都漏发了约 15%–18% 的计划。五个 Node 负载进程在四进程 Agent 布局下事件循环利用率约 95.1%–95.6%，在双 P8 布局下约 96.1%–96.3%；两台 Agent 宿主机仍有明显 CPU 空闲。多在途探针只比闭环多完成少量请求，却把延迟推高到约 600 ms，不能称为吞吐优化。

同口径的两个双机布局中，2×P8 的完成量高约 2.9%，P99 也略低；差距小于本轮未重复运行所能稳定证明的差异。暂以每台宿主机一个 P8 作为更简单的参考部署，不宣称四进程布局必然较差。相对于单机闭环基线，已观察的双机闭环完成量远未达到 2 倍；但此时测试端未完整供给计划负载，不能把它当作水平扩容效率结论。即使假设当前双机实测 84,633/s 可线性翻倍，四台 Agent 也只得到约 169,000/s 的 *1:1 推算值*，不足以验收上行 200,000/s，更不能验收下行 500,000/s。推算不是生产容量预测。

下一步先解决负载供给：在不增加生产路径采集逻辑的前提下，将客户端五进程扩到八进程或增加独立客户端机器，仍以 3 分钟窗口复测同一双机布局，确认 100,000/s 计划能否真正发出。只有在客户端供给充足后，才用 Agent/MsgQ/Game 的 CPU、RPC 与网络画像决定上下行链路下一处优化；随后单独做 20/50 不对称验证。不要继续用当前五进程负载发生器搜索细小速率阈值。

原始 `client.json`、四台服务端的 vmstat/pidstat 和远端客户端 `.timings.json` 位于工程外的 `tx-artifacts/cloud-20260925-agent-scale/` 对应目录。云端服务端是同一 SHA-256 为 `ff17326b599910a60e1bc3d9288f9f5d09c7c39f2e96c991dc5263576670e43e` 的候选版；全部测试结束后 Redis 角色归属已释放。此次没有更改服务端生产路径，所有对照均未达到计划负载完整发出与 MMO 延迟目标。
