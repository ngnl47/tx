后续 [T3a 共享响应与失败清理](2026-09-12-nats-shared-replies.md) 已完成增量修复和新的版本/拓扑对照；本文保留修复前的 T3 证据，不作为当前原型请求等待实现的说明。

日期：2026-09-12。**T3 同机筛选未达到正式迁移门槛，暂停 T4。** 当前原型本地直达有吞吐收益，但跨进程 Call 稳定退化超过 10%；原因已缩小到请求等待、订阅及调度路径，尚未完成修复。本批不修改正式运行时、不提交 Git。T2d 已提交至 tx `8760c99`；本轮开始六工程干净，两个 server 分别为 `3afc074`、`2fd67a6`，其余三工程 HEAD 见材料 `baseline.json`。

## 口径与可复现环境

材料目录：`/private/tmp/tx-nats-comparison-20260912`。`tx.tar` 固定本批已提交源码；新增 `comparison_test.go` 只编入 Unix 测试二进制（Getrusage 采样不进入其他平台），`comparison_driver_test.go` 校验成功/失败计数。`compare.py` 串行编排独立容器，`results.jsonl` 保存逐轮原始结果，`summarize.py` 重算中位数及范围。编排脚本、原始 profile 和诊断 overlay 均不进入生产路径。

- 宿主为 Intel Core i9-9880H，32 GiB，Go 1.27.0；负载二进制以 `GOOS=linux GOARCH=amd64 CGO_ENABLED=0` 编译。
- Docker Desktop 29.6.1，Linux 6.12.76-linuxkit，16 逻辑 CPU、约 7.75 GiB VM 内存。每个 Go 负载进程、NATS 和 etcd 均设置 GOMAXPROCS=4；未配置 TLS 或 CPU quota。
- NATS 镜像固定为 `nats:2.14.6-alpine` / `sha256:ad7a43eb7e3337c3c38ce5d784d1461791f95f730f252d2b25eee699752a0ca3`；etcd 为 `quay.io/coreos/etcd:v3.5.15` / `sha256:0934690612905554eb61ddefb9faaaecb47c2f6931dbb453e694358092ee8990`。SDK 为仓库锁定的 nats.go v1.53.1 和 ProtoActor `3c0e61ca19c9`。
- 全部依赖、调用端和目标端在本批私有容器中，共用同一 Linux 网络命名空间；业务连接经 loopback。远端是两个独立 Go 进程，本地是同一个 Runtime。该布局排除宿主跨 Docker 端口映射的不对称影响，**不是独立机器、生产网络或 NATS 集群容量测试**。
- 使用现行 ProtoActor `Runtime.Call`、固定 Kind 宿主及真实 etcd Provider；NATS 使用 T2d 原型 `Transport.Call`。固定路由在计时前已解析，实体先预热。未测 VirtualPID/disthash 选址、槽位冷 CAS 或 GD/Procedure/持久化。
- 两边使用同样的 Delivery/Result、共享 Echo 业务、载荷副本及响应内容校验，消息承载 128B、1KiB 或 8KiB，返回相同长度载荷。NATS 测试适配补齐接收侧 Delivery 解码及返回副本，避免用缺少业务边界的原始 pub/sub 对比正式 API。
- 邮箱容量均为 1024，发送端 pending 上限均为 4096，每个调用使用 1 秒 deadline。所有调用按执行结果计数，不把发送成功或入队当完成。不同实体按预先已知的 1～1000 路由键循环访问。
- P50/P99 为每轮成功完整 RPC 样本的 nearest-rank 分位数，再对五轮取中位数；失败分类和客户端丢弃单列。精确样本记录属于驱动成本，CPU/分配统计保留这项成本；分位数排序在内部 CPU/分配采样后进行。
- CPU 包括调用端、目标端、独立 NATS broker 和 etcd；依赖容器计数的窗口略宽于 RPC 窗口，不将其伪装成精确逐调用 CPU。Go 分配合计调用端与目标端，不包含 broker 的 Go 分配；broker 的 CPU/RSS 单独保留。RSS 为预热并显式 GC 后的驻留快照，不是峰值或单实体独占内存；已加载实体保持驻留。
- 初次烟测在读取 Docker RSS 前因 ps 参数拼接错误停止，未产生性能结论；修正参数后四组烟测通过。标签 ownership 校验限制清理范围，已有开发容器未修改。

## 结果

先扫描 3 种载荷 × 4 档并发 × 2 种实体分布 × 2 个后端，共 48 个场景，每例 1s；再选 5 个远端代表点及 2 个本地点，每个后端交替运行五轮，每例 3s。另有 30 个固定到达率样本、20 个订阅诊断样本及 2 次 8s CPU profile。四组烟测加全部采样共 174 个窗口，完整校验成功约 2147 万次 RPC，性能窗口的 RPC 返回错误为 0；客户端未投递的丢弃另列。故障探针预期失败不计入该统计。

### 当前原型与正式 ProtoActor

| 路径 / 载荷 / 并发 / 实体 | ProtoActor RPC/s | NATS RPC/s | 吞吐变化 | ProtoActor P99 μs | NATS P99 μs |
|---|---:|---:|---:|---:|---:|
| local / 128B / 1 / 1000 | 45,706 | 159,645 | +249.3% | 99.3 | 44.8 |
| local / 128B / 64 / 1000 | 257,653 | 508,993 | +97.6% | 973.1 | 1,159.5 |
| remote / 128B / 1 / 1 | 1,644 | 1,205 | -26.7% | 1,275.3 | 1,679.4 |
| remote / 128B / 64 / 1 | 58,405 | 20,580 | -64.8% | 2,651.1 | 6,665.9 |
| remote / 128B / 64 / 1000 | 52,616 | 17,955 | -65.9% | 2,988.8 | 7,751.2 |
| remote / 1024B / 64 / 1000 | 41,768 | 17,062 | -59.2% | 4,319.9 | 8,318.4 |
| remote / 8192B / 64 / 1000 | 17,729 | 9,639 | -45.6% | 9,100.1 | 14,513.6 |

这里的吞吐是固定在途并发下的闭环完成速率，不是某个生产实例的容量承诺。以 128B/64 并发/1000 实体为例，ProtoActor 五轮吞吐范围为 4.01～7.90 万次/s，NATS 为 1.68～2.51 万次/s；P99 范围分别为 1.94～4.22ms 和 5.59～8.24ms，差距没有被轮次波动覆盖。远端代表点的中位吞吐下降约 27%～66%，明显超过门槛。不能以本地直达收益抵消跨进程损失，也不能把该数字泛化成 NATS 产品能力上限。

本地 64 并发的 NATS 吞吐虽提高约 98%，P99 中位数仍上浮约 19%；闭环每轮完成量不同，不把吞吐提升理解为所有延迟指标都改善。固定 Kind 比较包含现行宿主转发层；它不能代表 Virtual Actor PID 直达路径。

### 资源与实体驻留

128B/64 并发/1000 实体的五轮中位数：

| 指标 | ProtoActor | 当前 NATS 原型 |
|---|---:|---:|
| 合计 CPU μs/完成 RPC | 87.2 | 250.1 |
| 其中 broker CPU μs/RPC | 0.03（空闲 NATS 对照） | 82.3 |
| 调用端 + 目标端分配 B/RPC | 4700 | 6362 |
| 调用端 + 目标端分配次数/RPC | 52.8 | 76.8 |
| 预热/GC 后四容器合计 RSS MiB | 162.4 | 131.7 |
| 目标 Go HeapAlloc MiB | 48.2 | 28.5 |
| 目标 goroutine | 34 | 1006 |

两侧都保留相同私有 etcd/NATS 依赖容器，未使用的依赖仅作为空闲对照，原始 CPU 可拆分。NATS 的 broker CPU 是新增通信成本的一部分，不隐藏在目标服务之外。目标堆较小是原型的实测收益；1000 个实体 worker 也是必须承担的成本。重复远端采样前后，ProtoActor 目标为 34→34，NATS 为 7→7 或 1006→1006、调用端 6→6，未观察到持续增加；这不替代大量实体和计时器长期试验。

### 固定到达率补测

128B、64 个调用 worker、1000 实体，客户端有界等待队列为 64。按预定时间生成到达，过载时记录未投递丢弃，不等上一请求完成才安排下一次。每组五轮、3s：

| 到达率 /s | 后端 | 完成 RPC/s | 单次 RPC P99 μs | 从计划到达起 P99 μs | 客户端丢弃率 |
|---:|---|---:|---:|---:|---:|
| 2000 | proto | 2,000 | 1,517.3 | 3,085.1 | 0.00% |
| 2000 | nats | 2,000 | 3,321.3 | 4,285.5 | 0.00% |
| 10000 | proto | 9,974 | 2,019.1 | 2,608.9 | 0.24% |
| 10000 | nats | 9,955 | 4,178.2 | 5,312.3 | 0.41% |
| 30000 | proto | 29,724 | 2,358.8 | 3,006.2 | 0.88% |
| 30000 | nats | 20,107 | 6,623.1 | 10,223.1 | 32.87% |

“从计划到达起 P99”包含生成器晚点、客户端排队和 RPC；单次 RPC P99 从 worker 开始调用时计算。当前驱动不能进一步拆分生成器晚点与排队，不能把这项 P99 当纯服务延迟。Go 定时器和 VM 调度会形成短时批量到达，所以即使未到后端极限也可能有客户端丢弃；表中丢弃不是 MQ 丢失或服务端已接受任务被丢弃。两侧使用同一生成方式，NATS 原型在 3 万次/s 下明显更早触发等待边界。

### 定位与未采用的诊断候选

SDK 源码显示：`UseOldRequestStyle` 每条请求执行订阅、AutoUnsubscribe、发布及取消订阅；这是 T2a 为绕过共享响应表发布失败泄漏而选用的原生路径。仅在临时 Go overlay 二进制中移除这一选项，其他原型与驱动源码不变，五轮交替对照：

| 128B / 1000 实体 | 当前独立订阅 | 共享响应表诊断版 |
|---|---:|---:|
| 并发 1：RPC/s | 1037 | 1191 |
| 并发 64：RPC/s | 18385 | 27774 |
| 并发 64：P99 μs | 7483 | 4843 |
| 并发 64：合计 CPU μs/RPC | 247.1 | 166.9 |
| 并发 64：两业务端分配次数/RPC | 76.8 | 68.8 |

64 并发吞吐提高约 51%，确认订阅/请求资源维护是成本来源之一。但该诊断组与主对照不处于同一批采样，不能拼接百分比宣称已经追平 ProtoActor，更不能由此判断剩余差距全部来自代理转发。

本轮在固定 SDK 和独立 NATS 重新执行 16 次超过 MaxPayload 的发布失败：共享响应表残留 16 项，独立订阅残留 0 项。`sdk-probe.log` 保存实际输出；这是连接存活期间的等待项残留，关闭连接会清理，并非服务端持久消息。诊断版因此**未写入仓库、未采用**，不以性能为由接受无界残留。

`current.pprof` / `shared-diagnostic.pprof` 为调用端 8s CPU profile。当前版平坦样本中 `runtime.futex` 占 21.64%，Linux syscall 占 17.49%；`requestFuture` goroutine 累计约 23.60%，其中 SDK Request 累计约 19.12%，另有 flusher、分配和编码成本。共享表版仍有系统调用、调度和分配热点。累计栈相互重叠，不能把这些比例相加；profile 也不能独自证明应删除哪个 Future 语义。下一项应先收敛请求等待路径和失败清理，再按相同矩阵复测，而不是直接增加连接池、批量协议或更换整个 Actor 模型。


## 职责与可删除范围

| 现行职责 | 采用 NATS 后的去向 | 当前结论 |
|---|---|---|
| Call/Tell/Future 的业务完成、错误与取消等待 | 新 Transport + 本地 Runtime | 四种必要语义保留；Future 取消不能撤销业务，不因吞吐目标删除这项契约 |
| Kind、邮箱、激活、生命周期、排水 | 本地 Runtime/Behavior 与宿主收尾 | 仍需维护；NATS 不代替实体状态、加载准入和邮箱顺序 |
| ProtoActor Remote、ActorSystem、官方 etcd Provider | NATS 连接、实例入口及通用发现装配 | 只有正式替换后才能删除，不能把新原型直接计成已减少代码 |
| 虚拟实体放置、固定 Kind 路由 | 稳定逻辑分区、SlotStore/Directory、加载前归属校验 | 冷加载、Watch/租约、两个示例接线仍需实现/验收 |
| 业务 Messenger 与高级扩展入口 | 稳定实体路由键及必要 SPI | 常规 API 隐藏连接与装配；ActorSystem 高级使用场景需逐一映射，不机械删除单实现接口 |
| 普通框架 gRPC、Session/MsgQ 的 Seq/Ack | 现行 modules/rpc、agent、msgq | 本批无替换收益；JetStream 与 etcd 替代仍是独立决策 |

当前 `modules/actor` 非测试、非生成源码为 10 文件 1955 行，原型为 5 文件 1162 行。两者契约与接线完整度不同，不能用差值声称可净删 793 行。tx 中 ProtoActor 的生产引用还涉及 `internal/framework/context_access.go`、`modules/agent/actor_dispatcher.go`；两个独立示例的 Actor 业务和生成入口也需适配。高级 SPI、关键可靠性测试与业务持久化职责不属于可无条件删除项。
