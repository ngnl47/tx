# MsgQ Rec 长流隔离对照

## 范围

在 `modules/msgq/rec_transport_benchmark_test.go` 中注册仅供基准使用的 gRPC 双向流，复用现有 `RecRequest`、`RecResponse` 与 `mailboxService.Rec`。每条请求仍须收到 MsgQ 回执后才继续，`Rec` 仍先于业务分派；没有修改生产 proto、Seq/Ack 契约、Agent 或 MsgQ 服务入口。基准使用同一内存邮箱、复用的 gRPC 连接与 `127.0.0.1` TCP 回环，初始化不计时。

## 本机结果

2026-09-24 在 Intel i9-9880H、darwin/amd64、Go 1.27.0 下执行 `go test ./modules/msgq -run '^$' -bench '^BenchmarkRecTransport$' -benchmem -count=5`，五轮中位数：

| Rec 路径 | ns/op | B/op | allocs/op |
| --- | ---: | ---: | ---: |
| 进程内调用 | 478.0 | 127 | 2 |
| 复用连接 Unary gRPC | 113,397 | 9,842 | 156 |
| 单条请求/回执的常驻 gRPC 流 | 67,290 | 1,425 | 44 |

相对 Unary，常驻流的单次耗时低约 41%，分配字节低约 86%，分配次数低约 72%；但相对本地调用仍有约 67 µs 的回环往返。这里没有批处理，也没有放宽逐条确认。该基准仅有一个顺序会话，不能外推 10,000 会话吞吐、并发 P99 或四机链路收益。

随后用 16 个并发通道承载 1024 个会话；每个通道顺序处理自己的 64 个会话，Unary 组仍共享一条 `ClientConn`，长流组每通道持有一条流。会话初始化和建流均不计入计时。两次 `-benchtime=2s -count=3` 的各轮中位数范围：

| Rec 路径 | ns/op（16 通道合计） | B/op | allocs/op |
| --- | ---: | ---: | ---: |
| 复用连接 Unary gRPC | 18,309～19,648 | 9,369～9,374 | 140 |
| 16 条常驻 gRPC 流 | 7,392～8,171 | 1,121～1,126 | 30 |

按本机完成速率折算约为 5.1～5.5 万与 12.2～13.5 万次 `Rec`/秒；长流快约 2.4～2.5 倍，单次分配低约 79%。`ns/op` 是 16 通道的汇总吞吐指标，不是单请求延迟。这个隔离负载没有 Agent、Game、下行或网络跨机竞争，也没有会话热点和流重建；不能当作正式集群的容量结论。

## 生产接线前的边界

当前 `SessionClientRouter` 按目标 MsgQ 实例复用连接，多个 Agent Session 并发使用。若共用一条试验流并逐条等待回复，所有 Session 会被串行化；16 通道基准说明有限并发流值得试验，但没有证明其生产容量。最小接线可按 SessionID 固定选择通道，每条流只保留一个待回执请求；此时不需要请求 ID。单条 `Rec` 错误会终止所在流，后续请求须新建流，其他通道不受影响。增加并发流可能重新带来 CPU 和内存成本。

若生产流在发送后断开，本次 `Rec` 的提交结果未知；客户端适配不得自动转 Unary 或在新流上盲重投同一请求，而应让当前 Agent 会话失败，由原 Session 的恢复 `Init` 读取 MsgQ 游标。会话 Context 取消必须能终止占用中的流，不能让同一通道的其他 Session 无限等待；这条取消与流池关闭边界尚未在生产会话客户端接线验证。若将来允许一条流同时挂起多个请求，就必须重新设计请求关联与失败分发。

因此本轮只确认“长流值得继续对照”，不替换生产 Unary `Rec`，也不把它当作会话租约或上行可靠性修复。相关会话语义见 [租约证明](2026-09-24-session-lease-proof.md)，同进程链路对照见 [Rec 装配对照](2026-09-24-rec-colocate.md)。

## 有限通道流池原型

后续在 `_test.go` 增加仅供隔离验证的流池：同一目标 MsgQ 的 SessionID 固定映射到有限通道，每个通道持锁完成一次 `Send`/`Recv` 后才接下一条。当前请求 Context 取消会取消该通道的流并丢弃它；下一次请求才新建流，不自动重投结果不明的旧请求。关闭流池会取消所有通道。若取消回调已开始，即使当前请求收到回复也丢弃该流，避免回调迟到时取消下一条请求。

用例验证了：同通道的一个跳号请求失败后，另一个 Session 可以经新流继续；一个通道在服务端已接受消息后等待回执时，另一通道仍可处理请求；取消等待者会释放该通道，后续 Session 可重建流，恢复 `Init` 仍读到原请求的已接受序号；关闭流池可解除等待。新增用例的定向 `-race` 和 `go test ./modules/msgq -count=1` 均通过。

将流池加入 1024 会话、16 并发通道的同机基准；三轮 `-benchtime=2s -count=3` 中位数如下。该轮所有请求均使用可取消 Context，流池包含通道锁及每条请求的取消监听：

| 路径 | ns/op（16 通道合计） | B/op | allocs/op |
| --- | ---: | ---: | ---: |
| 复用连接 Unary | 18,700 | 9,368 | 140 |
| 原始长流 | 7,838 | 1,127 | 30 |
| 受控流池长流 | 8,968 | 1,261 | 32 |

折算本机完成速率约为 5.3 万、12.8 万、11.2 万次 `Rec`/秒。受控流池相对 Unary 约 2.1 倍，相对原始长流慢约 14%；原始组的每个工作协程独占一条流，流池组按 SessionID 在 16 条流之间交错，差额包含锁竞争与取消监听，不能单独归因。测试未覆盖网络断连、流重建的高频成本、同一通道热点、真实 Agent/Game/下行竞争及完整链路 P99；也未证明任意一个未取消的慢请求不会阻塞该通道的其他 Session。下一项是在正式会话客户端中做受控接线及同版链路 A/B，先验收取消、错误与 P99，再决定是否默认使用长流；本轮生产路径未变。
