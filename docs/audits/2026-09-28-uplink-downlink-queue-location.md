# 20/50 链路排队位置复核

本轮只加抽样阶段探针，不调整消息语义或发送策略。六台云实例运行两台 P8 Agent、两台 P4 Game 进程、两台 P4 MsgQ 进程，以及两台客户端发生器。两个客户端各建立 5000 个 TCP 会话；每会话计划上行 20 次/s、平均下行 50 次/s，测量窗口 60 秒。负载仍是 `System_Ping`，Game 在生成 `Pong.ServerTime` 前先发布额外下行，因此该时间戳不是 Handler 刚开始执行的时间。

探针每 64 条抽样一条，Prometheus 直方图在窗口前后取差。表中的 P99 是**桶上界**，不代表精确分位数，也不能将不同阶段的 P99 相加。客户端阶段样本使用跨机器 Unix 毫秒墙钟；负 1ms 样本未取零，阶段分位数仅取非负样本。该精度足以区分数十毫秒量级的趋势，不足以证明亚毫秒先后关系。

Game 的 `tx_rpc_stream_submit_seconds` 是投递邮箱操作本身，两轮 P99 桶上界均为 0.025ms；这与 Actor 入队后等待执行是不同边界。Agent 的 `tx_agent_uplink_dispatch_seconds` 包含发送锁等待，P99 桶上界为 20–40ms，不能再与发送锁 P99 相加。Game→MsgQ 发布队列指标从发布入口计时，包含生产者等待与本地队列等待，并非仅 channel 内驻留时间。

客户端抽样显示，第一轮 `Pong.ServerTime` 前后两段的 P99 分别为 A 68/70ms、B 66/60ms，最慢 1% 样本以时间戳前段占优；第二轮分别为 A 45/68ms、B 43/63ms，最慢 1% 样本约 75%–76% 以后段占优。客户端计划发起延迟 P99 在四组中为 50–57ms；Node 事件循环延迟 P99 在各 worker 间约 35–50ms。后段与计划发起延迟按秒聚合后同向变化明显，但这只是相关性，不能认定客户端事件循环是唯一原因。客户端单机 TCP 接收队列和 Agent TCP 发送队列出现短时字节积压，但其采样不能直接换算每条请求的排队时长。

## 判断和接续

Agent→Game 的**共享流发送锁**是目前最清楚且可重复测到的上行排队点；底层 `Send` 本身很快。Game Actor 邮箱和 Game→MsgQ 本地发布队列也有毫秒级等待。MsgQ→Agent 共享流及 Agent 会话队列的 P99 桶上界较低，不能解释单独出现的 80–118ms 整链路 P99。两轮最慢样本分别偏向 `Pong.ServerTime` 前、后，尚无证据把整条长尾固定归因于一个服务端队列。客户端发生器计划和事件循环本身有几十毫秒长尾，是下一次归因必须隔离的变量。

此前同拓扑的「只合并已排队消息」试验虽然降低 Agent CPU，却提高了端到端 P99 且略降完成率，因此本轮不重新引入该队列。下一次应先用同一窗口的请求级阶段时间戳或可关联的低比例 trace，将 Agent 读取→发送锁→Game 入邮箱→Game 出邮箱→发布→MsgQ 送出→Agent 收到→客户端解码串起来；同时单独记录客户端事件循环延迟。不要根据直方图分位数之和做架构优化，也不要继续试固定合批阈值。

第三次复测未进入有效负载：第一次因就绪后未及时触发导致客户端等待 `start` 超时；重启后在建立连接阶段等待 `System_Pong` 超时。两次 `attempted`/`completed` 均为 0，已从性能结论中排除。集群业务服务按 Agent/Login → Game → MsgQ 顺序停止，压测角色夹具已清理；中间件容器未改动。

原始客户端结果及 Prometheus 前后快照位于工作区 `tx-artifacts/cloud-20260928-dual-client/mailbox-queue-20260928/` 和 `tx-artifacts/cloud-20260928-dual-client/actor-publish-20260928/`。探针二进制是在同一工作区先后编译的 Linux `amd64` 产物，第二轮 Game 二进制增加 Actor/发布队列探针；MsgQ、Agent 使用第一轮探针二进制。二者均开启 `txbench`，部署后核对过二进制架构和 SHA-256。
