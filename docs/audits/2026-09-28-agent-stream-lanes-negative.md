# Agent 直连流分道试验：局部等待下降，端到端未获益

## 问题与条件

六机部署下，双客户端各发起 5,000 个 TCP 会话，双 Agent 各承接 5,000 个会话；万连 20 次/s 上行、平均 50 次/s 下行时，Agent 的上行分派和客户端调度均出现长尾。为区分本地发送锁与完整链路容量，先在原构建上采集短时锁画像，再只替换两个 Agent 的构建做 A/B。每轮正式负载 60 秒，客户端各 8 个 worker，Game、MsgQ、Login 构建及实例数量保持不变。pprof 轮仅用于定位，不参与无画像 A/B 容量比较。

旧实现对每个目标服务实例复用一条 Actor `CallStream`，并用一把发送锁保护该流。10 秒 Agent B 画像中，`grpcConnection.SendStream` 的发送锁占互斥等待**采样量**约 98.3%；阻塞画像也集中在此锁。采样量会叠加多个 goroutine 的等待时间，不能解释为 CPU 占比或 10 秒墙钟时间。画像提示局部串行，但不证明分道能提高最终吞吐。

试验构建将 Agent→Game 的单目标发送改为固定八条单向流，同一 Actor 身份稳定落在同一条流，Game 接收循环及邮箱入队语义不变。新增测试验证同 Actor 顺序和不同 Actor 不再被同一流的接收阻塞。`tx` 全量及定向 `-race`、`txgame/server` 全量测试通过。该候选只用于云端 A/B，试验后已从工作区撤回。

| 八流候选 | 34,682 / 14,489 | 136.03 / 101.70 ms | 3.81 / 3.12 ms | 396 / 397 核秒 |

两轮均为 10,000 会话、20/50、60 秒；实际发出的请求均完成，未发送来自客户端计划时隙，不能记作服务端投递失败。分派 P99 是 Prometheus 直方图桶估算，CPU 为进程累计 CPU 差分。A/B 显示 Agent 局部等待明显缩短，但客户端未发送总数由 26,537 增至 49,171，端到端 P99 也变差；单次轮次不足以量化退化幅度，却足以否定“局部锁下降即可直接提高 20/50 完整率”的假设。本候选不进入默认实现，也不继续盲目增加流数。

另做的一轮 1/64 客户端阶段采样显示八流候选的到 Handler 前段长尾上升，但跨主机墙钟出现明显偏移：候选客户端 A 有 11,983/93,569 条采样被判为时钟无效，B 有 1,910/93,743 条。跨机时间戳不能用作精确分段因果。Game 的接收/入队直方图 P99 为亚毫秒量级；它与客户端几十毫秒差额之间仍有未定位的排队。客户端八 worker 的事件循环延迟也会随负载变化；简单改成十六 worker 的一轮没有稳定收益。

## 取舍与接续

保留原单流生产代码。下一步固定原构建与 20/50，使用同进程单调时钟分别量化 Agent 写入流之前的等待、Game 从流读取到邮箱入队的等待、以及客户端生成计划时隙到实际写 socket 的等待；每项用计数和分布记录，避免跨主机墙钟相减。先找实际积压位置，再决定是调整传输还是发生器，不重复搜索固定分道数或 worker 数。相关客户端、Agent、Game 与 MsgQ 原始归档在 [`cloud-20260928-dual-client`](/Users/a47/workspace/tx-artifacts/cloud-20260928-dual-client/)；Agent B 的阻塞/互斥画像也在该目录。测试后八个业务服务均停止，压测夹具已清理，中间件仍运行。
