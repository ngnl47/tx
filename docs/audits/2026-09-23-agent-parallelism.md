# Agent 并行度对照与建连故障诊断

接续[四机压测](2026-09-23-four-host-uplink.md)。本轮只验证20000次/s下Agent并行度对延迟的影响，不修改默认部署参数，不执行Git commit。

## 改动与边界

原始347条断连尚未确定根因。为下一次复现保留有效信息，`msgq.maintainRoles`的错误补充RoleID，续期拒绝分别标识本地租期过期、存储代际不匹配、在途续期被替换及续期耗尽租期。仍使用`%w`保留`ErrSessionChanged`判定，不改变续期、驱逐、重投或确认行为。

原来的TCP i/o timeout可能来自Agent会话取消后对ReadDeadline的唤醒，不能直接解释为网络根因。准备保活跳过非connected端点，导致部分断连延迟到预热才暴露，这项压测准备阶段的失败检测仍待完善，不通过自动重连掩盖故障。

为加速观察曾使用400会话、20秒租期的诊断配置，不能计入容量结果：

- 第一次重启未重建隔离槽位，Agent报告`slot runtime is unavailable`；已在全停状态prepare后重建。这是本次编排前置条件错误，不是原始故障。
- 重建后的短租期轮出现约20秒时`session has changed`及Pong超时，但没有新增角色续期分阶段错误。20秒租期与10秒保活及半租期续期间隔过近，存在边界风险，尚不能证明与原10分钟租期故障同源。恢复原配置，不据此修改生产契约。
- Redis报告evicted_keys=0，无内存淘汰证据。

## 对照方法

与上一轮相同四台8vCPU/16GiB主机、正式Ping/Pong和两客户端进程。10000会话、50/s建连、每会话2/s、预热2秒、正式30秒、5秒单次等待、10分钟租期。MsgQ、Game和Login保持GOMAXPROCS=2，只有两个Agent从2改为4。

两组均使用同一诊断二进制，SHA-256=`afddbf77d5e97994dddfc9a2eb5742e7d0f0aab4c685be037881c84ecf544e69`。每组全停后重建专用测试夹具；组内两轮不清库、不重启，等待旧角色归属自然释放。P4-a漏发1次后停止自动晋级，检查诊断后保持参数不变进行P4-b同档复测；没有放宽窗口或验收门槛。
