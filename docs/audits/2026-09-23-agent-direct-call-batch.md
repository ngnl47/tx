# Agent→Actor 直连 Call 短窗口合批

日期：2026-09-23。接续[预评估](2026-09-23-agent-call-batching-probe.md)。本轮只合并 Agent 到目标 Actor 宿主实例的直连 gRPC `Call`；MsgQ `Rec`、Seq/Ack、Actor 邮箱与业务处理不变。默认关闭，示例可用 `runtime.actor.directCallBatch: true` 做部署期 A/B。

## 实现与边界

- 同一 Agent 进程按目标实例分桶，从第一条到达后 1ms、达到 100 条或累计约 2 MiB 时先满足者发送，避免大载荷批次超过 gRPC 单消息限制。每项保留 Actor Kind/Key、原业务信封和相对批次截止时间；不同目标实例不合并。
- 接收端仍逐项调用原 Actor 宿主，结果按完成顺序流式返回，并以批内索引交给原调用方。一条慢 Actor 请求不等待在其他已完成项之前；业务错误只作用于该项。流中断时已返回项保持原结果，未返回项失败，不能伪装为成功。
- 批内较早超时的项在宿主入队前检查自己的期限。调用方取消后的业务是否已经执行，仍遵循原 RPC 的结果未知语义；不自动重投。批次不是 JetStream 可靠任务，也不改变排水保证。
- 新协议复用现有服务发现、gRPC Host、Sender 连接和本地 Actor 邮箱；未增加第二套选址或压测专用业务。接收端始终支持批量入口，发送端仅在开关开启时使用。

例如，同一毫秒里发往 Game A 的 20 个不同 Role Actor 的上行命令仍各自完成 `MsgQ.Rec`，然后共用一次 `CallBatch`；一条返回 `ErrActivationDenied` 时，其他 19 条按自己的执行结果完成。发往 Game B 的命令进入另一个桶。

## 本地验证

`tx` 全量 `go test ./...`、`txgame/server` 全量 `go test ./...` 通过；`TestDirectSharedHostKinds` 在 `-race -count=3` 下通过。定向测试覆盖跨 Kind 同批、逐项拒绝、错误归属分类、慢项不阻塞快项、100 条立即刷新、2 MiB 分批、逐项期限及流中断后的部分完成。首次全量测试发现 Bee/Ant 的 `ActorConfig` 字段对称契约缺口，补齐 Ant 映射后通过。

在 Intel i9-9880H Mac、Darwin/amd64、`GOMAXPROCS=4` 上，对复用的 loopback gRPC 与真实本地 Actor 宿主运行三轮 `BenchmarkDirectCallTransport`。P16/P64 为 Go `SetParallelism` 系数，分别约对应 64/256 个并行基准 worker；`ns/op` 是吞吐摊算值，不是端到端延迟。

| 档位 | 单条中位 ns/op | 合批中位 ns/op | 合批项/次 RPC | 单条→合批 B/op | 单条→合批 alloc/op |
| --- | ---: | ---: | ---: | ---: | ---: |
| P16 | 22,493 | 25,718 | 约 63 | 15,469→4,604 | 196→53 |
| P64 | 17,752 | 6,927 | 约 93 | 15,294→4,669 | 196→52 |

低并发档因窗口等待和协议开销约慢 14%，高并发档吞吐摊算约快 2.56 倍；这支持保留默认关闭与真实链路 A/B。

## 四机同版短轮

四台 SA9 8vCPU/16GiB 主机分别承载 Login/Agent、MsgQ/依赖、Game 和双进程客户端。三个服务机使用相同 SHA-256 为 `acc0c1fa184c79de408cfdb9219ea122e68f589c7f6510ff67a07a74816549d8` 的实验二进制，只有两台 Agent 的开关在 A/B 间变化。客户端为 10,000 个 TCP 会话，每档约 500/s 配置建链，Ping/Pong 维持 1:1 上下行，正式窗口约 30 秒。

首次新二进制基线在准备阶段失败：重启 Game 后，专用 etcd 槽位仍指向已退出的旧实例 ID，Agent 报 `discovery: slot runtime is unavailable`。确认旧租约不存在后，在八个测试服务均停止时调用现有带 ownership 检查的 `cluster-fixture cleanup/prepare`，重新准备 10,000 角色，随后同版基线通过。该失败与合批关闭状态同时发生，不能归因于批量协议；它提示下次全量重启必须先处理测试槽位归属。

原始客户端报告、建链速率、`pidstat`、`vmstat` 和可取得的服务日志位于 `tx-artifacts/cloud-20260923-followup/batch-off2-20260923-3.75/`、`batch-on-20260923-3.75/` 及 `batch-on-boundary-20260923-{4,4.5,5}/`。失败的首次准备轮保留在 `batch-off-20260923-3.75/`。一次关闭基线的末尾服务日志采集因公网 SSH 超时而不完整，客户端报告与资源采样已保存；不把这次采集异常解释为业务失败。四机所测二进制构建于增加 2 MiB 字节上限及错误归属分类修正之前；这两个边界不触发本轮正常小载荷 Ping/Pong，新增定向测试在本地验证，最终代码仍需同版云端回测。

## 2026-09-24 最终构建复测

三台服务机均部署同一 SHA-256 `6848469d76b7cb2d14ee7b6478c08a1743cac231f9e09cf1653f2dcf9e9671fb` 的最终二进制，包含 2 MiB 批次上限和 `ErrNotOwner` 分类修正。全部测试服务停止后，以现有 ownership 检查夹具清理并重建专用槽位及 10,000 个角色。四台 SA9 8vCPU/16GiB 机器分别承载 Login/Agent、MsgQ/依赖、Game、双进程客户端；两台 Agent 各设 `GOMAXPROCS=4`。每轮均重新建立 10,000 个 TCP 会话，目标建链 500/s，Ping/Pong 维持 1:1 上下行。A/B 只切换两台 Agent 的 `directCallBatch`，不改变二进制、MsgQ `Rec`、Seq/Ack 或业务代码。

3.75/s 同版短轮开启后，P99 降约 39%，两 Agent 的 CPU 降约 22%。CPU 取正式窗口 `pidstat` 中两个 Agent 进程的 30 秒峰值均值；长轮 CPU 取 00:36–00:44:30 的 511 个采样均值。4.5/s 长轮平均完成约 44,985 次/s，实测建链约 438/s；十个完整分钟各完成约 269.8–270.1 万次，按每 64 次抽一条的分段耗时样本估算，分钟 P99 为 57–71ms，这不是全量客户端 P99。接入机 `vmstat` 同区间平均 idle 31.8%、iowait/steal 均为 0，两个 Agent 平均 RSS 各约 217–218 MiB。MsgQ 宿主平均 idle 60.4%，Game 宿主 70.6%，客户端宿主 71.5%。长轮结束及低负载 A/B 后，专用 DB12 的角色归属键均释放；客户端报告、建链速率和资源采样在 `tx-artifacts/cloud-20260923-followup/batch-final-{off,on}-20260924-3.75/`、`batch-final-on-long-20260924-4.5/`、`batch-final-low-{off,on}-20260924-1/`。

低负载 1/s 时，开启合批使 P50 增约 1.40ms、P99 增约 1.59ms，符合等待窗口会抬高稀疏调用延迟的预期。因此保留生产默认关闭，仅在目标服务的高密度 Agent→Actor `Call` 场景按部署配置启用；不能由高负载收益推出全局默认开启。4.5/s 长轮通过既定零失败、零漏发和 P99≤100ms 门槛，但本轮未对最终构建测 5/s 稳态，也未验证 20 上行/50 下行的不对称 MMO 目标。

本轮本地重新运行 `tx` 与 `txgame/server` 全量测试、合批关键路径 `-race -count=3`。`tx` 首次授权全量测试中，既有 `TestSessionClientRouterConcurrentFreshSessionsShareRoleOwner` 偶发出现同一 owner 被拨号两次；该用例单独重复 20 次及随后全量重跑均通过。默认沙箱的首次测试还因 Go 缓存和 loopback 端口权限失败，这不是代码结果。未因非确定性现象修改与合批无关的角色路由实现，后续需单独复核该用例的单连接断言。云端两台 Agent 已恢复默认关闭并重启，八个服务实例仍运行最终二进制且保留旧二进制备份；本轮未提交 Git。
