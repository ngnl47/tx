# RecStream 64/256 路与客户端供给对照

## 目的与测量边界

复核 64 路 `RecStream` 的分桶等待是否限制万连 10/s 平衡链路吞吐。四机部署保持 Login×2 P4、Agent×1 P8、MsgQ×2 P4、Game×2 P4；客户端在独立 8 核主机运行八个 Node worker。每轮 10,000 TCP Session、每 Session 上行与下行各 10/s、每条 Ping 对应一个 Pong、每 Session 最多四条在途、正式窗口三分钟。两轮不并行，服务端不启用 pprof；旁路采集 pidstat/vmstat，客户端保留现有调度与事件循环诊断。

64 路 Agent 基线二进制 SHA-256 为 `f53ced59b50d5dee7fe6a19e9140a5408a8e6dc5b79548a57830785c8ff70af5`，256 路候选为 `2fc2de8307872a52e581a7badd46e75dc968384015f6d91dcd387fa6eb4a90bc`。两份源码构建只改变 `recStreamLaneCount`。测试后已恢复 64 路二进制并确认 Agent 服务 active；当前源码也恢复为 64 路。

## 完整链路结果

| Agent RecStream 分道 | 完成/计划 | 上下行各自完成吞吐 | 未发送 | 业务失败 | P50/P95/P99/max |
| ---: | ---: | ---: | ---: | ---: | --- |
| 64 | 17,787,430/18,000,000 | 98,819/s | 212,570 | 0 | 96.52/395.91/483.02/903.19 ms |
| 256 | 17,607,313/18,000,000 | 97,818/s | 392,687 | 0 | 102.29/448.36/531.14/1,112.56 ms |

两轮都没有达到零未发送，不能认定万连 10/s 通过。单轮对照没有显示 256 路收益；它的完成吞吐低约 1%，P99 高约 48 ms，Agent 平均 CPU 也从约 6.59 核升至 6.81 核。测试只做一轮每档，差异不能解释为确定的退化，但足以否决继续增加分道数作为当前优化方向。保留已验证的 64 路实现，不保留 256 路改动。

## Rec 等待与事件循环诊断

64 路画像的 block profile 中，`recStreamPool.Rec` 在 `lane.ready` 上等待累计约 132.85 小时，在流 `Recv` 上等待约 1.74 小时。此数是并发 goroutine 等待时间的总和，不是 CPU 时间，也不是一次请求的等待时长。阶段计时轮中 `Rec` 的 P50/P95/P99 为 56.77/118.83/134.35 ms；路由解析 P99 约 0.007 ms。画像证明分道有竞争，但把分道数从 64 提至 256 后，完整链路没有改善，因此分道等待不是这一档总吞吐的唯一限制。

同一客户端正式窗口的客户端诊断还显示负载发生器接近饱和：

| 分道数 | 八 worker 平均事件循环利用率 | worker 中最高事件循环 P99 停顿 | 总容量等待次数/累计时间 | 跳过计划槽位 |
| ---: | ---: | ---: | ---: | ---: |
| 64 | 89.18% | 110.62 ms | 1,071,532 次/81.53 s | 211,199 |
| 256 | 91.04% | 110.49 ms | 2,067,020 次/175.02 s | 391,495 |

这些容量等待是八个 worker 的累计数，不能当成单一墙钟等待时间。它们说明 `notSent` 同时受到响应未及时完成和客户端固定时间轴供给的影响；客户端 P99 不能单独作为服务端 RTT。

客户端每 64 个请求抽取一次 Game `serverTime` 样本，所有有效样本均未出现负时钟差。样本显示：

| 分道数 | Handler 前样本 P50/P95/P99 | Handler 后样本 P50/P95/P99 | 样本数 |
| ---: | --- | --- | ---: |
| 64 | 67/365/446 ms | 18/96/179 ms | 277,932 |
| 256 | 65/417/492 ms | 20/102/197 ms | 275,118 |

Handler 前包括客户端调度与发送、Agent→MsgQ `Rec`、Agent→Game Actor 调用；Handler 后包括 Game 发布、MsgQ 下行、Agent 写帧及客户端回调。它们是不同抽样集的分位数，不能相加为端到端 P99；跨宿主机时钟也限制了精确归因。数据进一步显示 256 路没有改善前段或后段。

正式窗口内 pidstat 进程平均 CPU：

| 分道数 | Agent | Game 每进程 | MsgQ 每进程 |
| ---: | ---: | ---: | ---: |
| 64 | 658.7% | 240.3% / 239.6% | 182.6% / 182.1% |
| 256 | 681.2% | 233.0% / 232.0% | 175.3% / 175.6% |

这次没有单独采集网卡 PPS、TCP 重传、软中断或宿主机总 CPU 的正式时间窗统计，不能仅凭当前数据把剩余时延归因于网络、Agent 或 Game。

## 8/16 个负载进程对照

为判断单个 Node 事件循环是否限制请求供给，固定服务端与 64 路 Agent 二进制、万连×10/s、1:1、三分钟和每 Session 四条在途，将负载进程从 8 个提高到 16 个。16-worker 轮完成 17,455,446/18,000,000，吞吐 96,975/s，P99 562.27ms，未发送 544,554，业务失败为 0。对照的 8-worker 64 路轮为 17,787,430 条、98,819/s、P99 483.02ms、未发送 212,570。

16 个 worker 的平均事件循环利用率降至 70.05%（8 个时 89.18%），每个 worker 的事件循环 P99 停顿中位数从 101.1ms 降至 65.0ms；但最大事件循环停顿仍为 535.3ms，且完成吞吐略低、端到端 P99 较高。`maxInFlight=4` 达到上限后的累计跳过槽位从 62,211 增至 485,034。利用率下降不等于 CPU 节省或服务器变快；它与大量在途容量等待共同说明，16 进程降低了单循环负担，却没有提高响应链完成速度。每档仍只有一轮，且 16-worker 轮未同步采集服务端 pidstat，不能据此断言某个服务实例是唯一瓶颈。

该轮客户端汇总和 16 个 worker 的诊断归档见工程外 `tx-artifacts/cloud-20260925-four-host/lane256-ab-worker16-20260925.tar.gz`；SHA-256 见同级 `SHA256SUMS`。

随后用同一服务版本和负载配置各复跑一轮 8/16 worker，并同窗采集服务进程 CPU、`sar` 网卡/TCP 与 `nstat` 计数。两轮完成吞吐分别为 98,280/s、98,211/s，P99 为 502ms、530ms，未发送分别为 309,686、322,090，业务失败均为 0；确认 8→16 worker 没有可测的闭环吞吐提升。16-worker Agent 平均 CPU 约 5.80 核，8-worker 约 5.76 核；Game 与 MsgQ 进程在两轮均未打满。Agent `eth0` 平均包率约为 8-worker Rx/Tx 239k/242k、16-worker 219k/236k 包/秒；两轮设备错误和丢包计数均为 0。

Agent `TcpRetransSegs`/`TcpExtTCPLossProbes` 计数较高（两档约 5.6k/s 与 5.4k/s），但 Linux 将 `TcpExtTCPLossProbes` 定义为 TCP 尾部丢失探测包的发送数；对应的 `TcpExtTCPLossProbeRecovery` 两档各增加 2，`TcpExtTCPFastRetrans` 分别增加 1/0，`TcpExtTCPTimeouts` 分别增加 0/6。故这些探测数不能解释成同等数量的数据包丢失；当前采样也没有显示 NIC drop/error。它可能反映大量有未确认尾包的短突发连接，但 8→16 worker 后计数下降且 P99 稍升、吞吐不变，仍不足以解释主要长尾。下一步需取得 Agent TCP 连接的 RTT、未确认队列与重传状态分布，并和 Agent 阶段计时同窗对照；不把全机探测计数当成链路丢包结论。[Linux 内核文档](https://www.kernel.org/doc/html/v6.5/networking/snmp_counter.html)将 `TCPLossProbes` 与 `TCPLossProbeRecovery` 分开定义。

8/16 worker 两轮完整客户端和服务端旁路归档分别为工程外 `tx-artifacts/cloud-20260925-four-host/lane256-ab-net-8-*.tar.gz` 与 `lane256-ab-net-16-*.tar.gz`；SHA-256 见同级 `SHA256SUMS`。nstat 起止快照覆盖采样启动到收尾的较宽时间段，sar/pidstat 记录固定 210 秒，均略宽于正式 180 秒窗口。

## Agent CPU 路径复核

已有 64 路 Agent CPU profile 的 15 秒样本共 108.44 秒 CPU。平坦样本中 Linux `Syscall6` 占 20.85%；累计栈中 Agent TCP `writeBuffersFull` 占 17.75%、MsgQ `RecStream.Rec` 占 15.37%、Agent 上行分发占 30.10%。`tcpTransport.Write` 每个下行帧都会调用 `net.Buffers.WriteTo`，`tcpTransport.Read` 每个上行帧都解码一帧；这说明每条消息对应的 socket/协议处理成本值得继续量化。profile 的累计栈相互重叠，`Syscall6` 也不只代表一个网络方向；不能把这些百分比相加成独立成本。当前没有证据支持为单帧写再加微批缓冲：一个帧已经通过 `writev` 风格的 `net.Buffers` 合并写入，额外等待窗口可能增加延迟，且稳态单 Session 消息较稀疏。

## 结论与下一项

保留 64 路 RecStream；不继续按 lane 数或客户端进程数盲目扩张，也不把租约候选的 CPU 节省推导成整体吞吐收益。8/16 worker 同窗对照显示 Agent 接近 5.8 核、包率高，Game/MsgQ 尚有余量；分片数变化没有提升闭环吞吐。TCP 尾部探测计数不能直接视为丢包，且网卡计数未见错误/丢弃。下一项用低扰动 `ss -ti`/TCP_INFO 采样抽取 Agent 客户端连接和内部 RPC 连接的 RTT、未确认字节与重传状态，并对照 Agent `Rec`、Actor Call、下行写阶段；先判定长尾是否来自 socket 发送排队或用户态调度，再决定改动。暂不引入下行微批窗口：现有单帧已经使用 vectored write，且缺少它能改善当前稳态链路的证据。

原始摘要和系统采样位于工程外 `tx-artifacts/cloud-20260925-four-host/lane256-ab/`；目录打包及 SHA-256 见同级 `README.md` 与 `SHA256SUMS`。

## 同窗 TCP_INFO 与客户端阶段采样

为确认尾部探测是否对应高 TCP RTT，固定现有四机服务与 Agent 64 路二进制，再跑万连×10/s、八个客户端 worker、1:1、三分钟。客户端正式窗口完成 17,612,239/18,000,000，吞吐 97,846/s，P99 520.42ms，未发送 387,761，业务失败 0。Agent 在 19000 端口每 9 秒用 `ss -ti` 读取约 100 条间隔抽样连接；客户端保留每 64 条请求一次的 Handler 时间与事件循环诊断。

空载 TCP RTT 样本中位数约 0.07ms；压测窗口各次抽样的 RTT 中位数约 5–17ms、P95 约 15–30ms、最高样本约 38ms。抽样时 0–28/100 条连接报告有未确认段，未见活动中的重传；连接累计重传字节比例约 3%（按抽样 socket 汇总）。这确认压力下 Agent 到客户端机的 TCP 延迟确有抬升，但单次样本仍远低于约 520ms 的端到端 P99，不能单独解释长尾。该轮没有同步采集主机范围的 `nstat` 起止计数，因此 socket 累积字段不代表整机丢包率，也不能判定重传成因。

有效客户端阶段样本 275,195 条；整段样本 P50/P95/P99 为 120/446/521ms，其中发出请求到 Game Handler 记录 `serverTime` 为 82/418/480ms，Handler 时间戳到客户端回调为 18/113/204ms。该拆分中位数和 P99 与整段延迟接近，但两个子阶段的分位数不能相加。所有阶段均用客户端与 Game 主机墙钟作差；有效样本未出现负值，但跨机时钟误差仍可能影响子阶段边界。到 Handler 段包含客户端事件循环、客户端至 Agent 传输、Agent `Rec` 和 Actor `Call`，不等同于网络 RTT。

八个 Node worker 的事件循环利用率为 89.3%–90.0%，各自事件循环 P99 停顿 110.6–152.4ms、最大停顿 361–555ms；总计划漏发约 2.15%。这说明发生器同样接近饱和，客户端供给与服务端响应共同影响结果，当前三分钟负载不能只看作服务端容量测量。另一次同配置 `txbench` Agent 诊断轮中，采样 `Rec` 的 P99 为 134.35ms、Actor `Call` 为 112.14ms；两段按同一 `(roleID, seq)` 配对后的 `Rec+Call` P99 为 191.60ms。该轮开启阶段计时和画像、持续 30 秒，测量开销会扰动负载，不能与本轮拼接为逐请求因果链，但说明 Agent 上游热路径内部确有百毫秒级等待。

原始客户端 worker 延迟、调度与阶段样本及 Agent `ss -ti` 日志归档于工程外 `tx-artifacts/cloud-20260925-four-host/tcpinfo-10k-10ps-20260925/`；本轮客户端和 Agent 原始压缩包的校验和见同级 `SHA256SUMS`。一次同窗补采尝试使用旧 `server-txbench`，客户端准备阶段报告 `discovery: slot runtime is unavailable`，实际未发出 Ping；普通 Agent/Game 已恢复。随后本地构建错误地沿用了 `darwin/amd64` 默认目标，该产物不适用于云端 Linux；正确设置 `GOOS=linux GOARCH=amd64` 后已得到并通过 ELF 格式检查的诊断二进制（SHA-256 `2033c372cd6e8355df5e143194d80b6fd9461d8ec4dad9d03220675ec5974041`）。压缩后约29MiB的 SSH 上传单流一分钟多仅到约765KiB；改为四路并行分块后约25秒合计约2MiB，吞吐未改善。该交付问题已通过构建精简的诊断二进制解决，后续同窗测量已完成，详见[2026-09-26 RecStream 等待拆分报告](2026-09-26-recstream-lane-wait-isolation.md)。

## 2026-09-26 RecStream 长尾拆分

先在 10k×10/s 短测中配对 Agent 完整 `Rec` 和 MsgQ 内部 `mailbox.Rec`：23,554 个样本中，Agent `Rec` P99 为 158.193ms，MsgQ 邮箱执行 P99 为 0.007ms。随后把 Agent RecStream 细分为获取 lane 的等待与 lane 内 `Send+Recv`，相同 `(roleID, seq)` 配对 23,808 个样本；完整 `Rec` P99 147.534ms，两阶段和 P99 147.431ms，lane 等待 P99 146.194ms、流往返 P99 12.134ms。两轮是独立窗口，绝不把它们的延迟值拼接；逐阶段同轮配对只适用于第二轮。

这证明高负载下 Agent 的完整 `Rec` 等待主要发生在 64 路 lane 排队，不是 MsgQ 邮箱内处理；不过 Agent P8 本轮平均约 7.30 核，客户端八个 worker 的事件循环利用率约 92%，发生器也接近饱和。该证据定位等待位置，不代表 lane 排队是唯一的整链吞吐根因。此前无采样 64→256 lane 对照未提升完整链路吞吐，因此不再盲目扩 lane、不启用租约。新增采集仅在 `txbench` 构建有效，普通构建为无操作。详细边界和数据见[2026-09-26 RecStream 等待拆分报告](2026-09-26-recstream-lane-wait-isolation.md)，原始归档的 SHA-256 见工程外测试目录。
