# 云端登录速率与万连长窗口复测

日期：2026-09-23

## 目的与范围

验证登录建链速率目标调整为 300–500 个会话/秒后，四机当前部署能否在目标速率内完成万连，并在 20,000 次/s 的正式上下行 Ping/Pong 负载下跨过会话续期窗口。此记录只评价当前测试版本、部署和负载，不代表生产 SLA 或服务容量上限；以下登录与平衡吞吐基线没有修改生产代码，文末的 Agent 优化试验另行记录了代码改动。

## 夹具准备

第一次夹具准备有一轮遗漏 `cluster-fixture prepare`，导致若干登录请求提示 `discovery: slot runtime is unavailable`。这轮是无效准备，不纳入服务故障或性能统计。之后按正式夹具流程检查 Mongo 中目标角色，补齐缺失区间，并核实 `480100–490099` 共 10,000 个角色均存在且不重复，才开始速率测试。

## 登录建链速率

登录速率按从压测进程开始准备，到 10,000 个不同角色的会话全部进入 ready 状态计算。因此它包含客户端启动及完整登录/分配链路，不等同于 Login 服务单进程吞吐。

| 配置目标 | 会话数 | 建链耗时 | 实测速率 | 随后 Ping 验收 |
| --- | ---: | ---: | ---: | --- |
| 300 会话/s | 10,000 | 37.498 s | 266.7 会话/s | 30 s；599,998/600,000 完成，失败 0、未发送 2，P99 7.217 ms |
| 500 会话/s | 10,000 | 23.054 s | 433.8 会话/s | 30 s；600,000/600,000 完成，失败/未发送 0，P99 9.353 ms |
| 500 会话/s（长测） | 10,000 | 22.829 s | 438.0 会话/s | 10 min；12,000,000/12,000,000 完成，失败/未发送 0，P99 8.617 ms |

实际建链能力随配置目标并非线性增长：300/s 配置未达到 300/s 下限；500/s 配置的 433.8–438.0/s 落在 300–500/s 目标区间内。后续报告应使用实测 ready 速率，不把配置参数写作实际速率。

## 十分钟正式负载

负载为 10,000 会话各 2 次请求/s，总计 20,000 次/s；两台 Agent 各持有 5,000 个会话。测试持续 600 s，覆盖两次会话续期。计划、尝试与完成均为 12,000,000，失败和未发送均为 0。汇总延迟：P50 0.962 ms、P95 4.145 ms、P99 8.617 ms、最大值 65.751 ms。两个客户端 worker 的 `skippedSlots` 和 `pendingAtEnd` 均为 0，事件循环利用率分别为 34.8% 和 35.1%；事件循环延迟 P99 分别为 11.264 ms 和 11.338 ms，最大值为 24.216 ms 和 21.398 ms。

## 资源与限制

十分钟 Ping 窗口中，服务进程 CPU 均值/峰值约为：Agent 两进程各 193%/205% 与 193%/204%，MsgQ 两进程各 106%/113% 与 106%/112%，Game 两进程各 109%/122% 与 110%/121%。进程 CPU 百分比以单核为 100%。各宿主机整体 CPU 均值/峰值为接入机 52%/58%、存储机 32.7%/41%、Game 机 32.3%/37%、客户端机 12%/28%；CPU steal 最大值均为 0。各机最低可用内存为 13.1、9.3、12.7、12.1 GiB。Agent 进程峰值 RSS 约 264 MiB，MsgQ 约 135 MiB，Game 约 519–535 MiB。

这些采样没有显示宿主机 CPU 或内存被打满，因此本轮未见资源耗尽证据；它们不能证明更高负载下没有瓶颈。客户端机器也参与端到端采样，结果是四机组合链路的测量，不是单台服务器或 Login 的隔离容量值。跨主机阶段延迟计数有 6,000/6,163 个无效时钟样本，不据此分析细分 RPC 阶段耗时。

本轮未观察到业务失败或会话所有权残留：测试结束后 Redis DB12 中角色归属记录降为 0。原先记录的 347 次准备阶段断连未在这次正式运行复现，因此不能据此宣称根因已找到或服务端问题已修复。txclient 本地修复解决的是准备阶段断连的报告与等待行为，不构成该云端现象的根因证明。

## 结论及后续

在四机当前配置下，10,000 会话以实测约 438 会话/s 建立，并在 20,000 次/s Ping/Pong 下稳定运行 10 分钟、零失败和零漏发，满足本轮新增的 300–500 会话/s 速率区间和 20,000 次/s 长窗口验收。300/s 的客户端配置实测只有 266.7/s，之后需用实测值报告速率。

当前原先关注的 20,000 次/s 十分钟长尾问题本轮未复现。继续向 30,000 次/s 或更高档位寻找容量边界尚无明确验收目标；在确认是否继续上探前，不把本轮结果外推为上限。

## 平衡 1:1 上下行吞吐边界

按用户要求先测试每会话相同频率的 Ping/Pong，不进入 20/50 不对称负载。每档 10,000 个会话，Agent 各承载 5,000 个角色；短档 30 秒，候选长期档 10 分钟。验收门槛为失败 0、未发送 0、P99≤100ms。以小数频率进行 1:1 配置，例如 3.75/s 表示每秒 37,500 个上行 Ping，并由每个 Ping 对应一个下行 Pong。

| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 3/s | 30 s | 900,000/900,000 | 29,703 | 0/0 | 31.457 | 通过 |
| 3.5/s | 30 s | 1,050,000/1,050,000 | 34,703 | 0/0 | 55.225 | 通过 |
| 3.75/s | 30 s | 1,130,000/1,130,000 | 37,368 | 0/0 | 73.171 | 通过 |
| 3.875/s | 30 s | 1,170,000/1,170,000 | 38,701 | 0/0 | 77.156 | 通过短档 |
| 4/s | 30 s | 1,199,997/1,200,000 | 39,702 | 0/3 | 194.961 | P99 不通过 |
| 5/s | 30 s | 约 1,494,458/1,500,000 | 49,518 | 0/5,542 | 243.439 | 发生器调度与长尾均不通过 |
| 5/s（4 客户端进程复测） | 30 s | 1,497,104/1,500,000 | 49,606 | 0/2,896 | 263.120 | 仍不通过 |
| 3.5/s | 10 min | 21,000,000/21,000,000 | 34,985 | 0/0 | 61.219 | 通过长期档 |
| 3.875/s | 10 min | 23,250,000/23,250,000 | 38,735 | 0/0 | 103.365 | P99 略越线 |
| 3.75/s | 10 min | 22,500,000/22,500,000 | 37,485 | 0/0 | 79.395 | 通过长期档 |

两档 5/s 的四个客户端进程复测中，事件循环利用率约 73%、事件循环 P99 约 32–43ms，说明请求长尾并非只由双进程负载发生器饱和造成；不过约 0.19% 的计划请求仍被调度器跳过，因此 5/s 不能用作已完整承载的边界证据。短档 4/s 请求漏发仅 3 个，但 P99 已达 194.961ms，不满足门槛。

10 分钟 3.5/s 测试期间，四个客户端 worker 的事件循环利用率为 41.3–41.7%，事件循环延迟 P99 约 12.5ms，`skippedSlots` 均为 0；3.75/s 对应值分别为 45.8–46.3%、13.6–13.9ms，`skippedSlots` 也均为 0。接入机 vmstat CPU idle 平均分别为 25.2% 与 22.3%；3.75/s 时两台 Agent 各平均约 305% CPU（单核为 100%）。Game 机 CPU idle 约 64%，两 Game 进程各约 143%；存储机 CPU idle 约 63%，两 MsgQ 进程各约 128%；客户端机 CPU idle 约 74%，四个 Node worker 各约 55–57%。3.875/s 十分钟档接入机 CPU idle 约 20.4%，Agent 各约 313–315%，P99 为 103.365ms。其他节点有明显 CPU 余量，压测发生器事件循环亦未饱和。

服务端零失败/漏发及 P99 门槛不能掩盖更高分位的毛刺。对完整客户端延迟数组做阈值计数：3.5/s 的 21,000,000 次中，19,950 次超过 100ms（0.095%）、2,143 次超过 200ms、48 次超过 300ms，最大 328.511ms；3.75/s 的 22,500,000 次中，92,118 次超过 100ms（0.409%）、12,479 次超过 200ms、2,927 次超过 300ms、273 次超过 400ms，最大 481.989ms。由此，约 35,000 次/s 是尾部更薄的保守稳态档；约 37,500 次/s 是本轮最高通过既定 P99≤100ms 门槛的十分钟档，但长尾明显增厚。

据此，在当前四台 8 vCPU 实例与两 Agent 配置下，保守长期档约为 35,000 次/s；按既定 P99≤100ms 门槛，本轮最高通过十分钟的平衡吞吐约 37,500 次/s。接入机 Agent 是目前最接近 CPU 资源压力的路径；当前观测到 P99 跨过 100ms 的转折位于约 37,500–38,700 次/s。该结果是本拓扑与 System_Ping/Pong 工作负载的容量边界，不代表带业务逻辑、世界广播或其他硬件的容量，也不是 20/50 目标的验收。

平衡路径已经有 10 分钟零失败/漏发的通过档。后续可按用户顺序转入上下行不对称测试；不把 3.75/s 等值外推成独立上行或下行的容量值。

## Agent CPU 画像与小帧读取试验

在四机万连、3.75 次/s/会话的负载下，临时启用现有 `txbench` pprof 入口，对 `GOMAXPROCS=4` 的两台 Agent 各采 20 秒 CPU 画像及分配画像；采样结束即关闭入口。开启画像的负载完成 2,250,000/2,250,000 次，失败/漏发 0；其 P99=73.272ms，包含画像开销，不拿来和无画像基线直接比较。两台 Agent 的 CPU 样本约为每台 3.1 核，调用栈相近。`grpc.ClientConn.Invoke` 累计约占 42%–43% CPU；Agent TCP `Read` 累计约 8%，`Write` 累计约 9%；`msgq.FetchSome` 累计约 15%–16%，Actor 直连 `Call` 累计约 21%–22%。这些是包含子调用的累计值，彼此重叠，不能相加为各阶段独立占比。分配画像显示 gRPC 每次 unary 调用创建流和处理响应的对象分配占主导。Agent 接入压力因此不只是 socket 数据读写，也包括每条 Ping/Pong 必经的 MsgQ 与目标 Actor gRPC 调用。

先对 TCP 小帧读取做受限优化：每条连接保留 256 字节读缓冲，万连对应约 2.44 MiB 固定缓冲；超出时仍按实际长度分配。解码器已复制返回的 Payload，因此下一帧复用缓冲不会覆盖上一帧。以 `System_Ping` 大小的帧做三轮本地微基准，原版中位约 342.2ns、208 B、6 alloc；优化版中位约 312.5ns、160 B、5 alloc，减少 48 B 和一次分配，读路径耗时约降 8.7%。这是隔离读路径的结果，不推导为端到端等比例提升。`go test ./...`、Agent/TCP/Frame 定向测试及该范围的 `-race` 均通过，包含前后两帧 Payload 独立性检查。

读缓冲版 3.875/s 两轮十分钟均完整执行 23,250,000 次、无失败/漏发，P99 为 90.647/80.680ms，实测吞吐 38,735 次/s。相比原版最高通过的 3.75/s 十分钟档 37,485 次/s，本轮重复通过的档位高约 1,250 次/s（3.3%）；原版 3.875/s 同日长测 P99 为 103.365ms。由于原版同档只有一轮，不能断言单处小分配优化独自造成全部 P99 差异。优化版首轮此档接入机 vmstat 的正式窗口核心分钟平均 CPU idle 约 21%，两台 Agent 平均 CPU 各约 310%，进程 RSS 峰值约 315/300 MiB；同频原版早一轮的 Agent 平均 CPU 各约 313–315%。CPU 差异很小，也不足以单独解释延迟变化。

读缓冲版 4/s 首轮十分钟实测吞吐 39,985 次/s，P99=97.303ms，距门槛只有 2.7ms。四个客户端 worker 均未跳过计划点或留下待完成请求，事件循环利用率约 52%、延迟 P99 约 16ms。接入机核心分钟 CPU idle 均值约 18.3%，两台 Agent 各约 319% CPU，Game、存储和客户端主机 idle 均值分别约 63%、65%、70%。相邻的原版同档长测也完整执行 24,000,000 次，但 P99=115.041ms；接入机 CPU idle 均值约 18.0%，两台 Agent 各约 320% CPU，客户端 worker 同样没有漏发，事件循环利用率及延迟与优化版接近。两版 CPU 利用率几乎相同，P99 差约 17.7ms，说明不能仅靠 CPU 百分比解释延迟。随后优化版同档重复测 P99=109.194ms，四个 worker 分别跳过 254/330/303/288 个计划点，合计 1,175 个；事件循环利用率仍约 50%、延迟 P99 约 15–16ms。这说明 4/s 过线不可重复，不能作为稳定容量增益。

本轮保留该 6 行净增的生产优化和独立性测试：小帧每次读取少一次分配，云端 3.875/s 长档重复通过；4/s 一轮通过、一轮 P99 与漏发均失败，不能作为稳定边界。更大收益需评估 Agent 每条消息触发的 MsgQ 与 Actor gRPC 调用成本，不继续在 TCP 小帧上叠加微优化，也不直接改动 Rec/Ack 或排水契约。试验结束后两台云端 Agent 已恢复原版二进制，临时 pprof/二进制启动覆盖均移除；云端构建源码恢复原版，压测角色归属降为 0。优化版代码只在本地未提交工作区，云端原始 profile 与客户端结果保存在上述本地产物目录。
