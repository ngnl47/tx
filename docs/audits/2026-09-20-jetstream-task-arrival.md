# JetStream 固定计划到达率验收

接续未提交的 [闭环任务基线](2026-09-20-jetstream-task-baseline.md)，复用同一独立测试入口。生产 Publisher、Processor、Worker 和默认同步策略均未改变。

## 口径

环境保持 Go 1.27.0 darwin/amd64、GOMAXPROCS=4、NATS 2.14.6、nats.go 1.53.1。同机三 Broker、FileStorage、sync_interval=always，仅变更源流和 durable 的副本数；实际性能窗口只创建源流与 durable，不注入死信和故障。32 个热 Actor、256B payload、4 发布者和 4 消费回调，业务仍为内存计数，不含 GD/数据库。

`TX_TASK_RATE=50/100/200` 分别规定每秒计划到达数；每窗口 5 秒，即 250/500/1000 条任务。每档 R1/R3 各三轮，三档串行执行。4 个发布者按序号轮转承担任务，所有计划时刻在窗口开始即确定；延误不重置后续计划时刻，落后的任务保留，不丢样本或无限增加并发。它是有界发布并发下的固定计划到达模型，不承诺所有负载都能准时抵达 Broker。

指标定义：

- `planned_complete_p99_ms`：计划到达时刻到 Actor 执行及 DoubleAck 完成，包含本地调度等待、发布、排队和消费。
- `start_lag_p99_ms`：计划到达到实际开始 Publish 的延误；较大时说明发布端未跟上计划。
- `unfinished_at_window_end`：5 秒窗口末尚未完成数，包含未开始发布、发布中、队列中及处理中任务，不是 JetStream NumPending。
- `not_started_at_window_end`：其中尚未开始 Publish 的数量，不能归因于 Broker 内部队列。
- `drain_ms`：计划窗口结束后，直到全部 Publish 返回且任务确认完成的额外耗时；提前完成记为 0。

窗口末采样由进程内定时器触发并加锁取数，有调度精度限制，不是某个绝对时刻的分布式快照。源流清理收敛另行校验，不计入上述完成计时。没有给可靠任务设生产 SLA；通过表示正确性核验成功，不表示任意流量下尾延迟达标。

## 复现

先准备独立三节点 NATS，显式确认同步策略和持久存储位置，然后在 tx 根目录运行：

```sh
TX_TASK_BASELINE=1 TX_TASK_RATE=100 \
TX_ACTORTRIAL_NATS_URL='nats://127.0.0.1:<隔离端口>' \
TX_ETCD_ENDPOINT=127.0.0.1:2379 GOMAXPROCS=4 \
go test ./internal/framework -run '^TestJetStreamTaskBaseline$' -count=1 -v
```

不设置 TX_TASK_RATE 时保持原闭环模式。性能记录不使用 `-race`；先单独运行 race 验证，再串行采集，采集期间不并行跑全量回归。随机资源继续按 owner 校验清理，失败保留。

10500 条正式采集任务全部执行并确认，逐条核验 NumDelivered=1、无重复完成、业务计数匹配，源流最终清空；没有丢弃未开始的任务。100 条/s 的独立 race 验证另计 3000 条，通过且不进入性能数据。

200 条/s 的 R3 第一轮中，实际开始发布→完成 P99 为 268.38ms，但计划到达→完成 P99 为 9454.43ms，窗口末 618 条任务尚未开始发布。只统计实际发布后的耗时会隐藏本地调度积压。R1 在该档也存在显著窗口波动，不能用最快一轮宣布容量达标。

这些是 5 秒短窗口及同机虚拟化存储的观测，不能证明长期稳态。没有通过修改默认同步策略、扩大消费超时、自动重发或放弃任务来改善结果，也没有把波动归因于某个生产代码热点。后续先评估同步策略/部署存储与所需任务速率的匹配，再决定是否有代码优化价值，不继续盲目做细碎优化。

本轮验证：100 条/s 的三轮 R1/R3 `-race` 通过（31.14s）；非 race 50/100/200 条/s 用例分别通过（31.01s、31.35s、57.79s），`go test ./... -count=1` 全量回归通过，未显式启用的外部依赖测试沿用跳过约定。本轮成功清理独立网络 `tx-task-baseline-8cln53ae`、三个测试容器及临时配置；此前失败保留的集群不在本次清理范围。
