# NATS 请求封包实验（T3f）

## 结论

本批完成已批准的“请求合批、回复逐条”候选、正确性检查和三组隔离对照。**不接入默认运行时，停止本方向的小幅优化，T4 继续暂停。** 四 P 下确实减少了 NATS 消息数，但没有稳定的完整 RPC 吞吐收益；单 P 基本无法成批，新增封包与关联成本仍需支付。

这不是 NATS 吞吐上限，也不代表所有合批方案无效。结论只适用于本次不等待凑批、维持本地 Publish 后返回、逐条回复的候选。没有继续双向合批、定时凑批或改变 Future 返回边界。

六工程状态在本轮开始重新核对：tx、txgame、txgameslg 位于 `feature/nats-actor-runtime`，tx HEAD 为 `974146c506a7279f188677de40ebf312078ba519`；txgen、两个客户端在 main。只有 tx 存在此前 T3d–T3e 和本轮 T3f 未提交变更。未提交 Git，未修改其他五工程。

## 实现与职责

设计依据为 [T3f 评估稿](2026-09-13-nats-request-batch-assessment.md)。[候选夹具](../../internal/actortrial/comparison_batch_test.go) 和 [接线构建脚本](../../internal/actortrial/testdata/request_batch/build.py) 仅进入测试覆盖构建：

- 单连接一个有界发送协程，每次取出当前已有的最多 64 项，再按目标实例稳定归组；没有定时器、帧等待或长期每实例队列。
- 同实例的 Call 可封包；Tell/TellAccepted 是单条发送边界。回复、Probe、激活与槽位控制仍走原路径。
- 单个实例订阅接收普通报文及实验封包，逐项复用原有身份解码、Delivery 解码、准入、邮箱和回复。慢 Actor 不拖住其他 Actor 的结果。
- 各项保留 Actor-Identity、Delivery 字节及独立 Reply，业务 RequestId 不被占用。外层使用 `inbox.b42` 一类单 token 地址，专门关联外层 503 或解码错误。
- 批次与仍在等待的调用共用 pending 的锁内删除边界；首项取消不影响其他成员的错误清理，不保存历史载荷、完成表或重投记录。
- 封包最多 64 项、64KiB，包含 NATS 头并服从当前 max_payload；大于封包上限的合法单消息保留原格式。队列条目数与编码字节预算在同一锁内准入，取出后归还预算。
- Runtime 排空及必要持久化成功后才停止发送准入、排完队列并 Flush。`Transport.Drain` 与 `SlotHost.quiesce` 都已接线；后者继续保留交接控制连接。持久化失败保留发送器与连接。

例如两条 Call、一个 Tell、再一条 Call 发往同一实例时，允许形成“前两条 Call 的批包 → Tell → 后一条 Call 的批包”。每条 Call 仍有自己的结果，不等待整批业务完成。

协议使用锁定的 protobuf v1.36.11 生成器及 protoc 36.0；没有修改现行 actor.proto、正式 API、SPI、生产配置或依赖版本。[复现说明](../../internal/actortrial/testdata/request_batch/README.md) 包含生成输入、覆盖构建和真实依赖检查命令。

## 正式性能样本

三组只比较完整实体运行时：base 为当前路径，batch1 为新封包但每包 1 项，batch64 为相同发送器及关联逻辑、每包最多 64 项。基线与候选的回复均逐条发送。

单 NATS 2.14.6 broker；调用端、目标端是独立 Docker 进程，三进程共享 Linux 网络命名空间，同样设置 GOMAXPROCS=1 或 4。Go 1.27.0、nats.go v1.53.1；128B 载荷、1000 个身份、64 并发，每组预热 1000 次，每个窗口 3 秒，每种 P 数交替五轮。各组 namespace 与实例名长度一致，组名仅用于容器和材料命名。

共 **30 个正式窗口，3,145,132 次成功 RPC，0 返回错误、0 丢弃**。每次结果均校验载荷；保存 N 份成功延迟，核验 P50/P99。每个正常窗口的 broker 入站和出站均为 Q+N，Q 是实际请求包数，N 是逐条回复数；没有把一批完成算成多次成功。

单 P 的固定发送器帮助 SDK 合并 Write，但它很快取走队列中的请求，外层封包仍几乎都是单项；这与“最多 64 项”并不矛盾。四 P 形成小批次，降低消息和发送字节数，但新增队列、protobuf 外层及 pending 关联仍有成本。以上是链路和计数证据，不仅是 pprof 推测。

## 本轮验证与材料

- 先用保留逐条发送的检查复现顺序测试失败，再实现归组与 Tell 边界；最终检查覆盖实际发送协程的跨实例稳定归组。
- 同批多实体独立结果与业务 RequestId、快慢项互不等待、加载拒绝、panic、坏身份和坏 Delivery、首项取消后整批 503/坏格式/发送失败/关闭清理均通过。
- 队列条目与字节预算拒绝及归还、旧连接排队请求不补发、关闭上下文、64KiB 含头边界和合法大单消息回退通过。未知外层格式未激活业务实体。
- 既有取消、重连不重放、邮箱准入、worker 回复与卸载、真实槽位交接、Redis 收尾及持久化失败保留连接回归通过。封包沿用逐项 `submitRequest` 准入，并未增加整批事务或第二套业务完成屏障。
- `go test ./... -count=1`：**1140 pass / 60 skip / 0 fail**，包含子测试；未显式启用的其他真实存储测试仍按原门槛跳过，不能算作本轮通过。
- 显式启用 NATS、etcd、Redis 的原路径 race：**61 pass / 1 skip / 0 fail**；候选 race：**69 pass / 1 skip / 0 fail**。单个 skip 是未由外部编排器启动的比较进程入口。
- 候选 `go vet` 通过；batch1 构建下的合批边界夹具也单独通过。其他五工程未修改，因此未重复全量测试或客户端构建。

本地原始材料目录：`/private/tmp/tx-nats-batch-20260913/`。包含 `results.jsonl`、逐窗口 `.json.gz` 延迟、`summary.json`、`source-and-binaries.json`、`sample-source/`、三组二进制及 overlay、诊断临时依赖副本、编排脚本、`checks.json` 和完整测试输出。正式采样源码快照保持原样；最后仅加强测试断言及收窄构建脚本参数，发送器和两份 Transport/SlotHost 覆盖源码与采样版本一致。
