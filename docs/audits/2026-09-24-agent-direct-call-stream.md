# Agent→Actor 直连双向流试验

## 目标与边界

本轮只替换 Agent→Game Actor 的直连 `Call` 传输：每个目标 gRPC 连接复用一条双向流，流内以请求 ID 关联逐项结果。Actor 的定位、激活、邮箱串行化、调用期限、错误分类及排水入口保持原路径；MsgQ `Rec`、`FetchSome`、Seq/Ack 和上下行帧未改。`directCallBatch` 在云端全部关闭，故以下 A/B 不包含 1ms 短窗口合批。

长流在首次调用时建立；调用方取消只取消本项，接收方仍可处理同流其他项。流断开会将所有未完成调用返回错误，不自动重投可能已经进入 Actor 邮箱的业务。后续调用可以建立新流。每条流最多有 1024 个服务端在途调用，达到上限时通过停止读取传递 gRPC 流控压力。两个开关均默认关闭；试验时明确设置 `directCallBatch: false`、`directCallStream: true`。

## 本地验证

同一个 loopback gRPC Host 与 Actor 夹具中，慢、快两项共用长流，快项无须等待慢项；关闭本项调用后，服务端观察到取消，同流后续调用继续成功。另用真实 TCP gRPC Host 注入断流：两条调用已进入服务端后强制停止 Host，两条在途调用及时返回失败，旧请求没有自动重投；同址重启后，同一个 Sender 的新调用恢复成功。检查发现旧流先通知错误、再从连接缓存移除，会让紧接着发起的新调用短暂取得已关闭流；现已改为先移除、再通知失败。此故障边界连续 100 轮 `-race` 通过。`tx` 与 `txgame/server` 的 `go test ./... -count=1`、原长流相关定向 `-race` 三轮均通过。

Mac、Go 1.26.5、`GOMAXPROCS=4`，同一 Actor+gRPC 夹具，`-benchtime=3s -count=3 -benchmem`：

| 并发 | Unary 每次耗时 | Stream 每次耗时 | Unary 分配 | Stream 分配 |
| --- | ---: | ---: | ---: | ---: |
| 16 | 21.36–21.52µs | 10.89–13.51µs | 196 次、约 15.5KiB | 75 次、约 6.3KiB |
| 64 | 18.67–19.41µs | 12.92–13.20µs | 196 次、约 15.3KiB | 74 次、约 6.3KiB |

这里的耗时是并行负载的吞吐摊销，不是单次端到端延迟，也不包含客户端、MsgQ 和云端网络。

## 四机同版 A/B

服务端均使用同一 Linux `txbench` 二进制，SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`；仅切换两台 Agent 的 `directCallStream`。两档都明确关闭 `directCallBatch`，保持两 Agent、两 Game、两 MsgQ、两客户端进程，10,000 个 TCP 会话、500/s 建连、预热 2 秒、正式测量 30 秒。所有已发送请求等待完整 Ping/Pong 闭环，不能把已发送成功当作业务完成。原始 `client.json`、逐进程采样和日志归档在工作区 `tx-artifacts/cloud-20260924-stream/`，采集脚本只在旁路运行。

上述云端二进制早于本地“先移除旧流、再通知失败”的竞态修正；该修正仅改变断流边界，尚未重新做云端性能 A/B。云端两台 Agent 当前均保持合批和长流关闭。

## 四机链路故障与恢复

将包含上述竞态修正的 `txbench` 二进制（SHA-256 `1b8579499619b081914fec3d11aea2b729e84a3e0dd24e5d24e593d418a65fc3`）仅部署到接入机；Game、MsgQ 保持同协议旧版。两台 Agent 设置 `directCallBatch: false`、`directCallStream: true`。先用 100 个 TCP 会话、每会话 1 次/s 的 10 秒预检完成 1000/1000 个 Ping/Pong，零失败、零漏发，P99 1.136ms。

随后在同负载的 30 秒测量窗口内，以接入机临时 `iptables OUTPUT REJECT --reject-with tcp-reset` 切断到 Game 两个 gRPC 端口 5 秒（UTC 2026-09-23 18:48:52–18:48:57）。两个客户端进程各计划 1500 次、实际发出 374 次、完成 324 次、失败 50 次；余下各 1126 次因工作负载遇错退出而未发送。两台 Agent 日志均记录 `Unavailable`，包括连接重置和重连时的 `connect: connection refused`；客户端记录等待 `System_Pong` 超时，没有把这些请求统计为成功。失败样本的 P99 只统计故障前完成的请求，不能作为故障期间的延迟指标。客户端工具在失败退出时没有生成汇总 `client.json`，上述计数取自归档的两个 worker JSON。

撤销规则后，不重启 Agent、Game 或 MsgQ，重新建立 100 会话并完成 1000/1000 次，零失败、零漏发，P99 1.074ms。这证明网络恢复后的新请求可在同一批服务进程中继续完成；客户端没有收到即时业务错误，本次也不能证明原会话在故障后自动恢复或所有在途调用都立即返回。故障期的请求结果未知时不自动重投。预检、注入、恢复的原始归档、注入时刻和 Agent 摘录见工作区 `tx-artifacts/cloud-20260924-stream/`；注入及采集脚本只在旁路运行。试验结束已将接入机二进制恢复到 A/B 版 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，两台 Agent 的合批和长流开关均关闭，四个接入服务运行中，临时防火墙规则已撤销。

## 后续验收

本地真实 Host 断流测试覆盖了在途调用失败及新流恢复；四机测试覆盖了 Agent→Game 网络中断后，业务失败可见和网络恢复后新会话继续运行。两者均不能代替生产滚动排水、实例异常或原会话自动恢复的验证。不能把 1:1 Ping/Pong 容量外推到 MMO 上行 20/s、下行 50/s；该不对称负载继续独立评估。

后续四机真实上下行不对称回测见 [2026-09-24-asymmetric-downlink.md](2026-09-24-asymmetric-downlink.md)。
