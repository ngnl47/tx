# 实例连接轮换与 Actor 直连传输对照

## 连接生命周期

普通 RPC Sender、MsgQ 下行发布 Sender 和 Agent 的远端 SessionClientRouter 现共用 `internal/instanceconn`：相同 endpoint 与 InstanceID 复用连接；目录出现同址新实例身份后，新拨号替换并关闭旧连接；拨号完成前若目录已移除旧身份，拒绝安装迟到的旧连接。关闭过程中完成的拨号也立即关闭。热路径不额外查询目录，三处仍由原路由器决定目标；流断开或实例轮换后，结果未知的在途请求不自动重投。

此处只统一物理连接的复用和关闭。Actor `CallStream` 自行关联并发调用，MsgQ `RecStream` 仍按会话分道等待逐条回执，下行 `StreamFetch` 仍是会话级服务端流；没有把三种不同语义改成同一个通用流协议。Agent 本地 `RecLeaseInterval` 候选未改，也不能据此称为分布式租约。

## Actor Batch 与 Stream 同版 A/B

一台腾讯云 SA9 8vCPU/16GiB、Ubuntu 24.04 机器，Login、Agent、MsgQ、Game 各一进程，均为 `GOMAXPROCS=2`。同一服务二进制 SHA-256 为 `7c60f0d4f0a2ee72d535348859a47f3d0bd864e0014076bd15a4350c73834418`；每轮重新准备 2,000 个 TCP 会话和角色，2 秒预热、30 秒正式窗口，每会话 10 次/s、1:1 Ping/Pong、最多 4 条在途。MsgQ `RecStream` 保持关闭；仅切换 Agent 的 Actor 直连 `directCallBatch` 与 `directCallStream`，顺序为 Batch→Stream→Batch。测试结束后四个单实例服务已恢复运行。压测脚本和完整原始采样归档已保存于工作区 `tx-artifacts/cloud-20260925-single-host/actor-batch-stream.sh` 与 `actor-batch-stream-20260925.tar.gz`。

| Actor 传输 | 完成/计划 | 未发送/业务失败 | P50 | P99 | Agent/MsgQ/Game 平均 CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| Batch A | 600,000/600,000 | 0/0 | 2.99ms | 24.62ms | 132% / 97% / 91% |
| Stream | 600,000/600,000 | 0/0 | 2.08ms | 29.19ms | 151% / 104% / 105% |

CPU 为 `pidstat` 各进程最后 30 个一秒样本的算术均值。Batch B 因窗口末一条计划消息未发，未达到严格零未发送口径。Stream 在此负载下 P50 更低，但两轮 Batch 的 P99 与 CPU 均更低；结合此前四机高密度 Batch 稳态收益，当前不能认定合批在长流启用后已经冗余。两者在现有运行时中是互斥选择，Stream 开启时不会叠加 Batch 的等待窗口。保留 Batch，不把单机 P2 的结果外推为四机万连容量或 20/50 不对称目标；下一步需按目标负载在多机环境复核传输选择，而不是直接删除已验证有效的协议。

## 验证边界

`tx` 全量测试以及 `txgame/server`、`txgameslg/server` 全量测试通过；`internal/instanceconn`、`modules/rpc`、`modules/msgq` 的竞态测试通过。连接轮换的并发测试覆盖同址新身份替换、旧拨号迟到、关闭期间拨号。A/B 所用云端二进制早于本轮共享连接缓存修改，因此 A/B 只比较传输模式，不作为本轮新缓存的云端性能回归。

## 本轮单机真实进程重启验收

在同一台云机的当前未提交源码上，先运行 Linux 定向测试，再编译服务；集群验收按项目已有专用 Redis DB12、Mongo database 和 etcd prefix 运行，不使用生产数据区。Agent 启用 Actor `CallStream` 和 MsgQ `RecStream`；测试启动 Login、Agent、MsgQ、Game 各两实例，以正式客户端完成初始 Ping/Pong，再依次验证 Agent 排水重启、同址 Game 重启、同址 MsgQ 重启、Login 重启和恢复后的会话消息链路。构建出的验收服务 SHA-256 为 `05368f1622d604b6b0af2312a4a8925a498a6db37bf204a06541360f166e7da6`。

本轮报告 `status=passed`，共记录 13 个先后启动的服务进程和 8 组会话证据。Agent 重启前后，角色 470201 的 SessionID 均为 `387689174646784`，ConnectionID 从 `6171600734361474827` 变为 `8830674099765359395`，MsgQ 实例身份不变。Game-a 从 `txgame-107-19962` 变为 `txgame-1982-20007`；MsgQ-a 从 `txgame-3059-19956` 变为 `txgame-1585-20018`，重启后两组会话分别落到新 MsgQ-a 与仍运行的 MsgQ-b。验收结束后原四个单实例 P2 服务均恢复为运行状态，临时启用的 `recStream` 模板已还原。原始 `summary.json`、客户端与进程日志已保存到工作区 `tx-artifacts/cloud-20260925-single-host/instanceconn-process-e2e-20260925.tar.gz`，运行输出保存为同目录 `instanceconn-process-e2e-20260925.log`。

这证明当前实现可在单宿主机的真实多进程同址重启后继续建立新连接并完成会话链路，不证明跨宿主机容量、异常断连时在途请求必完成，也不改变上述 A/B 使用旧二进制的性能证据范围。下一项在有多机环境时复核跨宿主机负载与故障边界；无需为已通过的同址重启再租机器。

## Batch 与 RecStream 组合对照

为补齐此前两项单独对照的组合空格，使用包含共享连接缓存的同一服务二进制（SHA-256 `a9d336fa697fae5fd977ee0332df5898aff149d4031bdcc0d444fad53c567f80`），固定 Actor `directCallBatch=true`、`directCallStream=false`，仅切换 Agent→MsgQ 的 `recStream`。单机 Login、Agent、MsgQ、Game 各一进程、各 `GOMAXPROCS=2`；每轮重新准备 2,000 个 TCP 会话，按每会话 10 次/s、1:1 Ping/Pong、最多 4 条在途运行。30 秒顺序为 Unary→RecStream→Unary，随后仅对组合候选运行三分钟稳态。

| Rec 传输 | 完成/计划 | 未发送/业务失败 | P50 | P99 | Agent/MsgQ/Game 平均 CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| Unary A，30 秒 | 599,999/600,000 | 1/0 | 3.03ms | 25.15ms | 132% / 97% / 91% |
| RecStream，30 秒 | 600,000/600,000 | 0/0 | 2.43ms | 18.68ms | 110% / 82% / 92% |
| Unary B，30 秒 | 599,985/600,000 | 15/0 | 3.03ms | 25.37ms | 132% / 97% / 92% |
| RecStream，三分钟 | 3,600,000/3,600,000 | 0/0 | 2.42ms | 19.19ms | 110% / 82% / 92% |

CPU 为 `pidstat` 在正式窗口末 30 或 180 个一秒样本的算术均值。两轮 Unary 存在未发送，不能作为严格零漏发的通过档；本次也没有定位其未发送原因。组合候选的短轮和三分钟轮均满足零未发送/业务失败，说明 Batch 与 RecStream 在此负载下可以同时工作，且相对两轮 Unary 呈现更低的 Agent/MsgQ CPU 与 P99。该结果只支持后续多机目标负载优先验证此组合，不直接将 `recStream` 改为默认开启，也不推断万连或 20/50 不对称容量。测试后四个原单实例服务均恢复运行；完整客户端与进程采样、运行输出和脚本归档于工作区 `tx-artifacts/cloud-20260925-single-host/batch-recstream-combined-20260925.tar.gz`。

## 四机万连同版对照

四台腾讯云 SA9 8vCPU/16GiB、Ubuntu 24.04 实例位于同一 VPC：MsgQ×2 P4 与 Redis、Mongo、etcd、NATS 在一台，Game×2 P4 在一台，Agent×1 P8 与 Login×2 P4 在一台，客户端八个 Node 进程独占一台。服务使用上述同一二进制及专用 Redis DB12、Mongo database、etcd prefix；每轮重新准备 10,000 个独立 TCP 会话和角色。固定 Actor Batch、下行 StreamFetch、2 秒预热、三分钟正式窗口、每会话最多四条在途；仅切换 Agent→MsgQ `Rec` 的 Unary/RecStream。先在 10/s 运行 Unary→RecStream，再在 5/s 运行 RecStream→Unary。每轮正式窗口分别采集 180 个一秒服务进程 CPU 样本，不将登录准备阶段计入。

| 每会话速率、Rec 传输 | 完成/计划 | 未发送/业务失败 | 上下行各自吞吐 | P50/P99 | Agent CPU | MsgQ 两进程 CPU |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10/s、Unary | 14,947,099/18,000,000 | 3,052,901/0 | 83,039/s | 476.98/676.44ms | 771% | 194%/195% |
| 10/s、RecStream | 15,795,869/18,000,000 | 2,204,131/0 | 87,755/s | 434.36/610.98ms | 627% | 192%/191% |
| 5/s、RecStream | 8,999,999/9,000,000 | 1/0 | 50,000/s | 1.80/28.80ms | 393% | 147%/147% |
| 5/s、Unary | 8,999,999/9,000,000 | 1/0 | 50,000/s | 2.02/36.24ms | 480% | 157%/157% |

10/s 两档都未达到零未发送和 P99≤60ms 目标。RecStream 相对 Unary 完成吞吐高约 5.7%、未发送少约 27.8%、P99 低约 9.7%，但不能将其视为 10/s 的容量验收通过；八个客户端事件循环利用率约 77%–85%，且报告了大量在途容量等待和跳过的计划时隙。5/s 两档完成吞吐相同，RecStream 的 Agent CPU 少约 0.87 核，P99 低约 7.44ms。两档各有一条计划请求落在正式窗口最后 0.16ms：客户端记录 `skippedSlots=0`、`capacityWaits=0`，对应会话分别在截止后约 0.23ms、0.46ms 才结束调度，因此是固定截止窗口边界的未发送，仍按严格口径判失败。此现象不代表服务端拒绝，也不能无证据地归为业务漏发。

四机结果支持保留 Batch+RecStream 作为候选：它在有余量的 5/s 档减少了 Agent 的 CPU 与尾延迟，在过载 10/s 档仅有限改善，尚未达到万连 10/s 严格目标，更不能外推 20/50 不对称吞吐。继续保持 `recStream` 默认关闭，下一项优先依据四机分段指标判断 Agent 仍消耗的 CPU 与排队位置；若评估调整传输默认值，先补严格零未发送的同档复核及排水、断线回归。四轮客户端原始结果、逐次延迟、调度诊断与三台服务机 CPU 采样保存在工作区 `tx-artifacts/cloud-20260925-four-host/`。

## RecStream 并发分道定位与复测

在上述四机、万连×10/s 档，仅为 Agent 编译启用 `txbench` 画像，运行 20 秒 CPU、阻塞和互斥采样。该诊断轮完成 14,208,031/18,000,000 次，P99 约 652ms；画像本身会扰动负载，因此不与无画像轮比较绝对吞吐。CPU 画像中，gRPC TCP 写入、`Rec`、`StreamFetch` 和 Actor 直连调用的累计调用栈分别约占 21.0%、13.9%、11.1% 和 8.1%，栈之间可能重叠，不能相加。阻塞画像显示 Agent 在 `recStreamPool.Rec` 等待共享流分道的累计协程等待时间约 42.2 小时；这是 20 秒采样窗口中众多协程的等待时间之和，并非请求延迟或单线程耗时。定位到原先每个 MsgQ 连接只有 16 条共享 `RecStream`，同一道上不同会话争用。

仅将 `recStreamLaneCount` 从 16 改为 64，未改变逐条等待 MsgQ 回执后才分派 Actor 的契约，也未改 Actor Batch、StreamFetch、业务协议和服务进程数量。两版在云端同一源码树、同一构建命令编译；重建 16 路二进制与上述基线 SHA-256 `a9d336fa697fae5fd977ee0332df5898aff149d4031bdcc0d444fad53c567f80` 完全一致，64 路二进制为 `f53ced59b50d5dee7fe6a19e9140a5408a8e6dc5b79548a57830785c8ff70af5`。仅 Agent 所在宿主机切换候选二进制。每档重新准备角色，正式窗口三分钟，无 pprof 干扰。
