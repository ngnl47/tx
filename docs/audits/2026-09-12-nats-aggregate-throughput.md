# NATS 多实例聚合负载与业务性能预算

日期：2026-09-12。起点 tx=4a92907；六工程开始时干净。tx、txgame=3afc074、txgameslg=2fd67a6 位于 `feature/nats-actor-runtime`。本批只修改 tx 的测试驱动和文档，不提交 Git，正式 API/SPI 与生产实现没有变化。

## 目的与计量边界

[T3a](2026-09-12-nats-shared-replies.md) 的三节点对照只有一组业务调用对。本批让三组调用端/目标端同时运行，检查分摊多个连接的聚合吞吐与资源成本，不把一个调用对的峰值乘以三当作扩容结果。

每组均为两个独立 Go 进程、1000 个预热实体、16 个 worker，合计六业务进程、3000 实体和 48 并发。固定路由、请求/响应校验及载荷副本沿用 T3 驱动。三组使用不同命名空间，共享同一 etcd；这测量固定调用对的数据面聚合，不等于六成员虚拟寻址、任意调用图或单世界热点验收。

| 对照 | 连接布置 |
|---|---|
| ProtoActor | 三组调用端直接调用各自目标，NATS 空闲 |
| 单 broker | 六业务进程都连接节点 1 |
| 三 broker，就近 | 第 i 组的两端都连接节点 i；各节点各承载一组 |
| 三 broker，跨节点 | 第 i 个调用端连接节点 i，目标端连接下一节点，形成 1→2、2→3、3→1 |

三节点场景均检查完整路由网格，以及每个 broker 恰有两个业务连接；不使用 Queue Group 随机分配实体。单节点仍启用 route 监听，另外两节点不在线。没有 JetStream、TLS、业务 GD/Procedure 或持久化操作，不宣称故障切换和 HA 通过。

本机为 Intel i9-9880H、32GiB，Docker Desktop 29.6.1 的 Linux VM 有 16 vCPU、约 7.75GiB，Linux 6.12.76-linuxkit。业务二进制为 Go 1.27.0、linux/amd64、CGO_ENABLED=0；每容器 GOMAXPROCS=4，未设 CPU quota 或独占绑核。所有容器共用同一 Linux 网络命名空间与宿主物理资源。GOMAXPROCS 不是预留 CPU，增加 broker 容器没有增加物理机器、内存带宽或网络容量。

镜像固定为 NATS `sha256:ad7a43eb7e3337c3c38ce5d784d1461791f95f730f252d2b25eee699752a0ca3` 和 etcd `sha256:0934690612905554eb61ddefb9faaaecb47c2f6931dbb453e694358092ee8990`，对应沿用的服务端 2.14.6 / 3.5.15。nats.go 仍为仓库锁定的 v1.53.1；本轮不更新依赖，也不重新断言它是当前最新版。

## 驱动改动与统计方法

- 增加共同计划起点和各端实际起止时间；各端预分配 worker 样本后等待计划时间。聚合吞吐为成功完成总数除以共同窗口，窗口按各端实际起点偏移加单调时钟耗时取最大值，不能相加三个不同时间段的峰值。
- 复用原驱动已经收集的成功请求样本。各端 RPC 结束后先完成所有资源快照，再通过独立 `samples` 命令导出、合并并计算精确 P50/P99；不平均各端 P99。失败与未发送请求单列。
- 固定到达率按每端 2000/6000/10000 次/s 调度，即总计 6000/18000/30000 次/s；每端调度队列容量为 16。计划到达 P99 包含生成器晚点、该队列等待及 RPC，仅针对最终成功请求。队列满时计入未发送数；不是 NATS 已接受消息丢失，也不能用成功样本的低延迟掩盖负载未送达。
- 每例预热、显式 GC 后采样 4 秒，四种布置交替进行五轮。表中为五轮中位数，范围保留在原始材料；短窗口不是长期稳定性或生产容量承诺。
- CPU 汇总六业务进程与全部依赖容器；Go 分配只含业务进程，不含 broker/etcd。调用端 CPU/分配覆盖运行窗口内 worker 与样本追加，开始前预分配、结束后的样本归并/排序和 JSON 导出不在该窗口。目标与依赖取前后快照，包含控制采样的少量开销，时间边界并非完全一致；每完成 RPC 成本只作同口径近似比较。
- RSS 为预热/GC 后全部容器驻留快照，包含运行时保留堆和前序负载影响，不是峰值或单 Actor 内存。全部三 broker 资源都计入，空闲依赖也保留在各自对照中。

材料目录：`/private/tmp/tx-nats-aggregate-20260912`。保留测试二进制、源码/脚本 SHA256、镜像与容器配置、各轮路由/连接快照、完整计数、压缩原始样本、汇总脚本和验证日志。`aggregate.py selfcheck` 用样本数悬殊的两端验证合并 P99 与共同窗口，Go 自检验证起点、成功样本及计数守恒。所有采集入口仅在 `_test.go` 或临时目录。

## 闭环聚合结果

请求和响应的业务载荷各为表中的字节数，不含信封。以下均为五轮中位数。

| 布置 | 载荷 | 完成 RPC/s | P99 ms | 总 CPU μs/完成 RPC | RSS MiB |
|---|---:|---:|---:|---:|---:|
| ProtoActor | 128 | 29,060 | 3.48 | 275.3 | 322.6 |
| 单 broker | 128 | 19,769 | 5.18 | 368.8 | 266.2 |
| 三 broker，就近 | 128 | 14,749 | 7.52 | 547.4 | 312.6 |
| 三 broker，跨节点 | 128 | 11,758 | 8.52 | 621.4 | 318.6 |
| ProtoActor | 1024 | 25,443 | 4.79 | 353.0 | 470.1 |
| 单 broker | 1024 | 16,276 | 7.01 | 483.5 | 353.5 |
| 三 broker，就近 | 1024 | 13,592 | 8.53 | 626.9 | 396.9 |
| 三 broker，跨节点 | 1024 | 10,347 | 9.63 | 781.0 | 403.3 |

128B 下，单 broker 相对 ProtoActor 中位吞吐低 32.0%，P99 高 48.8%，总 CPU/完成 RPC 高 34.0%；三 broker 就近/跨节点的吞吐分别低 49.2% / 59.5%。1KiB 的排序一致。

五轮 128B 吞吐范围：ProtoActor 2.52～3.18 万次/s，单 broker 1.76～2.57 万，就近三节点 1.18～1.61 万，跨节点 0.97～1.19 万。ProtoActor 与单 broker 的范围略有重叠，不能把中位差当作每轮固定倍率；按轮配对，单 broker 有四轮吞吐低超过 10%，两种三节点布置五轮均超过。既定筛选线仍未达到，不因此修改 T4 门槛。

这说明本机部署中，增加 broker 并分摊三组连接没有带来反超；不能据此断言增加独立主机、带宽及 CPU 后 NATS 聚合容量不会增长。这里没有一对与三对的同批对照，也不能把本轮数值与上一批相减来计算业务实例扩容倍率。

## 业务预算输入（待确认的假设）

以下是为了选择下一轮代表业务的工程估计，不是来自线上采样、行业标准或已通过的 SLA。流量估算为“同时活跃玩家 × 每秒需服务端处理的动作 × 每个动作的跨实例 RPC 数”，本地 Actor 调用不乘入；广播扇出、后台任务、真实 GD 操作和热点世界还需另外计入。

| 假设场景 | 平均负载估算 | 突发验证点 | 候选延迟预算 |
|---|---|---|---|
| SLG 摄像机与操作 | 1000 × 2 × 3 = 6000 RPC/s | 3 倍，即 18000 RPC/s | 单跳 RPC P99 ≤10ms；通信链整体另测 ≤30ms |
| 高频战斗指令 | 1000 × 10 × 3 = 30000 RPC/s | 2 倍，即 60000 RPC/s，本批未测 | 假设 20Hz/50ms 逻辑帧，通信链先分配 10ms；单跳候选 P99 ≤3ms |

单跳 P99 不能直接相加得到链路 P99，以上整链预算必须用实际调用链测量。候选预算若调整，须同时给出游戏节奏与调用链成本的理由，不能为通过某个候选库而放宽数字。

资源预算先按“实测总 CPU 秒 / 完成数 × 目标 RPC/s”估算通信所需核数，再给突发和真实业务留余量；不同到达率下的成本不恒定，不把闭环最低成本直接套入低负载。内存按业务实体规模、载荷及保留堆另估，本批 Echo 的 RSS 不代表 SLG 世界内存。任何存在未发送负载的点都不能以其成功请求 P99 宣称满足完整负载预算。

本批没有扫描最大实体数、单世界热点、真实 GD/Procedure、跨宿主网络或长时间稳定性。就算某个 Echo 点满足候选预算，也只能决定是否值得进入代表业务验证，不能提前确认正式迁移。

## 收尾核验与限制

- 8 个试跑、100 个正式窗口，共 5,929,473 次完整校验成功 RPC，其中正式批次 5,880,339 次；RPC 返回错误为 0。正式固定到达率窗口的未发送总数 1,234,725，单列而不算作成功。
- 共同实际起点最大偏差 4.878ms。独立核验发现 324 个调用端窗口中有 9 个墙上时间耗时与 Go 单调时钟耗时相差超过 1ms，最大约 2.205ms；原聚合吞吐误差最大约 0.0551%。增加时钟前跳自检后，用“相对最早起点的偏移 + 已保存的单调耗时”重算全部共同窗口，原始样本、计数和延迟无需重采。原结果/脚本保留，修正结果为 `corrected-results.jsonl`，两组 SHA256 清单分别保留；本报告只使用修正结果。该方法限于当前共享时钟的同 VM 进程，多机需另定对时与窗口口径。
- 全部压缩样本由独立有序归并再次计算 P50/P99，计数守恒、共同窗口、源码/二进制 SHA256 核验通过。调用延迟本来就用 Go 单调时钟，本次修正未改变延迟分位数或选型结论。
- 显式启用原型 NATS/etcd/Redis 后，tx 全量 `go test -mod=readonly ./... -count=1`：1158 pass、40 skip、0 fail。40 个跳过项包括独立压测进程入口及未显式启用的其他外部依赖测试，不表示所有集成入口已验收。
- `go test -mod=readonly -race ./internal/actortrial -count=1`：48 pass、1 个独立压测进程入口 skip、0 fail，无 race；不代表正式 ProtoActor Provider 完整关闭路径已通过 race。

## 下一项与决策

T3b 初评曾建议保留正式 ProtoActor RPC、独立评估 JetStream。后续讨论指出，本批测的是完整原型，缺少官方 SDK 和协议封装的分层基线，直接据此收缩 Core 试验尚早。用户已授权 T3c：保持当前语义及门槛，先定位 SDK、协议等待与实体调度的成本，再决定是否值得进一步调整。

本批实测数据保持有效；同机三节点没有反超不代表独立机器的扩容上限。T4 仍暂停，T5 尚未实施，不自动删除 feature 原型、高级 SPI、etcd 或 msgq。可靠任务继续遵守“业务执行后 ACK、永久加载拒绝转死信、未知结果不建完成表”的既定边界；正式 GD、生命周期接线另行验收。
