# Prometheus 指标接入后的四机上下行回测

## 条件与口径

2026-09-27 至 28 日使用四台腾讯云 SA9 8 核 16 GiB：接入机 Agent×1（P8）、Login×2（P4）；存储机 MsgQ×2（P4）及测试中间件；游戏机 Game×2（P4）；独立客户端机。每轮停止七个业务进程、重置专用夹具并创建 10,000 个角色。客户端均为同一版 TCP 压测程序，16 个 worker、500 连接/s、`max-in-flight=4`、2 秒预热、180 秒正式窗口。10/10 每条 Ping 产生一条下行；10/50 额外产生四条下行。

正式新版本三台服务机使用相同二进制，SHA-256 `e9f09c12640657d69bb5d07e083c5b584c5bd85e89cbc135ee9946ab0cf784fe`。每进程独立监听回环 `/metrics`，每约 5 秒抓取一次；正式轮没有启用 pprof 或逐消息 JSONL 诊断。“最终完整上行”包含测量截止后完成的请求，“窗口完整上行”扣除这部分请求；P99 使用客户端已完成请求的延迟样本。当前验收线是最终完整处理率至少 99.99%，10/50 的 P99 目标为 60 ms，窗口吞吐另行报告。

## 分段观测

稳定区间内，新版有抓取的 10/10 轮 Agent 约用 5.72 核，两台 MsgQ 合计 2.67 核，两台 Game 合计 3.10 核；接入宿主机平均空闲 23.6%。10/50 轮分别升至 7.59、3.85、4.06 核；接入与客户端宿主机平均空闲仅 3.82% 和 3.57%，存储与游戏机仍分别空闲约 48.6% 和 49.3%。四台机器的 `steal` 采样最大值均为 0。无抓取轮接入与客户端空闲均约 4%；旧版轮约为 6.1% 和 1.8%。这证明 10/50 下 Agent 与客户端发生器同时接近当前宿主机容量边界，不能仅凭端到端 P99 把长尾归到某一个服务。

新版有抓取轮的 Agent 上行分派直方图 P99 从 10/10 的约 18.1 ms 增至 10/50 的约 76.8 ms；这段包含目标解析与写入目标流，并非 Game 业务执行耗时。Agent 单次下行 Socket 写入直方图 P99 约 0.173 ms，写入失败为 0。Game 入 Actor 邮箱及 MsgQ 角色下行入队的分段 P99 均约 0.01 ms，相关错误计数为 0。MsgQ 两实例的未确认下行数在 10/50 中瞬时最高约 7.6 万与 9.3 万；该 Gauge 包含已投递但未被客户端 ACK 的消息，不能直接当成未发送积压或等待时长。指标直方图的 P99 是按固定 bucket 对采样期间增量插值得到的估计值，不等同于客户端精确分位数。

关闭抓取后单轮 P99 和未发送数降低，但 Agent 与客户端仍接近满载；旧版单轮反而更差。高压边界的轮次波动、旧版通信与配置差异以及双端同时饱和，使这些单轮结果不足以证明 Prometheus 抓取或埋点本身造成了多少开销。新增指标能低频观测失败、分段耗时、CPU 和邮箱规模；不应据此反复微调合写帧数或宣称 10/50 达标。

## 接续

下一轮先在**客户端发生器与 Agent 都未满载**的负载点，固定同一客户端程序和服务二进制，做有抓取/无抓取的交错短轮，单独量化观测开销。随后在 10/50 目标负载用独立客户端容量或分离的发生器验证服务端上限，并对 Agent 下行出队、编码及 TCP 写出做短时 CPU 画像；保留业务真实 TCP 链路，不用更多盲目速率档搜索代替定位。若同一 Agent 仍接近 8 核，再依据画像选择代码优化或水平扩展。此处尚未决定新增云主机或改动链路实现。
