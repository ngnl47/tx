## 长测失败与下一项

本轮600秒测试的两个客户端工作进程均报告`AgentClient 尚未连接`，正式planned/attempted/completed均为0。10:41:08形成准备屏障、10:41:31放行，但Agent已经在10:38:05～10:38:12记录347条新连接关闭；MsgQ同时间段记录`msgq terminate dead sessions failed`及`session has changed`。不能将该失败归因于600秒负载或20k/s吞吐上限。

当前客户端准备保活只向connected端点发送Ping，因此连接静默关闭后可能到预热才暴露，ready中10000个身份也不能证明放行时仍有10000条活连接。该事实与服务端关闭原因需分别处理。日志中的TCP i/o timeout也可能是session上下文取消后的读唤醒结果，不能直接判定网络超时。

下一项明确：先复现并定位**多轮重登录后、建连期的MsgQ归属续期/会话失效与Agent断连**，核对旧新代际及首次服务端错误；同时让准备屏障及时报告已断连接，不通过自动重连、扩大超时或清库掩盖问题。故障排除后重新建立短测基线，再跑20k/s十分钟；此前不继续更高频率。

本轮短测证明20k/s完整Ping闭环可完成，尚不代表稳定容量。相对最初SLG万连×10/s目标仅验证到20%的短时速率；MMO万连×20/s仅10%，下行广播负载、Core NATS和JetStream容量均不能外推。
