# 万连 10 上行 / 50 下行回测

## 条件与口径

2026-09-27 沿用[不对称下行回测](2026-09-27-asymmetric-downlink.md)的四台腾讯云 SA9 8 核 16 GiB 布局：接入机 Agent×1（P8）、Login×2（P4）；存储机 MsgQ×2（P4）及测试中间件；游戏机 Game×2（P4）；独立客户端机。10,000 个 TCP Session 经 Login、Agent 和正式 `System_Ping` 业务链路，每个 Session 每秒计划发送 10 条 Ping；Game 对每条 Ping 发送 1 条 Pong 和 4 条 `GlobalNotify`，构成计划的 10/50 上下行。客户端使用 16 个 worker、`max-in-flight=4`、2 秒预热和 180 秒正式窗口。业务服务使用同一个 `txbench` 二进制，SHA-256 为 `74588af334afe80f9c58ac960985285d524da84c0643ec0bdd5fe2e1bdedaaef`。

为固定下行比例，Game 的压测入口增加 `TXBENCH_PING_EXTRA_DOWN_COUNT=4`，客户端增加 `--extra-down-count 4` 及对应计数校验。两项均只服务于本轮压测，生产通信路径未为此改变。100 Session、10 秒冒烟完整处理 10,000 次上行和 50,000 条下行，失败 0，P99 0.530 ms。正式轮前停止七个业务单元并重置有归属标记的专用夹具，重新创建 10,000 个角色及 Session。

本轮未达到当前完整处理率 ≥99.99%、P99 ≤60 ms 的验收线。已发送的请求全部完成，`failed=0`；13,984 条未发送中，13,459 条为客户端调度跳过、525 条为窗口结束时待发槽位；其中 29 次跳过发生在容量等待后。3,632 条上行及对应 18,160 条下行在正式窗口结束后完成，已从窗口吞吐扣除。这个结果说明当前布局完整接收并处理了约 9.99 万上行/s、49.95 万下行/s，同时暴露客户端调度和尾延迟问题；不能把未发送解释为服务端丢消息，也不能称为 10/50 达标。

正式轮的 `pidstat` 平均值：Agent 约 6.47 核，两个 Game 合计约 4.13 核，两个 MsgQ 合计约 3.30 核；接入、游戏、存储宿主机平均空闲分别约 17.41%、47.77%、55.42%，`steal` 最大值均为 0。16 个客户端 worker 的事件循环利用率为 88.57%–90.36%，事件循环 P99 停顿为 68.75–90.96 ms。28.1 万条抽样延迟记录的 `toHandler` P99 为 62 ms、`fromHandler` P99 为 125 ms；这两个字段用跨机器墙钟计算，仅作诊断线索，不能当作精确的服务端分段延迟。

## 单变量对照与 Agent 画像

保持四机服务配置、10,000 Session 和 10/50 业务不变，只将客户端改为 32 worker，执行 60 秒短轮：计划上行 6,000,000，完整上行 5,925,581（98.75968%），下行 29,627,905，未发送 74,419，失败 0，P99 435.587 ms。32 个 worker 的事件循环 P99 停顿升至 155.06–224.00 ms，出现大量容量等待。这轮窗口较短，仅用于排除“增加 worker 就能消除长尾”的简单解释；它不提供与正式 180 秒轮相同口径的容量结论。

随后恢复 16 worker，在 Agent 上单独启用绑定 `127.0.0.1` 的 pprof，执行 60 秒诊断轮并采 30 秒 CPU。该轮因画像扰动，完整上行 5,939,500、P99 531.851 ms，不与无画像轮直接比较吞吐。CPU 样本累计 217.25 秒，约为 7.24 核。累计调用栈占比中，`writeDownMsgs` 为 33.27%，其中 TCP 批帧写出 `writeTCPDownBatch` 为 18.16%、单帧写出 `writeDownMsg` 为 7.09%；`grpcMailboxStream.readLoop` 为 15.66%，`dispatchUpMsg` 为 15.60%，`tcpTransport.Read` 为 16.32%。这些调用栈相互嵌套，比例不能相加；`writeDownMsgs` 包括取消息、编码和 Socket 写出，不能仅凭它判定 MsgQ 或网络是唯一瓶颈。两次短轮各自使用重置后的专用夹具。

本轮可确定 Agent 下行写出有显著 CPU 成本，且客户端发生器在 10/50 下也出现调度压力。下一项应先计数 Agent 同会话下行出队时实际已有的帧数，再以相同 16-worker、10/50 短轮对照当前最多 3 帧与最多 5 帧合写的 Agent CPU、写出次数和端到端延迟；只有排队中确有第 4、5 帧时，提高合写上限才有收益依据。若客户端事件循环仍先于服务端成为限制，应单独优化或拆分发生器，不能把客户端调度跳过归因于 tx 服务端。
