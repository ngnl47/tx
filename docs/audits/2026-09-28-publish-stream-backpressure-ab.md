# Game→MsgQ 下行发布流回测

六机拓扑：两台 Agent 各一进程 P8；一台 Game 上两个进程各 P4；一台 MsgQ 上两个进程各 P4；两台客户端各建立 5000 条 TCP 会话。每会话计划每秒 20 条上行，`System_Ping` 平均产生 50 条下行；每轮正式窗口 180 秒。三轮都重置同一专用夹具，Agent、MsgQ、Login 使用相同二进制和配置，只切换 Game 的 `PublishStream` 实现。各轮服务启动、角色准备和客户端连接完成后才开始窗口。客户端、服务指标和脚本保存在 `tx-artifacts/cloud-20260928-publish-ab/`。

基线和修复版的已发送请求失败数均为 0。修复版两台客户端分别完成 44,961,580 和 44,999,959 条下行；基线分别为 44,923,842 和 44,952,822 条。合计未发送上行从 49,378 降到 15,439，其中修复版客户端 A 为 15,421、客户端 B 为 18。未发送是客户端错过计划时隙，不是已发送命令失败。按先前 99.99% 的计划完成率标准，本轮**仍未达标**；不能把客户端 B 单独通过视为整套拓扑通过。

Game 侧 1/64 抽样直方图的 P99 桶上界，Actor 邮箱等待由 20 ms 降到 10 ms，发布流本地队列等待也由 20 ms 降到 10 ms。两台 Game 的 `process_cpu_seconds_total` 增量合计由 1185.48 降到 1097.58 秒；两台 Agent 由 2340.74 降到 2243.70 秒；两台 MsgQ 由 978.86 降到 953.02 秒。这里只各有一个三分钟窗口，进程 CPU 和延时差异可能含运行波动，不能据此推算线性扩容收益。MsgQ 仍用旧版二进制，部分新指标未暴露；不把缺失指标解释为零耗时。

首版的 256 项队列在高并发突发时被占满，一台 Game 的 `tx_msgq_publish_stream_errors_total` 增加 874，日志明确为 `msgq: publish stream queue is full`；Pong 缺失使两个客户端在预热或窗口中因等待超时退出。修复只调整满队列分支：有空位时仍在本地入队后立即返回；满时等待空位，受调用方 Context 和流关闭约束；不等待 gRPC `Send` 结果，也不扩容为无界队列。MsgQ/指标包 `go test -race` 已通过，修复版完整云端窗口未出现发布流错误。

Game 基线构建 SHA-256 为 `19c0c6aa1ae403c9a58cb4f239824c9eeeeb2c14bdff7149bc0c2535633948ff`，修复版构建 SHA-256 为 `35414337db19c4721027806112b33633c5d1c986930730dfcd37f71e5f8d0687`。修复版使用 `-ldflags='-s -w'` 缩小公网传输包；此差异删除调试符号，不改变业务实现。基线覆盖源保存在上述工件目录，修复版为当前工作区源码。

结果说明下行发布路径的逐条等待有可观成本，但剩余未发送主要集中在客户端 A：八个 worker 分别未发送 304–3756 条，客户端 B 的八个 worker 则各为 0–9 条。这是客户端主机或其链路值得优先排查的线索，尚不能据此排除服务端差异。下一轮应先定位客户端 A 的计划时隙、事件循环和读取调度，再判断服务端是否还有需要优化的队列；不以继续增加 Agent 数量代替这个归因。回测结束后，八个业务进程均已停止，专用夹具已执行 `cleanup`；中间件容器保留。
