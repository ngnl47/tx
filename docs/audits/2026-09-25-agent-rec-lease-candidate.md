# Agent 上行游标受控候选

## 目标与开关

试验只比较 Agent→MsgQ 上行 `Rec` 从逐条同步转为 Agent 本地游标、定期检查点后的完整链路收益。`ServerOptions.RecLeaseInterval` 默认零值，现有逐条 `Rec` 路径不变。txgame 的 `services.agent.recLeaseInterval` 是试验开关；不修改 MsgQ 下行邮箱、`StreamFetch`、Game 下行发布或客户端协议。此候选尚不是可跨 Agent 实例转移的分布式租约。

启用后，Agent 在业务分派前接受严格递增的上行 Seq，旧号跳过；只有业务分派完成才通过客户端帧确认处理进度。客户端的下行 Ack 先留在本地，周期检查点把当前最大 Seq/Ack 一次写入 MsgQ；纯空闲连接用 `Confirm` 保活。连接结束时使用独立收尾 Context 写回。同一 Agent 上恢复原 Session 时，先关闭旧连接并等待其业务和收尾结束，再由 MsgQ `Init` 重绑新 ConnectionID。正常排水先关闭业务准入，等待已接受的处理完成，然后写回全部在线游标，失败即让排水报错而不继续释放资源。

## 安全范围

本候选只用于固定 Agent 目标的受控压测：旧实例停止后才允许新实例使用同一地址恢复；不得在两个运行中的 Agent 之间并发恢复同一 Session。因为 MsgQ 目前没有授予 Agent 独占、可撤销的游标租约，远端并发 `Init` 改绑后，旧 Agent 在下一次检查点失败前仍可能分派业务。进程意外消失也可能让 MsgQ 检查点落后于客户端已见的处理 Ack；当前参考客户端会拒绝回退的 `Ready.Ack`。这两个边界必须在默认启用前另行解决，不能用本轮吞吐结果冲淡。

## 本地验证与云端对照口径

本地测试固定：两个上行帧只在断线时合为一次 `Rec`；跳号和旧号不会重复业务分派；排水写回后关闭连接不会重复调用 `Rec`；新连接的 `Ready` 等旧连接检查点完成后才发；默认路径原有故障边界仍通过。tx 与 txgame/server 全量测试已通过，候选恢复/排水测试的 `-race` 复测通过；网络集成测试在允许 loopback 绑定的环境执行。

云端同版 A/B 使用 SHA-256 `addd962c47d7b0143fc880de3e54516506a9a5d1b91f6288251f8a245b6ce636` 的同一候选二进制，仅切换两台 Agent 的 YAML 开关。两台 Agent 各 1×P8，Login、MsgQ、Game 各 2×P4；客户端为 8 个进程，万连×10/s、1:1、每档 3 分钟。各档先通过 100 会话×1/s、15 秒冒烟，1500/1500 完成，零失败/未发送。正式结果：

| 档位 | 上下行各完成 | 完成吞吐 | 未发送 | 处理失败 | P50 / P95 / P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 关闭，逐条 `Rec` | 17,874,292 | 99,302/s | 125,708 | 0 | 47.90 / 133.66 / 201.11 ms |
| 开启，1 秒检查点 | 17,931,582 | 99,620/s | 68,418 | 0 | 32.59 / 122.05 / 213.57 ms |

按两档采样窗口中段各 160 秒的 `pidstat`，Agent A/C 的平均 CPU 从 639.5%/643.8% 降至 525.0%/531.3%，约下降 18%；MsgQ A/B 从 262.0%/261.2% 降至 188.6%/188.3%，约下降 28%；Game A/B 仍约占 3.5 核。完成吞吐只提高约 0.32%，P99 反而高约 12.46 ms。单轮差异不能证明未发送减少是候选造成的；客户端仍未完整供给计划流量。CPU 下降说明逐条 `Rec` 有实际成本，但此配置的总吞吐和尾延迟没有获得足以抵消状态交接风险的改善。因此保持默认关闭，不把候选作为生产租约发布。

原始客户端报告和四主机每秒系统采样保存在工程外 `tx-artifacts/cloud-20260925-agent-scale/lease-{baseline,on}-10ps-3m/`。两档结束后 Redis 测试角色归属均清零，Agent 已恢复为同版二进制、原 YAML（开关关闭）的运行配置。云端没有直接采集 `Rec` 调用次数；少调用的断言来自本地计数测试，CPU 是完整链路实测。带活跃连接的云端排水故障注入、跨实例并发恢复和意外进程退出均未验收。

## 固有延迟与排队复核

停止继续搜索速率阈值后，复核了留在客户端云主机的本轮八个 worker 的 `.timings.json`。同版二进制的 100 会话×1/s 冒烟全链路 P50/P99 为 0.725/1.058 ms；10,000 会话×10/s 时，关闭候选的全链路 P50/P99 为 47.90/201.11 ms。两档的通信跳数和 Ping/Pong 业务路径相同，因此高负载增加的几十至上百毫秒不能解释为不随负载变化的网络传播或固定 RPC 往返时间。

`System_Ping` 的 `serverTime` 在 Game Handler 内生成，早于 Game 向 MsgQ 发布 Pong。客户端每 64 次尝试抽样一次；前段包括客户端发送、Agent 的 `Rec` 与 Actor 调用、到达 Game Handler，后段包括 Game 发布、MsgQ 下行、Agent 写入与客户端调度。两台主机当前均显示 NTP 已同步，抽样中关闭候选仅 2 个负时钟样本、开启候选为 0；这不足以证明测量当时的跨机时钟误差为零，故分段只用于定位量级，不把分位数相加或相减。

| 开关 | 抽样数 | 前段 P50/P95/P99 | 后段 P50/P95/P99 | 客户端事件循环利用率 / P99 停顿 | 客户端宿主 CPU 空闲 |
| --- | ---: | ---: | ---: | --- | ---: |
| 关闭 | 279,291 | 23/64/105 ms | 20/95/161 ms | 90.1%–90.4% / 101–108 ms | 8.9% |
| 开启 | 280,185 | 15/58/148 ms | 14/73/138 ms | 86.8%–87.6% / 78–85 ms | 12.0% |

客户端宿主 CPU 取对应正式开始后第 10～169 秒的 160 个 `vmstat` 样本均值；关闭候选时 user/system/idle 为 56.3%/34.8%/8.9%，开启时为 56.4%/31.5%/12.0%。因此“CPU 没打满”只适用于部分服务宿主机，不能概括客户端发压机与接近 P4 的 Game 进程。

关闭候选时的 `notSent=125,708` 中，固定时间轴诊断记录 `skippedSlots=125,507`、窗口结束待发 201；开启时分别为 66,927 和 1,491，合计 68,418。该计数只能证明客户端未按计划投递，不能单凭它区分本地事件循环迟到和服务端响应占满每 Session 四条在途的影响。现有数据也不能把前段长尾唯一归给 `Rec`，或把后段长尾唯一归给 MsgQ：Game 两个 P4 进程在窗口中各占约 3.5 核，已接近各自可并行执行的 4 核预算；按合计约 7 核和约 99,300 次完成/s 粗算，每次 Ping 在 Game 进程上消耗约 70 µs CPU。代码中的 `commandActor.execute` 必须等 `completeAgent` 同步 `PubRole` 成功才释放当前 Actor 邮箱处理；Game 的 20 秒 CPU 画像约四分之一累计样本位于这条发布调用栈。这定位出一个每次 Ping 必经、会把 MsgQ 发布等待传回 Game 邮箱的结构性成本，但累计 CPU 样本不是纯 `PubRole` 独占 CPU，也不能推导 RPC 等待时间或证明其是唯一瓶颈。`Rec` 候选减少 Agent/MsgQ CPU 却几乎不增加吞吐，进一步说明逐条 `Rec` 并非此档唯一主导限制。

结论是**固定传播延迟假设未获支持**；固定的逐消息 CPU 成本仍可能通过接近 P4 的 Game 产生排队，尤其要先核对同步 `PubRole` 等待；负载相关等待同时出现在 Game 生成响应前后。下一次诊断应固定万连 10/s、三分钟以内的同一负载，只采集客户端调度迟到与在途满等待的独立计数，以及 Game `PubRole` 调用端和 MsgQ 接收端的同进程单调时钟分段；若该段不足以解释长尾，再展开 Agent `Rec`/Actor Call 与 MsgQ 下行推送。只做定位，不用开启采集时的吞吐量替代关闭采集的容量结果。现有 `txbench` gRPC Binary Log 曾在旧拓扑显著扰动吞吐，不能直接把其样本当作当前生产延迟。

## 同负载时间分段复核

继续固定 10,000 个 TCP Session、每 Session 10/s、每次 Ping 对应一个 Pong、最多四条在途。只在 `txclient` 显式阶段诊断中增加在途满等待次数、等待耗时和等待后错过的计划槽位计数；不改变生产服务的协议、Actor 邮箱或确认语义。诊断构建复用已有无正文 gRPC Binary Log Sink，仅在独立短轮采集同进程单调时钟耗时。样本分位数不能相加或相减为单次消息的其他分段；跨机 `serverTime` 仅用于近似划分 Game Handler 前后。

第一次启用 Game/MsgQ 采样后，建连阶段发现 1,024 个 role 测试分区仍指向已退出的 Game 实例，未进入测量；全部接入与 Game 测试进程停止、Redis 角色归属为零后，备份并仅删除专用 `/tx/e2e/txgame/discovery/slots/actor-v1.cm9sZQ.p` 前缀，再冷分配。随后 100 会话×1/s 冒烟完成 1,500/1,500 条，零失败和未发送。该环境修复不计入容量或性能收益。

| 窗口 | 正式时长 | 完成/计划 | 未发送 | P50/P99 | 客户端到 Handler P50/P99 | Handler 到客户端 P50/P99 |
| --- | ---: | ---: | ---: | --- | --- | --- |
| Game/MsgQ Binary Log | 90 s | 8,199,065/9,000,000 | 800,935 | 431/605 ms | 389/504 ms | 39/207 ms |
| Agent/Game/MsgQ Binary Log | 60 s | 5,467,056/6,000,000 | 532,944 | 431/610 ms | 387/496 ms | 40/211 ms |
| 服务端无 Binary Log | 60 s | 5,941,317/6,000,000 | 58,683 | 45/207 ms | 23/134 ms | 18/166 ms |

三轮均零处理失败，下行完成数等于上行完成数；有未发送，不能称为 10/s 容量达标。前两轮的 gRPC Binary Log 显著改变了负载和等待形态：只采 Game/MsgQ 时 796,324 个错过的计划槽位中，760,277 个紧随在途满等待；加采 Agent 时分别为 528,714 和 491,234。**无 Binary Log 时仅有 14 次在途满等待、总计约 584 ms；57,694 个错过的槽位没有紧随在途满等待，另有窗口末尾待发 989 个。**因此采样轮的“在途窗口是主瓶颈”推论对正常链路不成立。无采样客户端八个 worker 的事件循环利用率为 86.5%–87.4%，P99 停顿为 84–97 ms；客户端宿主同 60 秒 `vmstat` 平均 user/system/idle 为 56.8%/32.0%/11.2%。漏发更符合发生器调度迟到，不能归咎于 Agent 连接处理池过小。

采样轮仍可用于识别必须经过的调用及其在受扰动状态下的等待位置：两台 Agent 的 `Rec` 调用端 P50/P95 约 12/47–48 ms，Actor `Call` 调用端约 91–93/146–149 ms；Game 的 `Call` 服务端约 49/111 ms，Game→MsgQ `PubRole` 调用端约 37/93 ms，MsgQ `PubRole` 服务端约 0.015/38 ms，MsgQ `Rec` 服务端约 0.009/0.017 ms。`Agent` 每 TCP 连接一个处理循环，同连接 `Read → Rec → Actor Call → FrameAck` 串行；没有跨所有连接的固定业务协程池。Binary Log 下同步等待超过单会话 100 ms 的计划间隔，后续请求才会在该连接上积压；这解释了采样轮约 91k/s 与大段 Handler 前等待，但**不证明无采样链路具有相同的逐条等待**。

无采样正式轮，Agent 两台 P8 进程分别平均使用约 6.31/6.43 核；MsgQ 两台 P4 各约 2.64/2.63 核；Game 两台 P4 各约 3.40/3.39 核。Game 宿主平均空闲 14.4%，两台 Agent 宿主分别空闲 19.2%/17.7%，客户端空闲 11.2%。这些 CPU 数据和 Handler 前/后都增长的时延，提示多个阶段同时接近并行预算，不能从整机尚有空闲推断链路存在单个固定 RTT 上限。无采样 P99 仍约 207 ms，但现有跨机时间戳与全量 gRPC Binary Log 都不足以无扰动地将它唯一归给 Agent、Game、MsgQ 或客户端回调；下一次应先减轻客户端发生器的定时调度成本或分机供给，再用低扰动手段采集同一请求的阶段时间。

原始报告与四机系统采样位于工程外 `tx-artifacts/cloud-20260925-agent-scale/stage-time-{main,agent-main,untraced-main}-20260925/`；采样 JSONL 和离线汇总脚本在 `stage-time-main-20260925/` 与云测试机的 `stage-time-20260925/`。所有采样环境已撤销，服务恢复为两台 Agent 原候选二进制 P8、Login/MsgQ/Game 各两台 P4，客户端云端夹具已恢复原 SHA，Redis 测试角色归属为零。恢复期间专用 Redis 曾意外处于指向外部不可达地址的只读副本状态；保存故障前 `INFO replication` 后执行 `REPLICAOF NO ONE`，并在测试机 `DOCKER-USER` 链仅阻断非 VPC 来源对容器 6379 的访问。其来源未确定，这次无采样正式轮在 Redis 恢复且 100 会话冒烟通过之后运行；测试机防火墙规则属于临时运行状态，重启后须重新核对。

## Mac 同机定位（云实例退还后）

只比较本机同负载的定位结果，不外推为云端容量。内存替身保留真实 `txclient` 发压循环、Seq/Ack 与 Ping/Pong 编解码；8 个 worker 各 1,250 会话×10/s、30 秒合计完成 2,999,980/3,000,000 次，20 条未发送均为截止边界待发，中途跳槽和在途满等待均为零。单 worker 的真实回环 TCP 替身完成 374,985/375,000 次，中途跳槽和在途等待仍为零，P99 约 2.14ms。这表明本机单靠每会话定时器或 TCP 客户端处理不足以复现正式链路的长尾；替身没有 Game、MsgQ 或跨进程 gRPC。

正式 `cluster-perf` 使用专用 Redis DB12、Mongo 测试库与 etcd 前缀，Login/Agent/MsgQ/Game 各两个进程，每进程 P2，两个 Node 客户端 worker；固定每会话 10/s、1:1 Ping/Pong、30 秒。该编排默认每会话**一条**在途，不能与云端四条在途样本直接比较。首次运行在 100 会话请求完成后遇到严格 JSON 解码不识别新客户端 `maxInFlight` 字段；同步 Go 结果结构和单在途校验后重跑。100 会话档 30,000/30,000 次完成，零失败/未发送，P99 1.49ms。

| 1,250 会话布局 | 完成/计划 | 未发送 | P99 | 两 worker 的 Handler 前 P99 | Handler 后 P99 | 事件循环利用率 |
| --- | ---: | ---: | ---: | --- | --- | --- |
| Agent、MsgQ 分进程，首轮 | 372,681/375,000 | 2,319 | 140.34ms | 67/73ms | 78/92ms | 89.8%/89.8% |
| Agent+MsgQ 合进程 | 373,507/375,000 | 1,493 | 约 70–72ms | 8/9ms | 67/70ms | 85.3%/85.0% |
| Agent、MsgQ 分进程，复轮 | 373,536/375,000 | 1,464 | 115.19ms | 56/51ms | 65/64ms | 86.7%/86.0% |

三轮均零业务失败、上下行完成数相等、在途满等待为零。未发送主要是固定计划的中途跳槽；复轮另有 152 条窗口边界待发。抽样使用同机墙钟，前后分位数不能相加为单请求 P99。合部署在同一总 GOMAXPROCS 预算下减少 Agent↔MsgQ 跨进程调用，同时也减少进程数并改变调度，故显著缩短 Handler 前长尾是**定位线索**，不能把全部约 40–70ms 差异归因于单次 `Rec` 网络 RTT。Handler 后仍有约 64–92ms P99，不能只优化上行。

另一次分进程 45 秒窗口对 Agent、Game、MsgQ 两实例分别并发采集 20 秒 CPU pprof；该轮完成 560,398/562,500 次，P99 116.77ms，采集开销和窗口长度不同，不用于严格 A/B。两 Agent 的 `syscall.rawsyscalln` 占 CPU 样本约 71.9%/72.3%，两 Game 为 55.6%/56.0%，两 MsgQ 为 59.0%/59.8%；调用栈主要可追到 Agent TCP 读写及 gRPC HTTP/2 读写。该结果指向 Mac 同机大量小消息的系统调用和调度成本，而非业务 Handler 计算占主导；它也不能证明 Linux 云端有同一占比。已有云端游标候选虽显著降低 Agent/MsgQ CPU，却未提升完成吞吐，因此不据此默认开启候选或改变 Seq/Ack 契约。

本轮原始结果、临时内存/TCP 替身和 pprof 位于工程外 `tx-artifacts/mac-stage-time-20260925/`。各轮退出后核对专用 Redis DB12 为零键、etcd `/tx/e2e/txgame/` 前缀为空。下一次若继续压缩长尾，应在**同一请求**上低扰动采集 Agent `Rec`、Actor Call、Game `PubRole` 与下行到达的单调时钟耗时，并保持默认关闭；不再用全量 gRPC Binary Log 的受扰动结果代替正常链路。云实例已退还，本轮不执行云端测试。
