# 腾讯云 Linux 上下行容量基线

## 部署边界

本轮为用户授权的临时单机压测环境。8 vCPU、16GiB、50GiB增强型SSD，腾讯云标准型SA9；来宾系统显示AMD EPYC 9K65、4核×2线程，不能把8 vCPU解释为8个独占物理核。Ubuntu 24.04.4 LTS，Linux 6.8.0-124-generic。

- Docker部署Redis 8.8.0、MongoDB 8.0.26、etcd 3.5.15、NATS 2.14.6，容器健康检查通过；端口仅映射127.0.0.1，数据使用Docker卷。
- NATS开启JetStream，复用`deploy/task-demo/nats.conf`，64MB内存/1GB文件上限及同步落盘；本轮Ping上下行不走NATS，未验收JetStream可靠任务容量。
- Compose复用`deploy/task-demo/compose.yml`，只在云端压测目录改为默认服务端口、独立项目名及精确镜像补丁版本；不修改仓库示例部署契约。
- Go 1.27.0、Node 26.0.0，与本机基线一致。官方安装包两端SHA-256一致。Docker 29.1.3，镜像使用腾讯云镜像加速；Redis/Mongo浮动标签曾拉到更新版本，正式测试前已固定回上述实际本地版本。
- Go服务及客户端直接在宿主机运行，八服务（Login/Agent/MsgQ/Game各两个）、两个Node负载进程；不使用Kubernetes。
- SSH会话默认软文件描述符上限1024，压测命令内显式`ulimit -n 65536`，硬上限1048576；不通过修改业务代码兼容资源配置不足。
- 公网5Mbps只用于SSH与产物传输；压测流量在本机回环路径完成。

代码快照包含tx、txgame、txclient的当前未提交改动，共2002个文件，逐文件SHA-256核验无差异。不传Git历史、node_modules或构建产物；通过go.mod/go.sum与package-lock.json安装依赖。快照归档SHA-256为`f1f9c252267e88acacd599b618167b99d9d9a0d199c9142f30ee5d0e595d1fc1`，上传后的说明文档编辑不影响此次被测代码。

## 复现与下一项

在已准备好的云端工作区运行：

```bash
ulimit -n 65536
cd /home/ubuntu/tx-perf/workspace/txgame/server
GOMAXPROCS=2 TXCLIENT_PERF_TIMINGS=1 go run ./cmd/cluster-perf \
  --concurrency 10000 --rate-per-session 1 --client-processes 2 \
  --connect-rate 50 --log-level warn --duration 10m --timeout 20m \
  --artifact-root /home/ubuntu/tx-perf/artifacts/cloud-10k-steady-repeat
```

依赖可通过云端`setup/compose.yml`执行`sudo docker compose up -d --wait`恢复；不得对生产数据运行此编排器。复测期间不同时运行其他压力任务。测试结束压测服务及采集进程已收尾；云实例和四种中间件保留，仍按量计费，最终导出需要的产物后再销毁。

下一项保持万连、同拓扑和P=2，在15000次/s档位进行有界CPU profile及RPC阶段对照，先定位CPU消耗，不扩大超时或继续盲目增压。不把当前每会话1次/s当作10次/s/角色或生产SLG/MMO容量。Core NATS与JetStream容量保持独立测试方向。
