# Agent→Game 单流机会合批对照

本轮只改变 Agent→Game 的 one-way `CallStream` 发送：候选版增加一条本地发送队列，发送协程在不等待新消息的前提下，合并当时已经排队的消息。`CallStream` 的请求/响应路径、Agent→MsgQ、Game→MsgQ 和客户端协议不变。候选版保持同一流内消息顺序；为避免请求过大，单帧上限为 1024 项、约 1 MiB。实验结束后已撤回协议、生成代码、发送队列、接收端解包和批大小探针。

## 同机对照

六台云实例的部署保持不变：两台 P8 Agent、两台 P4 Game 进程、两台 P4 MsgQ 进程，两台客户端各建立 5000 个 TCP 会话。每会话上行 20 次/s，平均下行 50 次/s；每客户端 8 个 worker、每秒建立 250 个会话、测量窗口 60 秒。候选轮后恢复单流基线二进制，清理并重建专用夹具，再跑同档基线。两轮均由客户端记录计划、未发送、完成和已完成请求延迟；无业务调用失败。使用的是顺序回测而非同时运行的随机分流，对细小差异不能作严格因果推断。

| 指标 | 单流基线 | 机会合批候选 |
| --- | ---: | ---: |
| 计划上行 / 完成上行 | 12,000,000 / 11,960,046（99.6671%） | 12,000,000 / 11,955,300（99.6275%） |
| 未发送上行 | 39,954 | 44,700 |
| 客户端 A 已完成请求 P99 | 116.03 ms | 173.11 ms |
| 客户端 B 已完成请求 P99 | 85.36 ms | 160.34 ms |
| Agent A 测量窗口 CPU 时间 | 402.25 s | 379.60 s |
| Agent B 测量窗口 CPU 时间 | 402.02 s | 375.51 s |

候选版各 Agent 的 CPU 时间分别降低约 5.6% 和 6.6%，但 P99 分别升高约 49% 和 88%，完成上行减少 4746 条。两轮完整率均未达到当前 99.99% 目标，候选版也没有改善该差距。单流发送锁等待的抽样值下降，但候选版把等待转移到新增队列，不能把锁等待降低直接解释为端到端等待降低。

批量探针每 64 帧采样一帧：Agent A 的样本平均 1.14 项/帧，单项帧占 92.37%；Agent B 平均 1.19 项/帧，单项帧占 92.56%。在这档实际负载下，多数帧并没有可合并的已排队项。抽样按帧而非按消息，不能用该比例精确推算全部消息的合批率。

## 判断与接续

不接纳本轮机会合批实现，也不继续针对固定批量阈值调参；保留现有单流发送。候选版减轻了部分 CPU 开销，却引入新的排队/调度路径，当前数据没有逐段证明是哪一段造成 P99 回退。后续若继续优化 Agent→Game，应先将新增等待与客户端发生器排队分开观测，再提出可以同时守住顺序、吞吐和尾延迟的方案。

候选首轮的 Game 二进制缺少 `txbench` 构建标签；第一次基线重跑误用了不支持 `alternate` 下行模式的旧 Game 二进制。这两轮构建错误数据均已排除。上述表格只取修正二进制、重建夹具后的有效候选与基线。原始客户端结果与各服务测量前后 Prometheus 快照分别保存在 [候选轮](../../../tx-artifacts/cloud-20260928-dual-client/oneway-batch-2050-clean-20260928/) 和 [基线轮](../../../tx-artifacts/cloud-20260928-dual-client/oneway-baseline-2050-v2-20260928/)；云端业务服务已停止，专用夹具已清理。
