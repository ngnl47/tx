# NATS 原型共享响应与等待清理

日期：2026-09-12。起点 tx=cdddf92，六工程干净。本批只修改 `internal/actortrial` 及试验文档，正式 ProtoActor API、两个独立示例与模块依赖不变，不提交 Git。

## 修改原因与实现边界

上一轮共同负载发现，独立 inbox 的逐请求订阅和等待 goroutine 构成部分成本。查询[官方发布](https://github.com/nats-io/nats.go/releases/tag/v1.53.1)确认最新版本仍为 v1.53.1；本轮读取的官方主线 `createNewRequestAndSend` 也仍在发布失败时直接返回，未删除此前登记的响应 token。因此没有采用升级版本或直接启用 SDK 共享 Request 的方案。

本轮复用 SDK 的 `Subscribe`、`PublishMsg`、关闭回调和重连机制。每个 Transport 使用一个共享响应订阅，有界表将回复主题关联到既有 Future；表的长度同时承担原来的 pending 限流，不再保留独立的令牌 channel。该表只存在于调用进程内存，是 RPC 等待关联信息，不是 Redis/GD 中的业务完成表或 MQ 幂等记录。

- 发起远端 CallFuture 时登记回复主题，然后交给 SDK 发布，不等待 NATS 确认或业务结果。
- 响应、发送失败和创建 context 取消共用删除边界，只有取得该条目的路径能完成 Future；迟到响应忽略。
- `context.AfterFunc` 处理创建 context 的取消与 deadline；收到响应后停止回调，不为每个未完成请求创建常驻等待 goroutine。
- 连接永久关闭时回收全部等待并返回 `ErrConnectionClosed`；临时断线仍按原有 deadline 回收，不缓存或重投 RPC。
- 取消单次 Await 仍只结束这次等待；Tell/TellAccepted、本地直达、业务错误、NoResponders、排水与容量准入语义不变。

例如 32 个远端请求同时未完成时，旧版有 33 个订阅，新版固定为 2 个（实例入口与共享响应入口）。取消其中 16 个后，等待额度回收；其迟到响应不会被交给其他请求。发送超限消息时，错误返回且等待表不残留。

## 性能口径

复用 [T3 共同负载](2026-09-12-nats-protoactor-comparison.md) 的固定镜像、GOMAXPROCS=4、同一 Linux 网络命名空间与两独立业务进程。每个场景预热后采样 3 秒，五轮交替运行提交版、新版和 ProtoActor。完成计数、载荷副本、响应校验、错误分类、资源统计及近似项均沿用原口径。CPU 包含两业务进程及 NATS/etcd；分配只统计两业务进程，RSS 为预热/GC 后快照。

该对照不覆盖独立机器、真实 GD、TLS 或业务处理成本；不能用完成 RPC/s 推导生产世界容量，也不能把等待关联表改进等同于整个迁移完成。

128B/64 并发/1000 实体：新版中位吞吐提高约 40.2%，P99 降低约 29.0%，合计 CPU 从 262.5 降至 218.9μs/完成 RPC，两业务端分配从 76.8 降至 71.8 次、6394 降至 6262B/完成 RPC。目标 HeapAlloc 约 28.5MiB，未见明显变化；共享响应订阅带来一个常驻回调 goroutine，1000 实体预热后目标从 1006 变为 1007。

两版本轮次波动较大，吞吐范围分别为 1.36～2.17 万与 1.77～2.50 万次/s；这些范围重叠，不能把 40.2% 当作稳定倍率。本轮 ProtoActor 范围为 3.91～5.33 万次/s，与新版仍不重叠，且 P99 为 2.66～3.92ms，新版为 5.58～8.11ms。因此请求等待路径有改进，但 T4 迁移门槛仍未达到。

## 同机三节点拓扑补测

仅使用新版原型，一对独立调用/目标进程、64 并发、1000 实体，比较单节点、三节点同 broker 和三节点跨 broker，并交替加入 ProtoActor 对照。每例 3 秒、五轮。三个 broker 仍共享同一 VM 与 Linux 网络命名空间；没有增加物理 CPU 或带宽，没有启用 JetStream。每次形成集群均验证每个节点能看到另外两个不同的 peer ID，快照保存在 `*-routes.json`。

单节点对照为同一 seed 进程只保留自身在线，仍启用 route 监听；两种三节点模式分别让两端都连接节点 1，或调用端连接节点 1、目标端连接节点 2。第三节点参与网格但没有承载业务连接。此设计用于隔离拓扑影响，不能测出多调用端、多目标进程的聚合扩容上限，也不是故障切换验收。

| 路径 | 载荷 | 完成 RPC/s | P99 ms | 合计 CPU μs/RPC | 全部容器 RSS MiB |
|---|---:|---:|---:|---:|---:|
| 单节点 | 128B | 29,100 | 4.97 | 180.6 | 133.3 |
| 三节点，同 broker | 128B | 24,275 | 6.23 | 221.0 | 173.3 |

三节点资源合计包括两业务进程、三个 broker 与空闲 etcd；单节点/ProtoActor 为两业务进程、一个 broker 与 etcd，不能把三节点新增资源隐藏掉。同 broker 情况没有观测到稳定扩容收益，跨 broker 的额外转发使固定调用对进一步变慢。本组与前面的单节点修复对照属于不同采样批次，不能混算版本改善百分比。以上数据不证明增加物理资源、分散多个业务连接后的 NATS 聚合吞吐不能增长。
