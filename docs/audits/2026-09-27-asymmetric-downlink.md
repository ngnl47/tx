# 万连不对称下行回测

## 范围

2026-09-27 沿用[四机 10/10 回测](2026-09-27-async-stream-review-cloud-retest.md)的腾讯云 SA9 8 核 16 GiB 布局：接入机 Agent×1（P8）、Login×2（P4）；存储机 MsgQ×2（P4）及测试中间件；游戏机 Game×2（P4）；独立客户端机。客户端经 Login、真实 TCP Agent 和正式 `System_Ping` 业务链路，每个 Ping 由 Game 生成 1 条 Pong 和按上行 Seq 交替生成 1 或 2 条 `GlobalNotify`，平均为每次上行 2.5 条下行。业务服务配置、10,000 个 Session、每 Session 10 次上行/s、`max-in-flight=4`、2 秒预热和 180 秒正式窗口均保持相同；两轮只改变客户端 worker 数量。

客户端适配多在途的额外下行归属，并校验每次 Ping 对应的所有下行；没有改生产链路。Game 使用启用 `txbench` 的同源构建，二进制 SHA-256 为 `68f2d6c80ebca0e96999547681b0e84a8f5296d053b0b4ed3f27d0463c4e8813`；客户端部署包 SHA-256 为 `ab6a5e7fec59508a73c8ece17624ee468a50d1d839f63ada14fa10408c1192e4`。每轮复用同一批 RoleID 前均停七个业务单元并重置有归属标记的专用夹具，避免旧 Session 绑定代次干扰。一次在冒烟测试后未重置夹具的准备失败没有进入测量窗口，不计入吞吐结果。

16-worker 轮按现阶段完整处理率 ≥99.99% 验收通过，P99 也低于先前讨论的 60 ms；8-worker 轮两项都未通过。两轮已发送请求均完整处理，`failed=0`。16-worker 轮的 195 条未发送全是测量窗口结束时的待发槽位，正式窗口内没有跳过计划槽位；另外 277 条上行和 669 条下行在窗口结束后完成，已从表中窗口吞吐扣除。8-worker 轮的 45,110 条未发送由 43,432 条调度跳过、1 条容量等待后跳过和 1,678 条窗口末尾待发组成。因而本轮 8-worker 失败主要反映压测客户端调度能力，不应误报为服务端丢业务消息。

8-worker 客户端事件循环平均利用率约 72.14%，各 worker 的事件循环 P99 为 32.54–35.52 ms；16-worker 分别约 46.43% 和 24.90–26.79 ms。16-worker 调整几乎消除了调度跳过，而服务端总 CPU 未出现对应幅度的变化，支持客户端发生器是首轮完成率与延迟恶化的重要干扰源。它不证明服务端没有更高负载下的排队：16-worker 时 Agent 已使用约 5.87/8 核，宿主机约 21% 空闲，20/50 档仍须另测。两轮宿主机采样中 `steal` 均为 0%；正式窗口内七个业务单元未检出 error/failed/panic/deadline 日志。8-worker 的服务采样因准备后到释放屏障的间隔过长，仅覆盖正式窗口 145–167 秒；16-worker 四台机器均覆盖 180 秒，跨轮资源比较只作量级判断。

## 边界与后续

这个结果仅证明当前轻量 Ping 业务、单 Agent 8 核、四机布局和 3 分钟窗口下的万连 10 上行/25 下行；不代表 MMO 广播、战斗计算、长时间稳定性或终极 20/50 已达标。下一步应在相同 16-worker 发生器下采集 Agent 的下行 CPU/分配画像，区分邮箱流读取、会话写出和客户端 Socket 写入开销，再决定是否优化单 Agent 或扩大实例。不要据 8-worker 轮的未发送推断 MsgQ 或 Game 已达容量上限。

原始汇总、两轮 worker 调度摘要、四机 `pidstat`/`vmstat` 和解析脚本保存在 `/Users/a47/workspace/tx-artifacts/cloud-20260927-asymmetric/`；逐请求大数组保留在临时客户端云机，归还实例后不可重算任意分位数。8-worker 轮后曾并行停止三台服务机，Game 因依赖 MsgQ 排水而以退出码 1 结束；重置单元状态后正常准备第二轮。最终按 Agent/Login → Game → MsgQ 顺序停止七个业务单元，均为 `inactive`、`Result=success`、退出码 0；测试中间件仍保持原有状态。

## 接续：Agent 下行 CPU 与分配画像

同日以 16-worker、10,000 Session、10/25、180 秒重新执行画像轮。Agent 使用与上表 Game 相同 SHA-256 的独立 `txbench` 二进制，`TXGAME_PROFILE_DIR` 只在 Agent 上启用绑定 `127.0.0.1` 的 pprof；Login、Game、MsgQ 和业务配置不变。准备完 10,000 个唯一 Session 后先保存 Agent 分配快照，再释放正式窗口；窗口内采 30 秒 CPU，约 120 秒后保存第二份分配快照。该轮的 pprof 和诊断开销不与无采样轮直接作吞吐归因。

画像轮完整处理 17,994,189 / 18,000,000 次上行（99.96772%），下行 44,985,330 条，业务失败 0，未发送 5,811，其中调度跳过 5,631、窗口末尾待发 180、容量等待后跳过 0；P99 为 48.546 ms。无采样 16-worker 轮的对应数为 17,999,805、44,999,548、未发送 195、P99 41.795 ms。此差值只说明采样轮受到扰动，不作为更改生产实现后性能回退的证据。30 秒 CPU profile 累计 179.98 CPU 秒，约 6.00 核，与同期 Agent `pidstat` 约 6 核一致；服务资源采样因释放屏障前等待较长，仅覆盖正式窗口 153–158 秒，客户端约 177 秒，不用于完整窗口容量比较。

| Agent CPU 调用链 | 累计样本占比 | 解释 |
| --- | ---: | --- |
| `writeDownMsgs` | 22.36% | 包含读取会话消息、逐帧编码与客户端 Socket 写出 |
| `tcpTransport.Write` | 17.77% | 位于上述调用链内部，其中 `writev` 系统调用约 10.66% |
| MsgQ `grpcMailboxStream.readLoop` | 9.35% | 接收共享的下行 gRPC 流并分派给会话 |
| `dispatchUpMsg` | 21.51% | 上行转发的另一条主要工作路径 |
| `tcpTransport.Read` | 19.00% | 客户端 TCP 上行读取；与其他上行调用链可能重叠 |

表中是累计调用栈占比，子调用和父调用不能相加。测量前后 `allocs` 差值估算分配约 48.46 GiB；`tcpTransport.Write` 累计约 16.69%，其中每帧 `context.AfterFunc` 本身占总分配约 10.23%（写出约占它的 70%，读取约占 30%）。Protobuf 反射新建约占 13.41%，服务发现 `cloneInstance` 中的 `maps.Clone` 约占 7.46%。这些百分比是采样估算的分配空间，不等于存活内存；所有父子调用比例也不能相加。现有 Socket 写出已经使用 `net.Buffers`/`writev`，不能把这些样本解释为当前仍在逐字节拷贝；也不应仅凭 `AfterFunc` 分配就移除取消和排水语义。

当前最值得验证的单变量是客户端下行逐帧写出成本：在保持帧顺序、Ack 和取消语义的前提下，先用局部基准或同条件短轮量化同一 Session 连续下行的写入次数及合并收益，再决定是否改生产发送路径。上行路由副本与 Protobuf 分配也有证据，但本轮没有分离它们对 10/25 下行延迟的影响。完整 CPU profile、分配前后快照、`pprof` 文本报告及四机采样归档在 `/Users/a47/workspace/tx-artifacts/cloud-20260927-asymmetric/r4/`。结束后按 Agent/Login → Game → MsgQ 顺序正常停止七个业务单元，均为 `inactive`、`Result=success`、退出码 0；临时私网二进制复制服务已关闭，正式二进制未被覆盖。

## 接续：同会话下行帧合写

先在 macOS 环回 TCP 上以相同的三个 96 字节下行帧对照：原路径逐帧 `Write` 两次测得 17.5–17.6 µs/三帧、1208 B 和 19 次分配；一次 `writev` 两次测得 6.2–6.3 µs/三帧、744 B 和 7 次分配。该基准只给出三帧同时待发时的传输收益上限，不能直接外推到完整集群。

随后四机保持 10,000 Session、每 Session 10 上行/25 下行、16 个客户端 worker，分别运行 60 秒旧路径 R5、合写候选 R6、回切旧路径 R7。旧路径诊断 Agent 在 1500 万次下行出队采样中，取出一条后同会话队列仍有至少一条的比例为 52.70%，至少两条为 16.03%。候选版只立即取走已排队的最多两条后续消息，不等待新消息；最多三个原协议帧一次 TCP `writev`，WebSocket、单帧发送、MsgQ/Game 和客户端均保持原路径。诊断 Agent 二进制 SHA-256：旧路径 `de7ae73c52dae206c67a5dbd3dcb5c57e4affab2b3b58be9a8b3e65b1b3b3837`；合写 `19340ec24457e61dcf1c3f9f57f1cbc4c6b8ca26bf0108adbf41e15be2e38219`。每轮在七个业务进程停止后重新准备专用夹具、启动相同服务布局并创建相同范围的角色。
