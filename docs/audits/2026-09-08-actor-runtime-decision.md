# Actor 运行时选型结论与排水职责边界

本文件用于将本轮结论带回主分支，可独立阅读，不依赖实验目录或临时日志。评估来源为 `feature/goakt-runtime-evaluation`，结论整理提交为 `a8018ae`。它是选型与交接记录，不代表尚未实施的功能已通过验收。

## 1. 最终决定

保留 ProtoActor 作为 tx 当前生产运行时，结束本轮 GoAkt 替换评估，不继续扩大适配范围。

评估固定 GoAkt v4.5.4。其 Grain 的正常远程投递、激活、内建钝化和有界邮箱可用，但公开扩展点不匹配 tx 所需的“接收侧入队控制 + 持久化失败保留运行时”。若补建接收层或改用普通 Actor，需要重新承担部分通信和生命周期职责，尚未证明有净简化收益。

这不是 GoAkt 整体质量较差或所有扩展能力都弱于 ProtoActor 的结论，也不意味着 ProtoActor 自动保证安全关闭。结论限定于当前版本、当前 Grain 适配方式和 tx 的既定需求。

实验代码、独立依赖和探针留在评估分支，不要求合入主分支。后续清理或重新评估须另行确认。

## 2. RPC 与 MQ 的消息职责

- RPC 提供服务正常运行期间约定的投递、接收确认和执行结果语义，不承诺服务异常、滚动重启或目标关闭后必达、必执行。
- 失败或超时不得伪装成业务成功；超时也不能证明业务未执行或已经结束，不应据此盲目重投。
- 排水只保障已接受工作的完成和安全收尾，不负责保证整条跨 Actor 业务链成功，不增加全局调用链追踪或自动补发机制。
- 需要异常后可靠完成的消息，应由持久化 MQ 及业务幂等、结算恢复等机制承接。RPC 与 MQ 可以复用业务分派，投递、重投和消费确认由各自适配层负责。
- Actor 入队成功不能直接等同于 MQ 业务消费完成。消费确认与业务处理、必要持久化的关系，在 MQ 设计时明确。
- 本轮不引入 MQ，不提前增加 MQ 依赖、公共接口或推测性扩展。

例子：盲盒集齐三个玩家后开奖。p3 的加入请求已进入邮箱，应继续处理；它随后向 p1、p2 发送发奖 RPC，如果目标已关闭准入，允许调用失败或超时。需要保证三人最终全部到账的业务，不能仅靠 RPC 和优雅关闭实现。

本次讨论的教训是：边界不清时，先确认消息契约。不能在排水场景下，把 MQ 可靠性消息的职责套到 RPC 消息上。

## 3. tx 的正常排水模型

1. 在入队前关闭业务准入；关闭与准入登记必须有明确的并发边界。
2. 等待已接受的工作处理结束，包括已准入但尚未入队、正在排队和正在执行的消息。不得在出队时仅因进入排水而丢弃消息。
3. 完成必要的持久化收尾。
4. 成功后停止运行时；失败时保留资源并沿用既定有限重试策略，重试耗尽记录日志并失败退出。不承诺故障下无限等待或数据绝不丢失。

“投毒”可借鉴的是停止标记排在已有业务之后的队列顺序，不是必须照搬某个停止 API。单独投毒不能替代入队准入控制，也不能把队列完成与 Actor 销毁、持久化成功混为一谈。

当前 ProtoActor 适配已经有等价的完成屏障：

- `modules/actor/mailbox.go`：入队前登记工作；入队失败或业务调用结束后注销。
- `modules/actor/lifecycle.go`、`modules/actor/runtime.go`：关闭同一准入，等待登记计数归零。
- `internal/framework/shutdown.go`：正常关闭先排水与组件收尾，成功后释放资源；失败保留供有限重试。

因此不应为了“投毒”形式增加第二套排水屏障。该结论只覆盖受框架生命周期管理的业务，不覆盖任意后台协程、绕过框架的消息、网络分区或异常强制退出。

## 4. 评估证据与限制

| 项目 | 已观察结果 | 不能推导的结论 |
| --- | --- | --- |
| GoAkt 本地适配 | 11 个核心用例三轮竞态验证通过，覆盖多 Session、容量、超时、钝化、投递语义及本地排水 | 不等于完整生产替换验收 |
| GoAkt 双进程 | 真实 etcd 下四种正常投递入口及业务错误回传可用，响应 PID 确认跨进程执行 | 不保证异常后必达、归属交接或跨进程持久化安全 |
| GoAkt 排水缺口 | 只关闭本地发送入口后，远端仍能令目标执行业务；实验已加保护，拒绝未经适配的集群收尾 | 保护不是接收端排水实现 |
| GoAkt 公开扩展点 | Grain 未提供自定义邮箱/入队拦截器；OnReceive 已在出队后；解码、上下文扩展缺少与入队成对的完成通知 | 不能靠检查一个关闭标志就宣称原子准入成立 |
| GoAkt 关闭生命周期 | 系统关闭与资源销毁绑定，关闭钩子报错仍继续清理 | Stop 成功不等于业务持久化成功，失败也不等于运行时保留 |

本地同一 Call 基准的阶段性结果：直接 Ask 适配约 10.5–10.6 μs/op、67 次分配；加入有界 Future 等完整入口适配后约 22.3–24.0 μs/op、72 次分配。环境为 Intel i9-9880H、darwin/amd64、256 B 请求和响应、共享 deadline，三轮各 300ms。这是实验阶段之间的局部比较，不是 GoAkt 与 ProtoActor 的等价集群性能对比；只能说明未获得性能无回退的证据。

未实施：GoAkt 接收端排水闭环、生成 GD 与真实持久化集成、完整归属交接、普通 Actor 替代适配。它们不再是默认待推进任务。

## 5. 回到 ProtoActor 主线后的待办

### 优先项：关闭阶段竞态

当前依赖为 `github.com/asynkron/protoactor-go v0.0.0-20240822202345-3c0e61ca19c9`。

使用真实 etcd 重跑现有 `TestActorRuntimeDrainWaitsForQueuedMessages`：

- 不带竞态检测连续三轮通过：执行中的第一条和排队的第二条均完成后才返回排水成功，关闭后新投递被拒绝。
- `-race -count=3` 失败，随后单轮再次复现关闭清理阶段的竞态。关键报告如下，已保留必要证据，不依赖临时日志：

```text

          etcd_provider.go:117  p.shutdown = true

          etcd_provider.go:168

```

复现命令，在 tx 根目录执行；测试自行使用独立 etcd 命名空间，不写 Redis/Mongo 业务数据：

```sh
TX_ETCD_ENDPOINT=127.0.0.1:2379 go test ./tests -run '^TestActorRuntimeDrainWaitsForQueuedMessages$' -count=3 -timeout 90s
TX_ETCD_ENDPOINT=127.0.0.1:2379 go test -race ./tests -run '^TestActorRuntimeDrainWaitsForQueuedMessages$' -count=1 -timeout 45s
```

下一步先评估该竞态的影响和不修改第三方源码的处置方式。不得把正常功能通过描述为竞态通过，也不得仅凭竞态报告断言已经发生数据丢失。本轮未修复此问题。

之后确认跨进程迟到请求、已入队工作完成、持久化失败保留与有限重试的验收范围。不新增 MQ，不追踪整条跨 Actor 调用链。
