# Prometheus 抓取与延迟抽样开销对照

## 对照条件

2026-09-28 复用四台腾讯云 SA9 8 核 16 GiB：Agent×1（P8）、Login×2（P4）、MsgQ×2（P4）、Game×2（P4）和独立客户端机。客户端通过真实 TCP 链路建立 10,000 个 Session，以每 Session 8 次/s 的频率运行 60 秒；每条上行 Ping 产生一条下行。此档选择在 Agent 与客户端机未满载的区域，目的在于测观测开销，不作为 20/50 容量验收。

四轮均使用同一服务端二进制 SHA-256 `d38c86ad38b59736569bc77a8a0728ebbf4c3f34dbec650ac56a366a3637f8fc`。A2、B1、A3 完整记录所有 Counter 和延迟 Histogram；C1 仍精确记录 Counter，只对延迟 Histogram 以 1/16 概率执行 `Observe`。A2、C1、A3 对每个服务进程的回环 `/metrics` 约每 5 秒抓取一次；B1 仍启动同一指标端点，但不抓取。每轮均在服务停止后重置专用夹具和 10,000 个角色，使用同一客户端程序、16 worker、500 连接/s、`max-in-flight=4`、2 秒预热。四轮顺序为 A2→B1→C1→A3。

抽样是本轮可撤销的对照探针，实验代码保存在工程外的 [`sampling-probe.patch`](/Users/a47/workspace/tx-artifacts/cloud-20260928-prom-sampling/sampling-probe.patch)；未作为生产默认行为保留。A1 首次尝试因客户端放行文件由外部触发，指标采样没有覆盖正式窗口，排除在结果之外。重建的夹具二进制与四轮共同服务二进制均来自同一云端 Go 1.27 构建目录；旧 `cluster-fixture.review` 连 `--help` 都发生段错误，未用于有效轮。

四轮 `failed=0`，所有实际发出的上行最终完成。CPU 取客户端正式窗口开始后第 5 至 60 秒的每秒 `pidstat` 样本，Agent 各轮均约 4.8/8 核；客户端机中段 `vmstat` 样本仍有约 51%–55% 空闲。A2、C1、A3 每实例在该窗口各取得 11 次无错误的指标抓取。Agent 的上行成功 Counter 约为 80,000/s：完整记录轮对应直方图约 80,000 次观察/s，C1 约 5,000 次/s；Game 与 MsgQ 相应直方图也从约 40,000 次/s 降到约 2,500 次/s。抽样开关确实生效，而精确消息量未被抽样。

本地 Mac 的单线程埋点基准中，上下行各记一次的成本从全量约 82–90 ns/组降到抽样约 29–31 ns/组，均为 0 B/op、0 alloc/op。这只量到埋点函数，不包含调用点的计时、云端并发竞争或整条消息链路。

## 判断与收尾

在未满载的 8/8 档，停止抓取没有降低 Agent CPU；抽样延迟也没有降低 Agent CPU。C1 P99 比 A2 低 0.76 ms，但紧随其后的全量 A3 又比 C1 低 0.04 ms；这不足以把差异归因于抽样。A2 与 A3 本身相差 0.80 ms，说明该量级属于轮次波动。此处没有证据表明当前 Prometheus 记录或 5 秒抓取是上下行吞吐的明显卡点，不应默认启用延迟抽样，也不应把 Histogram `_count` 当作抽样后的精确总消息数。

四轮客户端汇总、进程 CPU、宿主机 `vmstat` 和原始指标快照保存在 [`cloud-20260928-prom-sampling/results`](/Users/a47/workspace/tx-artifacts/cloud-20260928-prom-sampling/results/)；运行脚本与本次探针补丁在同级目录。测试结束后七个业务单元均停止，专用 Redis DB12、Mongo 验收库与 etcd 验收前缀已按夹具所有权清理；中间件容器仍运行。后续 10/50 的长尾定位应继续以 Agent 下行出队、编码和 Socket 写出画像为主，避免以抽样开关替代热点定位。
