# NATS SDK、协议与 Actor 调度分层评估

## 范围与方法

本批为 T3c，起点 tx=4a92907，保留 T3b 未提交驱动和报告；只有 tx 变更。txgame=3afc074、txgameslg=2fd67a6 仍在同名 feature 分支，其余三工程及两个示例均未修改。正式运行时仍使用 ProtoActor，T4 暂停。本批不以旧测试或旧 benchmark 作为新验证。

目标是判断完整原型的差距主要出现在哪层，不能把原生消息吞吐直接当作业务 RPC 性能。此次不修改通信原型、SDK、邮箱、公共 API 或 SPI，采集与旁路仅存在于 `_test.go` 和本机临时目录。

| 对照 | 实际路径 | 不包含的能力 |
|---|---|---|
| SDK 原生 | nats.go `RequestWithContext` → 单订阅回显 → SDK 共享响应订阅 | 身份、protobuf、业务结果、副本契约、实体与有界 pending |
| 协议封装 | 现有 `Transport.Call` → 身份解码及 protobuf → 相同结果/副本 → 现有响应等待清理 | 实体创建、准入、邮箱、生命周期与业务排水 |
| 完整 NATS Actor | 现有 `Transport.Call` → 实体准入及串行邮箱 → 业务回显 → 结果 | 正式 GD、Procedure、租约接线及持久化 |
| 正式 ProtoActor | 现行 tx Call → 固定 Kind 宿主按 RouteKey 激活实体 → 相同业务回显 | 同上，不测虚拟归属或迁移 |

协议层在目标订阅回调中直接完成回显；完整层回调只入队，由实体 worker 执行。这个对照用于消去实体调度成本，不能替代实体串行及生命周期。原生层只校验载荷相等；其数字也包含共同驱动的 deadline、时间采样和目标 Subject 构造，不是 SDK 内部单函数微基准。相邻两层的差值包含协议字节、校验、副本、等待和调度的组合影响，不能直接归因为某个 JSON 调用。

Go 1.27.0、nats.go v1.53.1、nats-server 2.14.6，Linux/amd64 二进制运行在同一 Docker Desktop Linux 内核中；每个业务进程及 broker 的 GOMAXPROCS=4。单 broker 和一组独立调用端/目标端，各一个 NATS 连接；不设 Queue Group、TLS、JetStream 或逐请求 Flush。ProtoActor 使用同一内核下的直连 gRPC，与现行正式封装保持一致。镜像沿用 T3b 固定摘要，未使用 latest。

每个实体对照预热 1000 个不同身份；原生及协议旁路不创建实体。初筛为 128B、1/16/64 并发，每点 2 秒；正式采样为 128B×16、128B×64、1024B×16，每点 3 秒、五轮，按轮轮换四组顺序。均为闭环负载，统计成功回包并通过校验的完整 RPC；不沿用 T3b 固定到达率数据。成功样本在资源快照后导出，CPU profile 独立采集，不混入正式中位数。

本机材料：`/private/tmp/tx-nats-layers-20260912`。`manifest.json` 固定采样源码、二进制及编排器 SHA-256；`before.patch` 保留进入本批时的 T3b 工作区；`layers.py` 为本批编排，`compare.py` 复用上一批进程与资源所有权管理。`results.jsonl` 和各窗口 `.json.gz` 保留完整计数、单调耗时、Go 资源及成功延迟样本；`summarize.py` 独立检查计数、分位数及 broker 收发消息数。

```bash

  go test -mod=readonly -c ./internal/actortrial -o /private/tmp/tx-nats-layers-20260912/comparison.test
```

`TestRPCComparisonProcess` 用 `TX_RPC_COMPARISON` JSON 选择 `Backend`（`nats-native`、`nats-envelope`、`nats`、`proto`）及 `Mode`（本批只用 `server/client`）。先取 server 的 `Ready`，作为 client 的 `Target`，通过标准输入发送 `run`、`samples`、`stop`。目标进程的配置 `Profile` 从启动采到退出；调用端负载 `Profile` 只包围负载窗口。broker 使用镜像自带 `--profile` HTTP 端口采 CPU。采集接口均不编入生产二进制。

官方 Pub/Sub 校准使用当前 SDK 自带 `examples/nats-bench/main.go`，不另装 CLI 或依赖。它以独立连接发送和订阅，但发送/订阅位于同一进程，且订阅 pending 无界；只作为环境校准，不作为业务内存边界方案。报告必须分别使用 PUB、SUB 行，不能使用将收发次数相加的组合速率冒充单向完成量。

## 分层结果（GOMAXPROCS=4）

12 个初筛窗口与 60 个正式窗口合计完成 **4,555,224 次 RPC，返回错误为 0**；每个 NATS 窗口均验证 broker 入站、出站各增加 `2 × 完成 RPC 数`，broker 连接数均为 2（两端各 1）。72 份延迟样本的计数及 P50/P99 独立重算通过。

| 对照 | 两业务进程 CPU μs/RPC | 分配次数/RPC | 分配 B/RPC | 两端 goroutine |
|---|---:|---:|---:|---:|
| SDK 原生 | 78.9 | 19.0 | 1490 | 13 |
| 协议封装 | 138.6 | 64.9 | 5811 | 14 |

CPU 是两端 Go 的进程累计 CPU 差，**不含 broker、etcd 或 Docker 虚拟化宿主开销**，不能拿来比较部署总成本；目标端快照还覆盖少量空闲/控制开销。资源预分配、样本排序与导出在调用端快照外，逐请求 deadline 和采样记录在内。goroutine 数不是线程数或耗时比例，1000 个空闲实体 worker 不等于 1000 个 CPU 同时工作。

## CPU profile 与后续单变量检查

四组分别留存调用端、目标端、broker 的 CPU profile，共 12 份。调用端采 10 秒负载；目标端从进程启动采至退出（约 12～18 秒，包含初始化/预热/关闭）；broker 采其中 8 秒。ProtoActor 不经 NATS，该 broker profile 仅是空闲对照。profile 窗口不纳入上表。

原生层的调用端、目标端、broker 中，`runtime.futex` 的 flat CPU 占比分别为 38.29%、42.78%、38.12%，Linux Syscall6 分别为 25.62%、33.24%、29.94%。完整层调用端为 20.68%/21.14%，目标端为 26.47%/21.66%。这些是 CPU 归属，不能当作请求墙钟等待比例，也不能仅凭 futex 就断言某把业务锁竞争。

完整层调用端 `Transport.message` cumulative 10.63%，其中 JSON Marshal 3.50%；目标端 `Transport.receive` cumulative 11.79%，其中 JSON Unmarshal 2.89%，`Runtime.submitRequest` 6.14%。累计项相互包含，不能相加；它们不足以支持“删一次 JSON 编码就能弥补全部差距”或立即重写邮箱。Call 没有逐条 Flush；NATS 订阅回调只入队，业务由 worker 执行；正式 ProtoActor 使用远端批处理，NATS SDK 也有缓冲输出，不能把 Publish 次数等同于系统调用次数。

三端原生路径都出现调度同步热点，因此追加 GOMAXPROCS=1/4 的单变量检查，确认这个同机小消息负载是否因并行调度放大开销。此检查只改测试容器的环境变量，不修改 tx 默认配置，也不把单线程设置推广为通用生产建议。

### GOMAXPROCS 单变量五轮复测

先做 6 个筛选窗口，确认有明显收益后做 30 个正式窗口；都是 128B、16 并发、1000 身份、每窗口 3 秒。三端及临时 etcd 统一使用 1 或 4，按轮交换并行度与后端顺序，其余代码、连接和载荷不变。此补测有自己的同批 GOMAXPROCS=4 对照，**不拿前一张表的较慢结果充当前值**。

| 对照 | 并行度 4 RPC/s | 并行度 1 RPC/s | 中位吞吐变化 | P99 ms：4 → 1 | 两端 CPU μs/RPC：4 → 1 |
|---|---:|---:|---:|---:|---:|
| SDK 原生 | 20,402 | 28,935 | +41.8% | 1.886 → 0.992 | 69.4 → 33.4 |
| 完整 NATS Actor | 14,971 | 24,163 | +61.4% | 2.066 → 1.935 | 135.3 → 72.9 |
| 正式 ProtoActor | 26,086 | 30,866 | +18.3% | 1.197 → 1.561 | 131.2 → 56.5 |

完整 NATS 五个配对轮次的吞吐提升分别为 66.5%、63.8%、124.5%、76.0%、35.9%；各组全部五轮均有吞吐提升。完整 NATS 的中位 P99 降低 6.3%，分配次数约 71.8/RPC 不变；ProtoActor 吞吐提升的同时 P99 上浮 30.4%，说明吞吐和尾延迟须分别评估，不能只挑一项。

同为并行度 1，完整 NATS 的中位吞吐仍比 ProtoActor 低 21.7%，P99 高 23.9%；五个配对轮次仍全部超过既定 10% 吞吐退化线。并行度 4 的完整 NATS 范围为 10,763～16,802 RPC/s，1 的范围为 20,346～27,978；仍保留共享宿主机的波动限制。

追加三组、三端共 9 份独立 profile。并行度 1 时，原生调用端/目标端/broker 的 futex flat 占比为 4.07%/23.72%/9.40%；完整 NATS 为 5.90%/5.22%/6.23%。这些变化与吞吐提高、两端每 RPC CPU 下降相互支持，说明当前环境的并行调度配置确实影响测量；它并未定位到某一把 tx 业务锁，也不能证明 Go、Docker 或 NATS 有普遍缺陷。

补测 36 个窗口完成 2,663,057 次 RPC，错误为 0；样本、计数、连接及 broker 消息数再次独立核验通过。完整 T3c 合计 **108 个非 profile 窗口、7,218,281 次 RPC**，另有 750 万条 Pub/Sub 校准消息；两种语义的数量分别报告。全部 21 份 profile、固定镜像/源码/二进制哈希及复测材料位于上述目录与 `gomax/` 子目录，临时容器全部按所有权标签清理，原有五个开发容器保留。

## 结论与下一项

1. 用户提出的“使用或压测配置影响 NATS 表现”得到部分证实：同机的 GOMAXPROCS 配置显著影响小消息 RPC，且官方 Pub/Sub 确有接近百万条/秒的完成速率。先前的完整原型结果不能解释成 NATS 服务端的通用吞吐上限。
2. 当前协议和实体调度均有成本，但没有证据支持靠删一个编码 helper 或校验就解决全部差距。原生 Request 只用于正常成功基线，不替代现有有界等待、失败清理和未知结果不重投约定；本批没有移除必要语义。
3. 本轮不修改生产 GOMAXPROCS、连接池或邮箱。空回显受益于降低并行度，真实 GD/Procedure 业务则需要不同实体并行执行；全局设为 1 可能损失业务 CPU 吞吐，不能自动推广。
4. **T4 继续暂停，保留 NATS Core 候选**。下一项建议评估含 GD/Procedure 的代表业务链路与部署 CPU 预算，再确认延迟/吞吐目标及运行配置。具体负载与预算尚需评估；不继续当前空回显路径的零碎微优化，也不据本批直接转为已确定的 ProtoActor + JetStream 方案。

简单例子：role 向 world 发 128B 请求并等待业务回包属于本批完整 Call；连续 Publish 128B 消息而不逐条等结果属于 Pub/Sub 校准。前者多了结果等待和实体处理，后者的百万条/秒不能作为前者的 SLA。
