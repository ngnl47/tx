# Agent→MsgQ `Rec` 双向长流候选

## 接线与契约

`MailboxService.RecStream` 复用原 `Rec` 处理，每条上行仍等待 MsgQ 的回执后才分派业务；下行 `StreamFetch` 与 Seq/Ack 契约不变。Agent 的 `recStream` 开关默认关闭，可随时回退到 Unary `Rec`。每个目标 MsgQ 客户端用 16 条长流按 SessionID 分道，同一道每次只保留一条待确认请求。流错误或请求取消后丢弃该流，下一条请求新建流；发送后结果未知的请求不会自动重投。服务端重启并沿用地址时，路由器以新的 InstanceID 更换客户端，避免继续使用旧长流。

## 隔离与完整链路回测

本机 1024 会话、16 通道的真实 `RecStream` 实现基准，三次 1 秒样本中，Unary 为 19.3～23.5 µs/op、140 allocs/op，长流为 8.9～10.1 µs/op、32 allocs/op。这里的 `ns/op` 是并发完成量的摊算，不是端到端请求延迟。

单台 8 核/16 GiB 云机上 Login、Agent、MsgQ、Game 各一进程 P2；Agent→Game 的 `directCallStream` 保持开启，2,000 TCP 会话×10 次/s、1:1 Ping/Pong、30 秒 Unary→RecStream→Unary 同版对照：两次 Unary 均完成 600,000/600,000，P99 分别为 27.027/27.406 ms，Agent CPU 平均约 151%/152%；长流完成 599,990/600,000，10 次未发送、零业务失败，P99 21.915 ms，Agent CPU 约 132%。这轮长流因未发送不算完整通过。随后 3 分钟长流单独完成 3,600,000/3,600,000、零未发送/失败，P99 20.651 ms，Agent CPU 约 130%。单机回环与进程竞争环境不能外推四机容量或 20/50 不对称负载；短轮未发送也不能被长轮结果抹去。

## 重启交接验证

首次真实多进程 `cluster-e2e` 在 MsgQ-a 排水并于原地址重启后连续两次失败：Agent 的客户端路由仅按 endpoint 复用，继续持有旧实例的 gRPC 长流。针对同地址、新 InstanceID 增加了先失败后通过的客户端轮换测试，并更换旧连接而不自动重投结果未知的 `Rec`。修复版真实多进程测试通过 MsgQ、Game、Agent、Login 重启/排水及原 Session 恢复场景；其中新会话的 MsgQ owner 指向重启后的新 InstanceID。测试结束后已恢复原四服务夹具。

同一修复版程序又做了 30 秒候选短轮：599,995/600,000 次完成、零业务失败、5 次未发送、P99 21.387 ms。未发送仍属未通过；这轮没有相邻的修复版 Unary 对照。路由修复仅发生在取得会话客户端时，尚不能据此前修复版的吞吐优势量化该改动的性能影响。

两客户端工作进程中只有第二个缺 5 次。其诊断显示 `skippedSlots=0`、`capacityWaits=0`；5 个会话的最后一次计划时刻分别为窗口的 29,999.5～29,999.9 ms，协程结束于 30,000.72～30,000.76 ms。因固定截止时刻已经越过，它们没有发出；这次缺口属于压测发生器在窗口边缘的调度抖动证据，不能解释为 MsgQ 拒绝、上行错误或流池背压。严格零未发送验收口径仍保留。

本轮保留开关默认关闭。完整链路的当前证据支持继续作为可选候选；没有证明跨宿主机、万连、20/50 或异常断连期间的容量和延迟边界。早期隔离原型及其限制见 [Rec 长流隔离对照](2026-09-24-rec-stream-probe.md)。
