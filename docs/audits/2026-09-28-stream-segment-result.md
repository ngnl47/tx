# 六机 20/50 单流分段诊断

本轮保持两台 Agent 各 P8、两台 Game 各 P4、两台 MsgQ 各 P4、两台客户端各 8 个 worker 的拓扑。客户端各连接 5,000 个 TCP Session、每 Session 每秒计划 20 条上行和平均 50 条下行，正式窗口 60 秒。两台 Agent 使用最终版单流探针构建，SHA-256 为 `fe834bd2d20837d8924fdbe7d5c4d622da70bf2e9daea2e934e475ecbe97d36d`；Game、MsgQ 与前轮保持同版。没有启用八流候选或新的合批。

此前六台实例进入「待回收」时启动的同名诊断轮无效：客户端 A 留下一个失败结果，客户端 B 没有结果，服务进程随后退出。用户恢复实例后，已取回 A 的残留诊断、停止所有进程并清理专用夹具；以下数据来自重新准备夹具、重新启动八个业务进程后的**新窗口**。新窗口结束后，六台主机的结果与窗口前后指标均已取回，业务进程已停止，夹具再次清理。原始归档在 `/Users/a47/workspace/tx-artifacts/cloud-20260928-dual-client/stream-segment-final-20260928/`。

两端 `failed` 计数均为 0，`completed=attempted`；顶层状态仍是 `failed`，因为未达到计划发送数。窗口后才完成的 A/B 请求分别为 3,053/239，单独统计，不算作窗口内完成。本轮既未达到 99.99% 完整率，也未达到已完成请求 P99≤60 ms 的目标。

各节点 `/metrics` 在客户端就绪后和窗口结束后抓取，差分区间比正式 60 秒窗口更长，包含短暂空闲与预热。因此下列是**诊断区间的分布**，不是严格 60 秒 CPU 利用率；直方图 P95/P99 只给出落入的桶上界。Agent 的发送锁和 `Send` 每 64 条各抽样一次，客户端阶段数据同样每 64 条抽样一次。

| 同进程阶段 | A P95/P99 桶上界 | B P95/P99 桶上界 | 判断 |
| --- | ---: | ---: | --- |
| Agent 等待 Actor 流发送锁 | 10/20 ms | 20/40 ms | 局部排队明显 |
| Agent 持锁执行 gRPC `Send` | 0.025/0.05 ms | 0.025/0.05 ms | 单次本地调用短；不代表远端已收取 |
| Agent 上行分派整体 | 10/20 ms | 20/40 ms | 长尾与发送锁同档 |
| Agent 下行 Socket 写出 | 0.025/0.25 ms | 0.025/0.25 ms | 本轮无相近长尾 |
| Game 从流读取后入邮箱 | 0.01/0.025 ms | 0.01/0.025 ms | 入邮箱不是本轮显著等待点 |

两台 Agent 在诊断区间分别记录约 619.6 万和 619.8 万条已接受上行，发送锁抽样数分别为 96,807 和 96,847；锁等待均值分别为 1.48/2.25 ms，而 `Send` 均值仅 0.0084/0.0090 ms。Game 两进程的入邮箱直方图计数分别约 620.8 万和 618.3 万，P99 均落在 0.025 ms 桶内。MsgQ 的客户端会话下行发布未报错。不同节点的计数边界含预热和观测时差，不能逐项强制相等。

客户端使用自身单调时钟测量计划时隙到发起 Ping、以及发起 Ping 到 `socket.write` 回调。A/B 的计划发起延迟 P95 为 28.1/30.2 ms、P99 为 61.4/73.3 ms；本机写入回调 P99 为 0.049/0.045 ms。原始样本中少量负的计划偏差表示计时器略早唤醒；本地代码已把这种提前量按 0 延迟记录，**不会改变本轮正值 P95/P99**。客户端计划延迟解释了部分“未发出”与发生器容量压力，但已完成请求的往返 P99 从实际发起后计时，不能把计划延迟与 90/102 ms 直接相加。`toHandler/fromHandler` 包含跨主机墙钟偏移，不能据此单独归因前后半程。

当前证据把一个明确的服务端等待点缩到 Agent→Game 单目标共享流的发送锁：每台 Agent 约十万条上行/s，单次 `Send` 很短，但在并发调用下等待锁出现 20–40 ms 的 P99 桶。Game 入邮箱与 Agent 下行 Socket 写出没有同量级等待。同时客户端发生器本身也有 61–73 ms 的计划发起长尾。此前固定八流候选虽使局部锁等待下降，却使端到端结果变差，故本轮结果**不支持直接恢复八流方案**。

下一项应针对这个已定位的串行点提出一个保持每 Session 顺序和现有错误边界的最小发送方案，先用同负载 A/B 同时看锁等待、Agent CPU、客户端未发出和往返 P99；只减少发送锁等待不算通过。客户端发生能力也要独立验证，否则无法把 99.99% 完整率不足全部归因到服务端。不要继续通过固定分道数或 worker 数搜索局部最优。
