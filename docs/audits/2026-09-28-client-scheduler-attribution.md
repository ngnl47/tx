# 六机 20/50 客户端未发送归因

承接 [Game→MsgQ 下行发布流回测](2026-09-28-publish-stream-backpressure-ab.md)。固定六机服务拓扑与修复版 Game 二进制：两台 Agent 各 P8，Game 和 MsgQ 各两进程 P4，两台客户端合计 10,000 条 TCP 会话，每会话计划 20 条上行/s、平均 50 条下行/s。角色夹具每轮重置；下列 60 秒轮只改变客户端诊断开关、角色分配或 worker 数。原 180 秒无诊断轮客户端 A/B 分别未发送 15,421/18 条，已发送失败均为 0，计划完成率 99.957114%，尚未达到 99.99%。脚本、结果及服务采样保存在 `tx-artifacts/cloud-20260928-publish-ab/`。

调度诊断将 A 的 11,211 条未发送全部记为错过计划时隙；其中只有 1 条紧随每会话四条在途上限等待，全部 worker 的容量等待合计仅 7 次、约 176 ms。B 的 3,986 条中有 3,975 条错过时隙、11 条停在窗口末，容量等待仅 1 次、约 27 ms。两机本地 Socket 写入抽样 P99 分别为约 0.044/0.040 ms；计划时隙到发起 Ping 的抽样 P99 分别为约 85/69 ms。A 的八个 Node 事件循环利用率约 66.6%–68.2%，延迟 P99 约 33.6–41.3 ms；B 分别约 62.4%–64.6% 和 27.2–34.3 ms。`vmstat` 测量窗口 CPU steal 均为 0，A/B 平均 CPU idle 约 31%/34%；这些值不能解释所有短时停顿，但不支持“单会话在途上限堵住发包”的判断。

角色区间交换后，A 仍未发送 6,520 条，B 仅 4 条；两台客户端各自分到两台 Agent 的会话数仍接近一半。该轮两机容量等待均为 0，A 的多个 worker 事件循环最大停顿为 126–197 ms，B 为 62–104 ms。故未发送偏差跟随客户端主机及其收发调度，而非原角色区间或单个 Agent。诊断未再把客户端内核收包、Node 回调执行与宿主机调度完全拆开，不能进一步断言唯一物理根因。

Node GC 日志中的最长单次 Scavenge 暂停约为 A 43 ms、B 39 ms，小于上轮 A 的多次超过 120 ms 的事件循环停顿；GC 不能单独解释长停顿。CPU profile 中开销分散在 Socket 写入、协议解码、回调、微任务和 GC，没有一个可凭本轮证据直接删除的客户端函数。两种画像都会抬高负载，不能把它们的漏发量当作容量值。

同为无客户端诊断的 60 秒控制轮下，A 从 5,000 降为 4,000 会话后，未发送由 9,385 降至 37；B 从 5,000 升为 6,000 后，由 1 升至 17,156。8→16 worker 没有改善，A/B 分别升至 37,575/4,789。两种调参都未让合计计划完成率达到 99.99%，因此不改默认 worker 数，也不将不均分配作为正式压测配置。上述各轮服务端已收到的请求均完成，失败为 0；这不能替代按计划请求数计算的端到端验收。

结论：修复版 Game→MsgQ 发布流的 180 秒收益仍成立；剩余未发送首先受当前两台客户端发生能力和调度长尾限制，不能据此宣布 Agent、Game 或 MsgQ 已达到容量极限，也不能宣称万连 20/50 已通过。继续正式容量验收时，应先提供独立的第三台客户端发生器，将 10,000 会话更均匀地分摊，再保持服务端实例数、二进制、总负载及三分钟窗口不变；额外客户端只用于供给负载，不计为生产服务扩容。若仍有已发送请求长尾，再依据同窗服务指标定位服务端。所有本轮业务进程已确认停止，专用角色夹具已执行 `cleanup`；中间件容器保留。
