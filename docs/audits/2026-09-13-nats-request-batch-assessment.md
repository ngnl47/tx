# NATS 请求封包合批评估

## 结论与状态

建议只做一次“请求合批、回复逐条发送”的隔离验证，暂不做双向合批。它能减少请求方向的 NATS 消息数、主题匹配和订阅回调次数，而 T3e 只减少了连接 Write 次数。收益空间存在，但需要额外的封包和批次错误关联，是否值得采用必须由完整 RPC 对照决定，不能根据消息数直接预测吞吐提升。

本轮是评估与计划补充，没有实施新协议、修改 Go、运行 benchmark 或重跑功能测试。2026-09-13 核对：tx HEAD=974146c，T3d–T3e 变更仍未提交；tx、txgame、txgameslg 位于 `feature/nats-actor-runtime`，其余五工程干净。六工程 AGENTS.md 已重新读取。T4 继续暂停，原有 10% 筛选线不变。

本评估使用当前代码、README 和计划；[T3d](2026-09-12-nats-rpc-path-differences.md)、[T3e](2026-09-12-nats-fixed-sender.md) 的数字仅作为已有实验记录引用，不是本轮新测结果。

## 已核验的链路

- [Transport](../../internal/actortrial/nats.go) 已经按 namespace 与启动时唯一 InstanceID 生成实例主题；目标 Actor 身份放在 Actor-Identity 头中。批量归组可以复用已解析的 Target.Instance，不需要 game 提供批量接口，也不引入 Queue Group 重新选择 owner。
- CallFuture 克隆 Delivery、设置 CALL 模式，再将请求关联到本连接的唯一回复地址；一个通配订阅复用 pending 表。发送失败、取消、回复和关闭共用清理入口。本地 Call 仍直接进入实体队列。
- [Runtime](../../internal/actortrial/runtime.go) 在逐实体 submitRequest 时执行准入，回复回调在 worker 内完成；Drain 等这些 worker 和卸载回调结束。
- [SlotHost](../../internal/actortrial/slots.go) 在工厂前检查槽位归属，quiesce 排空并完成必要收尾后才确认交接。合批不能缓存新的 owner、绕过归属检查或在响应未知后改派。
- 锁定的 ProtoActor endpointWriter 不仅合并 Write，还构造 MessageBatch，批内索引共享目标、发送者和类型。T3d 中关闭该批处理会改变多项封包成本，所以它不是“同一个 NATS 发送队列只缺一处调参”的证据。

NATS 的一次 PUB/HPUB 有一个 Subject 和一个可选 Reply，服务端接受的消息大小由 max_payload 限制。将多条 RPC 放入一次 Publish，内层身份与请求关联就成为 tx 的协议职责。[官方客户端协议](https://docs.nats.io/reference/protocols/client)

无订阅者时，broker 向该次请求的 Reply 返回 503；它不会理解用户自定义批包，替 tx 逐条回复。[官方 Request-reply 说明](https://docs.nats.io/learn/core-nats/request-reply#no-responders)

## 三种选择

| 选择 | 能减少什么 | 新增职责 | 建议 |
|---|---|---|---|
| 保持当前路径 | 无新增协议成本 | 无 | 保留为对照，候选无明确收益就继续使用 |
| 请求合批、回复逐条 | 请求方向的发布、匹配与回调次数 | 有界发送队列、封包、整批传输错误关联 | 推荐的最小实验 |
| 请求与回复都合批 | 两个方向的消息处理次数 | 还需结果队列、独立结果合批及相应排水接线 | 暂缓，先验证请求方向是否值得 |

回复不能等同批所有 Actor 结束再一次返回。那会把快请求绑定到最慢请求，并扩大超时影响。未来即便评估回复合批，也只能合并当时已经完成的结果，不能增加“整批业务完成”屏障。

## 建议的最小协议

业务侧仍逐条调用 Call、CallFuture、Tell、TellAccepted；Actor 身份、GD、Procedure、Session、Seq/Ack 和高级 SPI 均不变。

批包使用当前实例主题，通过一个实验格式标记区分普通消息和批包，共用同一个接收订阅，避免两个订阅回调导致同一实体的混合投递乱序。每条请求保留原 Actor-Identity、原 Delivery 字节和独立 Reply；目标拆包后复用现有身份解析、Delivery 解码、submitRequest 和回复逻辑。首轮不同时优化 JSON/base64 身份编码，也不覆盖业务信封中已有的 RequestId。

封包复用已锁定的 protobuf 工具链，在实验范围维护定义与生成物；不修改现行 actor.proto，不手写一套二进制序列化框架，不引入协议协商或永久双后端配置。未知批包格式和损坏的外层编码在投递任何业务前明确失败；合法外层中的无效身份或 Delivery 只使对应项失败。

外层 Reply 使用当前 inbox 通配符能匹配的单个末尾 token，例如 `inbox.b42`；普通请求继续使用 `inbox.123`。不能写成 `inbox.batch.42` 却继续订阅 `inbox.*`。外层地址只承担整批拒绝/解码失败等传输错误，正常结果仍发送到各项原有 Reply。

保留必要的一份批次关联：`批次 Reply → 仍在等待的请求`。它在 Publish 前登记，与现有 pending 使用同一并发边界；每项完成或取消时解除关联，最后一项结束即释放批次记录。批次只保留等待关联，不保留已发送载荷或历史结果；批次数及成员引用必须受 maxPending 和实验批量上限约束。不能依赖“第一项还活着”来保留整个批次，也不增加定时清扫器、重投队列、持久完成表或全局事务。

## 发送时机、顺序与资源

沿用一条连接一个发送协程的实验思路，只取队列中当时已有的工作；不等游戏帧，不用定时器凑批，不等待达到最大条数。

建议实验上限为每次取出 64 项、每个批包不超过 64KiB，并服从当前 Conn.MaxPayload，计算时包括 NATS 头。发送队列总条目数沿用 maxPending，已编码消息的字节预算取 `max(4MiB, Conn.MaxPayload())`，避免实验预算使原本合法的单消息永远无法入队；这些是实验值，不是生产默认值或 game 配置项。条目数与字节预留必须在同一个准入边界内检查，取出处理后归还队列预算，正在封包的工作另受 64 项上限约束。

每次取出的有限工作按目标实例稳定归组，保持同一实例内的原投递次序；不创建长期的每实例 goroutine 或队列。Call/CallFuture 请求可合批。Tell、TellAccepted 作为同实例顺序中的单条发送边界：先发此前的 Call 批，再发送该条，不能让它绕过已有队列抢先发出。不同实例之间不增加全局顺序保证。回复、Probe、初始化状态查询和槽位控制保持独立的原有处理路径，不等待业务凑批。

单条请求大于 64KiB 时，只要当前普通消息和实验队列预算允许，就沿原有单条格式发送；超过当前 SDK max_payload 则明确报错。不能因为候选批量上限而降低原有单消息契约，也不能把一个 RPC 拆成多个需要重组的分片。重连导致上限变化时，以实际 Publish 返回的错误结束相应等待，不自动拆包重发。

首轮维持现行本地 Publish 完成后返回的边界，不同时改变 Future 时机或回复 worker 的完成点。因此同一协程逐次调用 Call，或每次等本地发送后才创建下一个 CallFuture，都不能假定会形成批量；机会主要来自同时存在的独立调用。实际平均批量必须测量，最大值 64 不代表通常能达到 64。

## 失败与排水

| 情况 | 处理 |
|---|---|
| 队列满、字节预算不足、编码或本地 Publish 失败 | 明确结束对应调用的本地等待与 Future；批内正常项不得伪装成功；不重投 |
| broker 返回外层 503 | 通过批次关联结束该批仍在等待的 Call；不依赖第一项是否已取消 |
| 一个 Actor 加载拒绝、邮箱满、业务报错或 panic | 只结束该项，其他项继续走各自运行时边界 |
| 一项取消、超时，随后结果迟到 | 清理该项及其批次引用，迟到结果忽略；不推断业务未执行 |
| 连接关闭、发布后结果未知 | 按现有关闭和 deadline 边界结束等待；可观察发送错误记日志，不自动改派或补发 |
| TellAccepted 没有目标订阅者 | 仍可在本次 Publish 后经 Flush 确认到达 NATS；不能等待目标执行或把批次 503 改成该方法的前置条件 |
| 接收一个批包途中开始排水 | 逐条准入：已准入项继续完成，后续项拒绝；批包不是原子事务。连接关闭时拒绝响应可能无法送达，调用方仍可能超时 |

正常关闭继续先封闭 Actor 准入，等待现有 worker、回复和卸载前 RPC 结束，再完成必要持久化。回复逐条发送并留在原回调内，所以不需要新增 Actor 业务完成计数。持久化失败时，连接和发送器必须保留。

持久化成功后，传输层停止新发送准入、排完已有发送队列，最后 Flush 并关闭连接；发送队列等待使用关闭上下文，不无限阻塞。该等待只覆盖新增的本地发送阶段，不等待全部远端业务结果。SlotHost.quiesce 也要核对同一顺序，并保留交接控制连接；不能只修改 Transport.Drain 就宣称交接已验证。

当前隔离基线没有启用 NATS 权限配置。批内 Reply 放在 payload 里，不能假定 NATS 的动态响应授权会自动识别；正式采用前需确认服务拥有对应回复主题的发布权限。这是封包引入的真实接线差异，不在本次评估中扩展成新的鉴权系统。[官方授权说明](https://docs.nats.io/learn/security/authorization)

## 验证范围与停止条件

如果继续实施，先完成能复现关键边界的最小检查：同批多实体独立结果、快慢请求不互等、第一项取消后整批 503、部分失败、预算拒绝与释放、混合 Call/Tell 顺序、发送失败回收、断线未知结果不重投，以及回复/卸载 RPC/持久化失败时的排水。原有真实 NATS、etcd、Redis 回归与 race 必须继续运行；这些不能由空回显 benchmark 代替。

性能首先比较三组：当前原型、新封包但强制每批 1 项、新封包最多 64 项。后两组使用相同发送队列和关联逻辑，只改变批量上限，避免把格式变化、队列成本和合批收益混成一个数字。协议层旁路不能冒充完整实体运行时。

先以单 broker、独立调用端和目标端、128B、1000 身份、64 并发，在 GOMAXPROCS=1/4 下各交替五轮；三进程同样设置 GOMAXPROCS，始终不是 1/4 个 NATS 节点。各组使用相同长度的主题和实例名，轮次只在容器标签与材料文件名里区分，消除 T3e 的组名前缀长度差异。

有明确收益后，再补 1/16 并发的延迟边界、1KiB 载荷、多个目标实例使批量变小的负载，并以同批 ProtoActor 重做筛选。没有收益就停止，不自动推进双向合批、改写调度器或添加条件配置；T4 的正确性和 10% 性能筛选线不变。

正式样本记录完整成功 RPC/s、P50/P99、错误、两端 Go 分配/CPU/堆及 broker CPU/RSS。平均批量、连接 Write 和封包字节单独诊断，不把计数器混入正式中位数。请求批数为 Q、逐条回复数为 N 时，正常基准窗口的 broker 入站和出站应各为 Q+N，不能再沿用 2N 断言；保留逐项 payload 校验与 N 份成功延迟样本，防止把“一批完成”错算成 N 次成功。

例如 16 个独立调用恰好发给同一实例并形成一批，请求与回复消息数从 32 变成 17，减少 46.875%。这只是该假设下的消息数计算，既不是吞吐提高 46.875%，也不表示 16 个业务合成一个事务。
