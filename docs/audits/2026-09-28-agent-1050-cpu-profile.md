# 万连 10/50 的 Agent CPU 画像

## 条件和结果

四台 8 核 16 GiB 云实例分别承载 Agent/Login、Game、MsgQ/中间件和 TCP 客户端发生器。Agent 为单进程 P8，Game、MsgQ 各两进程 P4；客户端 16 个进程建立 10,000 个 Session，以每 Session 10 上行/s、每上行 5 下行运行 90 秒。三轮均重置同一测试夹具，使用相同的真实业务和网络链路。`r2` 关闭画像，`r1` 使用原诊断入口，`r3` 仅移除诊断入口中的锁与阻塞采样后抓取 30 秒 CPU。三轮都没有业务失败；`status=failed` 是最终完整处理率未达到 99.99% 验收线，不表示已发送请求执行失败。

| 轮次 | 最终完成 / 计划 900 万 | 未发送 | 客户端 P99 | Agent / 客户端平均 CPU | Game / MsgQ 合计平均 CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| `r2` 无画像 | 8,937,859（99.31%） | 62,141 | 452.92 ms | 7.67 / 7.72 核 | 4.10 / 3.78 核 |
| `r3` CPU-only 画像 | 8,305,300（92.28%） | 694,700 | 779.68 ms | 7.71 / 7.74 核 | 3.73 / 3.59 核 |
| `r1` 原画像入口 | 6,925,157（76.95%） | 2,074,843 | 1,144.02 ms | 7.81 / 7.92 核 | 2.98 / 2.96 核 |

CPU 数取正式窗口第 10–80 秒的 `pidstat` 均值。无画像轮的窗口完整上行约 99,236/s、下行约 496,179/s；其 6,640 条上行在正式截止后完成。三个轮次的已发送上行最终全部完成，失败计数为零。画像会明显扰动饱和负载：即便仅保留 CPU 采样，完整处理率仍比无画像轮低约 7 个百分点。因此画像只用于定位热点，不能作为优化前后的吞吐对照。

## 热点归因

CPU-only 画像覆盖正式窗口内 30 秒，采集 233.62 CPU 秒样本。`writeDownMsgs` 调用树占 41.06%；其中 `writev` 的 Linux 系统调用栈占总样本约 19.15%。上行 `dispatchUpMsg` 调用树占 20.65%，`grpcMailboxStream.readLoop` 占 12.92%。`gcAssistAlloc` 累计占 10.49%，它与业务调用树有包含关系，以上比例不能相加为整体分布。先前带锁/阻塞采样的画像也把下行 Socket 写出列为第一热点，但它对吞吐扰动更大。

同轮累计分配快照约 23.84 GiB；其中 `context.AfterFunc` 约 1.86 GiB，`tcpTransport.Write` 自身约 1.32 GiB。快照包括进程启动至采集时的所有分配，不能把这些数字直接解释为每秒分配。当前 TCP 读与写每帧都会注册取消回调，写出后还重置 Deadline；这是可量化的次级候选，但取消必须仍能打断阻塞的 Socket I/O。

无画像轮的两个 Agent `/metrics` 样本之间，成功写入 31,474,447 个下行帧，记录 10,315,756 次下行写操作，平均每次 3.05 帧；失败写入为零。这个计数是应用层写操作，不直接等于内核系统调用次数。此前同版 10/10 轮为约 1.00 帧/写，10/50 轮为约 2.97 帧/写。当前已经通过 `TryRecv` 把即时可用的帧合写，继续增大固定帧数上限不一定能减少写入次数；需要观察帧到达时序和实际批次分布，避免只对五条 Ping 下行过拟合。

结论是单 Agent 在该档位接近 CPU 上限，下行 TCP 写出是最明确的服务端热点；同时客户端发生器也接近 8 核，单凭本轮端到端延迟不能把全部长尾归因于 Agent。Game 和 MsgQ 仍有余量。下一项应先提供独立的客户端发生能力，再针对下行写入做同版本短 A/B：以每次写入帧数、Agent CPU、完整处理率和 P99 同时验收。优先评估减少每帧的取消/Deadline 设置成本与不增加固定等待的合写机会；任何代码变更都须保持慢客户端取消及排水边界。不为单一 10/50 档位写死合批参数。
