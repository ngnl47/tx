# 四机万连不对称上下行回测

## 测量口径

四台同 VPC 的 Ubuntu 24.04、8 核 16 GiB 云机分别承载 Login×2+Agent×2、MsgQ×2 与中间件、Game×2、客户端。Agent 的 `GOMAXPROCS=4`，MsgQ/Game 为 2。全部客户端使用 TCP；按每秒 500 次建立连接，在 10,000 会话就绪后预热 2 秒，再开始正式窗口。客户端由 2 或 4 个 Node 进程分片；表内记录实际进程数。Agent 上行经 gRPC 直达 Game，Game 下行经 gRPC 发布到 MsgQ，Agent 经 `FetchSome` 读取后写回 TCP。`directCallBatch=false`；表内 Unary 或 Stream 仅指 Agent→Game Actor 的直连传输，NATS 不参与上下行。

本轮为不对称负载增加了隔离的 `txbench` Ping 行为：每个 `System_Ping` 按上行 Seq 奇偶生成 1 或 2 条 `GlobalNotify`，再返回 `System_Pong`。客户端逐条检查通知对应的 Seq 与数量，收到 Pong 后才算本次请求完成。每两个 Ping 共 5 条下行，因此目标 20 上行/s、50 下行/s 可用同一条真实下行链路建模。偶数次 Ping 的会话总数恰为 2.5 倍；奇数次时受各会话起始 Seq 影响，不能要求总数严格等于 2.5 倍。`downCompleted` 统计客户端已处理且对应 Ping 完成的下行，不等于 MsgQ 已收到每条 ACK 的独立证明，也不覆盖 MMO 广播或业务计算。

Game 使用带 `txbench` 标签且设置 `TXBENCH_PING_EXTRA_DOWN=1` 的测试二进制；普通构建中的同名辅助函数为空，不生成额外下行。旁路编排器和资源采样在 `tx-artifacts/cloud-20260924-downlink/`，不接入服务业务路径。云端中间件与角色夹具为专用 Redis DB12、Mongo `txgame_cluster_e2e`、etcd `/tx/e2e/txgame/`。首次冒烟在 Game 二进制重启后因旧槽位实例 ID 返回 `discovery: slot runtime is unavailable`；它发生在负载前，不计入容量结果。八服务全停后重建专用夹具并重新准备 10,000 个角色，后续冒烟通过。

## 无采样结果

Stream 的 2.25/s、20 秒档因旁路编排器误以为下行总量必须严格等于上行的 2.5 倍而返回失败；客户端逐条校验与总计数都通过。编排器已改成检查上下界，随后同档 60 秒复测正常通过。多进程客户端还修正了另一处结果判定：未发送请求现在会使 `status=failed`，业务测量失败仍汇总写出 `client.json`，异常子进程退出仍终止同轮其他进程。表中早于该修正的 `status=passed` 若 `未发>0`，按未达标解释。

按既定的零业务失败、零未发、P99≤60ms 条件，这套四机拓扑目前观察到的 60 秒通过档为 22,500 上行/s、约 56,248 下行/s。目标万连 20/50 对应 200,000 上行/s、500,000 下行/s；当前通过档约为目标频率的 11.25%。这里没有测得生产容量：Ping 几乎不做业务计算，也没有真实 MMO 广播、持久化压力和长时运行扰动。

## 热点与下一步

同为 10,000 会话、3/7.5/s、四客户端进程、20 秒时，Unary 的 P50/P99 为 88.17/204.96ms，Stream 为 45.28/146.54ms。Agent 两进程 CPU 之和按 `pidstat` 每秒样本均值约从 610% 降到 569%；两轮均未达到 60ms 且分别有 19、5 次未发，不能据此宣布该档通过，也不能把单轮差异当成稳定收益。四客户端进程的事件循环利用率约 60%，两客户端进程的同档约 92%；增进程能降低一部分长尾，却没有消除服务端路径成本。

另在 10,000 会话、3/7.5/s、30 秒诊断轮中，随正式窗口启动采集两台 Agent 各 10 秒 CPU profile。两个 profile 的采样时间均落在正式窗口内：每台采样约 33.6 CPU 秒/10 秒，`grpc.ClientConn.Invoke` 累计约 47%–48%；其中 `FetchSome` 路径约 23%，Actor 直连 `Call` 路径约 18%–19%。这些累计占比存在调用栈重叠，不能相加。`runtime.mallocgc` 累计约 29%–31%，提示分配与 GC 成本也值得继续拆解。诊断轮的 profile/锁采样会影响性能，不并入上表无采样 A/B。

下一项建议先量化 `FetchSome` 的返回批量分布、每条下行对应的 gRPC 调用数及分配来源，再评估能否在现有可靠 Seq/Ack 和重连边界下减少重新建流；不要仅凭 CPU 累计比例直接替换成下行推流。目标先验证 Agent→MsgQ 这段的真实成本与可收敛空间，再决定协议改动。当前没有证据要求调整业务侧 GD、Actor 邮箱或 NATS 路由。

试验完成后，接入机恢复 `directCallStream=false`、`directCallBatch=false` 并关闭 pprof；Game 恢复原二进制 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，客户端恢复试验前源码。八服务全停后重建专用归属并重新准备角色；恢复态 100 会话、1/s、5 秒原始 Ping/Pong 冒烟 500/500 完成，零失败、零未发、P99 0.974ms。所有试验原始客户端 JSON、四机采样和对齐后的 Agent profile 均留在工作区 `tx-artifacts/cloud-20260924-downlink/`。
