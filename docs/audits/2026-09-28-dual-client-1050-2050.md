# 双客户端万连 10/50 与 20/50 回测

## 条件与结果

2026-09-28 使用六台腾讯云 SA9 8 核 16 GiB 实例，其中两台分别运行 5,000 个真实 TCP 客户端会话。接入机运行 Login×2（P4）与 Agent×1（P8），另一台只运行 Agent×1（P8）；Game×2、MsgQ×2 各为 P4，分别运行在独立游戏机和存储机。Login 将 10,000 个会话恰好分配到两个 Agent，各 5,000。客户端每台 8 个 worker、建连 250/s，每会话最多 4 条在途请求，预热 2 秒，正式窗口 180 秒；没有启用 pprof 或逐消息诊断。业务机低频抓取 `/metrics` 并采集进程/宿主机资源。所有通信走同 VPC 私网。

10/50 每条 Ping 产生一个 Pong 和四条 `GlobalNotify`。20/50 使用只在 `txbench` 构建和显式环境值 `alternate` 下启用的业务下行模式：按上行序号奇偶交替产生 2/1 条附加通知，与已有客户端 `--extra-down` 的期望一致，平均每条上行产生 2.5 条下行。8 会话冒烟确认 80 条上行、200 条下行全部完成。首次准备正式轮时冒烟角色与其中一个 worker 的角色段重叠，该 worker 在准备阶段超时；两者的因果关系未确认，这轮没有进入正式计时。随后停止全部业务服务并重置专用夹具，正式轮的 16 个 worker 均就绪。20/50 的 Game 构建 SHA-256 为 `1cfef2e47a9a1f8bf53007450686c53fc3bff52038573e8107f63cfba85fa902`，其余业务进程及 10/50 的构建为 `e9f09c12640657d69bb5d07e083c5b584c5bd85e89cbc135ee9946ab0cf784fe`；本次工作区只调整 `txbench` 下行数量，正式业务传输路径未改。

CPU 使用量由正式窗口内的进程累计 CPU 差分估算，直方图 P99 用 Prometheus 桶内插值，均非逐请求精确追踪。20/50 时 Agent 上行分派与客户端调度均出现明显排队迹象；客户端平均 CPU 尚未打满，但瞬时可运行进程数超过核心数。Game 与 MsgQ 的 CPU 仍有余量，不能据此断言它们绝无局部队列。当前数据不足以将端到端长尾唯一归因于 Agent、客户端、内核网络栈或链路中的某个等待点，不继续只靠调速率寻找极限值。

本轮 10/50 是一次三分钟验收，不代表生产长期稳态或真实 MMO 业务计算能力。20/50 接近目标**发送速率**但未达完整率和延迟门槛。下一项应固定 20/50 负载和部署，补 Agent 分派等待与客户端 worker 调度的低扰动分段证据，再选一个明确成本点做同版 A/B；不通过单纯增加实例来替代定位。
