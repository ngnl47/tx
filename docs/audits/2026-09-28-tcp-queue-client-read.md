# 20/50 下行 TCP 队列与客户端读取复核

本轮延续[客户端帧边界复核](2026-09-28-client-frame-stage.md)的六机拓扑、同版服务二进制和两个各 5000 会话的 TCP 客户端，正式窗口为 60 秒、每会话 20 上行/平均 50 下行。业务代码和发送策略未改；四台 Agent/客户端主机每 2 秒用 `ss -Htn state established` 读取一次 5000 条客户端连接的 Recv-Q、Send-Q，仅存聚合值。各主机显示 NTP 已同步，但仍未逐帧校准时钟偏差。

第一次采样脚本错把 `ss -H` 输出的第二、三列当成 Recv-Q、Send-Q；原始输出证实**第一、二列**才是这两个队列。该轮队列数据全部废弃，未参与下表。停止所有业务进程并清理专用夹具后部署修正版，重新 `prepare`、启动并准备 10000 角色，才取得本轮有效队列数据。脚本及原始 CSV 保留在工作区 `tx-artifacts/cloud-20260928-dual-client/tcp-queue-corrected-20260928/`。

| 客户端 | 完成上行 / 计划上行 | 未发送 | 上行完成 P99 | 已收下行 | 业务请求失败 |
| --- | ---: | ---: | ---: | ---: | ---: |

两客户端均因**计划完成率未达到 99.99%**而报告 `failed`，不能把本轮当作 20/50 容量达标。`未发送` 是客户端错过计划时隙，不是已发送业务请求丢失。

原始 Pong 帧进入客户端 `onFrame` 前的 `Pong.ServerTime`→帧时间 P99 在 A/B 为 78/57ms（分别约 2908/2910 个请求样本）；帧进入回调→请求完成的 P99 为 0.038/0.030ms。A 的计划发起延迟 P99 为 74.44ms，B 为 42.12ms。逐秒事件循环 P99 的中位数分别为 27.51/22.38ms。这与上一轮一样把长尾限定在客户端回调之前，并显示 A 的客户端排程比 B 更慢。

Agent 的 Send-Q 是 TCP 尚未获得确认的字节，不能等同于应用协程被 `Write` 阻塞；本轮 Agent socket 写入调用 P99 桶上界仅 0.25ms。Client Recv-Q 中已有到达本机内核、尚未由客户端读取的数据。A 的 Recv-Q 峰值及受影响连接数均明显高于 B，同时 A 的事件循环和帧到达长尾更高，支持**客户端读取调度参与长尾**。按 2 秒快照粗略配对，Client A/B 的 Recv-Q 合计与所在秒事件循环 P99 相关系数约为 0.46/0.29；与邻近帧样本 P95 约为 0.17/0.43。这些相关性样本少、时间分辨率粗，不能推导出逐消息因果，也不能把全部 78/57ms 归因于客户端。

同轮应用层直方图中，Game Actor 邮箱等待及 Game→MsgQ 发布队列 P99 桶上界均为 20ms；MsgQ 发送队列为 2–5ms，Agent 会话接收队列为 10ms。这些仍是潜在贡献者。不同队列的 P99 不属于同一消息，不能相加。当前可以排除“客户端帧已经进入回调后才积压几十毫秒”，但**Agent 写出→客户端内核收包→客户端回调**尚未有同一 Seq 的三个时间戳，不能继续把网络、内核发送缓冲与客户端事件循环拆开。

如继续定位，应对少量 `RoleID + DownSeq` 记录 Agent socket 写出时间、客户端帧回调时间，并优先取得客户端内核收包时间或同连接的 TCP 级时间戳作为中间边界；先校准跨机时钟，再评估探针负担。不要仅凭 Send-Q 字节总量调整 gRPC 流数或合批阈值。本轮采样结束后，业务服务按 Agent/Login → Game → MsgQ 顺序停止，专用夹具已 `cleanup`，四个采样进程均已退出；中间件容器未改动。
