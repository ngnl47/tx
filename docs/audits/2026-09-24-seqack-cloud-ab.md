# Seq/Ack 简化后的四机链路回测

## 对照范围

在同一组四台 8 核 16 GiB 云主机上，按 Login/Agent、MsgQ/依赖、Game、客户端分机部署。两台 Agent 的 `GOMAXPROCS=4`，两台 MsgQ 与两台 Game 各为 2；Agent→Game 直连合批和直连长流均关闭。客户端走 TCP，10,000 个独立 Role Session 平分到两台 Agent。每个 Ping 对应一个 Pong，未增加压测专用业务实现或生产采集入口。

基线取 `tx` 的 `74d03bc`、`txgame` 的 `8838975`、`txclient` 的 `c8fd366`；候选在同一基线之上叠加本轮未提交的 Seq/Ack 变更。两套服务端均在同一云机以 Go 1.27.0、`CGO_ENABLED=0`、`-trimpath -tags txbench` 构建，二进制 SHA-256 分别为 `f5e16fd23b985f4e5ede856df3e9a4de9e382f4cf6e255e8c7643015d9d2ddfe` 和 `ff17326b599910a60e1bc3d9288f9f5d09c7c39f2e96c991dc5263576670e43e`。两版客户端均复用同一 Node 依赖锁文件；压测脚本差异仅为客户端源码目录。候选生产路径仍逐条调用 MsgQ `Rec`，未引入 Agent 租约或 `Rec` 长流。

压测编排与 vmstat/pidstat 采集留在 `tx-artifacts/cloud-20260924-seqack/` 旁路目录，不进入服务二进制的采集路径。固定 `--connect-rate 500 --warmup-ms 2000 --request-timeout-ms 5000`，两个客户端进程，每会话每秒 3.75 次。30 秒窗口按当前生成器的整数计划数为每会话 112 次，即合计 1,120,000 次；10 分钟窗口为每会话 2,250 次，即 22,500,000 次。

## 环境归属与无效尝试

第一次基线建连约 6,500 个角色时，Agent 返回 `discovery: slot runtime is unavailable`，未进入计时窗口。检查发现专用测试 etcd 中 1,014 个 `role` 分区归属里，94 个仍指向上一轮已退出的 Game InstanceID；当时 Redis 测试角色归属与 Agent TCP 活跃连接均为零。只删除测试前缀 `/tx/e2e/txgame/discovery/slots/actor-v1.cm9sZQ.p` 下的 1,014 个旧归属，再做基线冷分配；两台当前 Game 最终各承接 512 个分区。切换候选前也在服务全停、会话归属清零后删除相同前缀下的 1,024 个分区，使两版处于相同冷分配条件。这次失败不计入 Seq/Ack 性能结论，也说明持久槽位归属在旧 owner 消失后不会自动改派。

## 正式结果

| 版本 | 窗口 | 完成/计划 | 上行与下行完成率 | 失败/未发送 | P50/P95/P99 | 接入机 CPU 空闲 |
| --- | --- | ---: | --- | ---: | --- | ---: |
| 基线 | 30 秒 | 1,120,000/1,120,000 | 37,333/s；基线客户端未单列下行计数 | 0/0 | 2.708/25.858/36.291 ms | 35.0% |
| 候选 | 30 秒 | 1,120,000/1,120,000 | 上下行各 37,333/s | 0/0 | 2.927/28.816/38.567 ms | 30.7% |
| 候选 | 10 分钟 | 22,500,000/22,500,000 | 上下行各 37,500/s | 0/0 | 3.651/30.780/41.962 ms | 29.4% |

短轮候选 P99 比基线高 2.28 ms，接入机 CPU 空闲低 4.3 个百分点；单次 30 秒对照不足以将差异归因于 Seq/Ack 代码，也没有证据表明吞吐上限因此提高。候选 10 分钟档完整达到已有的零失败、零未发送、P99≤100 ms 门槛，也低于讨论中的 MMO P99≤60 ms 目标；但仍有 42,909 次超过 60 ms（0.191%）、7,770 次超过 100 ms（0.035%），最大 389.556 ms。该长轮接入机、存储机和 Game 机的平均 CPU 空闲分别约 29.4%、66.1%、73.1%；这只表明本档整机未打满，不构成更高档位容量预测。长轮只跑了候选版，不能把它与旧日期、不同代码与环境的十分钟结果当作严格 A/B。

原始客户端报告与四机采样分别保存在 `tx-artifacts/cloud-20260924-seqack/seqack-controlled-before-375-v2/`、`seqack-controlled-after-375/` 和 `seqack-controlled-after-375-10m/`。三次有效运行都在完成后释放 Redis 测试角色归属。当前云端留下候选版二进制，服务保持运行；本地三工程变更未提交。

## 从高负载向下定位的短轮

沿用同一候选服务端、四机拓扑与 1:1 Ping/Pong 业务链路；为排除单个客户端进程先饱和，将旁路发生器从两个进程改为五个进程。仍为 10,000 会话、500 会话/s 的建连配置、2 秒预热、5 秒请求超时；下表每次均在前次角色归属释放后重新建连。短轮只用于定位区间，不代表十分钟稳态容量。

| 每会话速率 | 窗口 | 完成/计划 | 失败/未发送 | P50/P95/P99 | 接入机 CPU 空闲 |
| --- | --- | ---: | ---: | --- | ---: |
| 10/s | 15 秒 | 989,087/1,500,000 | 0/510,913 | 151.08/226.86/260.03 ms | 3.5% |
| 6/s | 30 秒 | 1,799,027/1,800,000 | 0/973 | 91.21/148.34/178.01 ms | 5.5% |
| 5/s | 30 秒 | 1,500,000/1,500,000 | 0/0 | 24.18/63.11/90.69 ms | 17.5% |
| 4/s | 30 秒 | 1,200,000/1,200,000 | 0/0 | 3.20/32.93/43.23 ms | 28.1% |

10/s 时客户端五个事件循环利用率分别约 68%–69%，接入机两台 Agent 合计约占 7.7 核；存储、Game 与客户端机 CPU 空闲分别约 67%、61%、49%。大量未发送源于单会话等待 Pong 后才发下一条，慢响应使计划槽位越过截止；不是把 100,000 次/s 全部送入了服务端。6/s 时接入机接近打满且 973 次未发送。短轮按零失败、零未发送及 P99≤100ms 衡量，区间落在 5–6/s；按讨论中的 MMO P99≤60ms，区间落在 4–5/s。两项都还需要长轮验证。

原始报告与四机系统采样在 `tx-artifacts/cloud-20260924-seqack/seqack-capacity-{10ps-5w-15s,6ps-5w-30s,5ps-5w-30s,4ps-5w-30s}/`，编排脚本位于 Git 工程外的 `tx-artifacts/cloud-20260924-seqack-after.py`。仅旁路脚本增加可选客户端进程数参数，没有改服务端采集逻辑。

## 十分钟复核

同版、同样五个客户端进程的 5/s 长轮，计划 30,000,000 次，完成上下行各 29,994,439 次，失败 0、未发送 5,561 次，P50/P95/P99 为 28.36/76.26/146.59 ms，最大 597.64 ms。因此 30 秒通过的 5/s 档不能作为稳态容量。接入机十分钟平均 CPU 空闲 13.7%，两台 Agent 合计约占 6.76 核；存储机与 Game 机 CPU 空闲约为 66.4% 与 64.0%。五个客户端事件循环利用率均约 55%，各有 992–1,210 个调度槽位被跳过，结束时均无在途请求。这些观测将主要压力指向接入侧，但并不单独证明是 `Rec`、Actor RPC 或具体函数造成。

4/s 长轮计划且完成上下行各 24,000,000 次，失败、未发送均为零，P50/P95/P99 为 3.62/34.42/47.10 ms，最大 148.75 ms；通过现行 P99≤100ms 门槛和讨论中的 MMO P99≤60ms 目标。接入机十分钟平均 CPU 空闲 25.7%，两台 Agent 合计约占 5.56 核；存储机与 Game 机 CPU 空闲约为 65.4% 与 67.2%。五个客户端事件循环利用率均约 38.7%，没有跳过计划槽位或遗留在途请求。长轮原始材料分别位于 `tx-artifacts/cloud-20260924-seqack/seqack-capacity-5ps-5w-10m/` 与 `seqack-capacity-4ps-5w-10m/`。

## 后续边界

本轮证明 Seq/Ack 简化没有阻断既有 1:1 万连 3.75/s 档；新的四机实测可持续通过档为 4/s，即上下行各 40,000 次/s，5/s 十分钟不满足零未发送及 P99≤100ms 门槛。容量边界只能限定在已测的 4–5/s 档之间，不能把 4/s 称为机器精确上限，也不能把候选版与基线版不同日期的结果解释为 Seq/Ack 性能收益。尚未验证 MMO 目标的 20/s 上行、50/s 下行不对称负载。下一项需评估增加 Agent 计算容量或修改逐条 `Rec` 数据路径的先后顺序；Agent 本地游标租约仍是独立设计问题，当前 MsgQ 继续持有权威上行游标、下行队列与确认裁剪。
