## 本轮代码、验证与收尾

回测前发现 `txclient` 多进程汇总没有合并各 worker 的 `completedAfterDeadline` 和 `downCompletedAfterDeadline`，会把窗口后完成误算进吞吐。先用回归用例复现，再补齐两项汇总。回测后按新的 99.99% 目标更新后续压测器：统计完整处理数时包含截止后成功完成的请求，窗口内吞吐仍排除它们；多进程以全局计划数与完整处理数判定，保留未发送计数，不让单个分片的边界缺口覆盖全局结果。显式运行错误与业务失败仍报告失败。历史两轮 JSON 没有修改，新的判定代码尚未在云端复测。`txclient` 104/104 测试、类型检查和生产构建通过。Go 侧沿用本地评审修复版，本轮没有再改业务实现。

两轮结束后正常停止 Agent、Login×2、Game×2、MsgQ×2，七个单元均为 `inactive`、`Result=success`、退出码 0；测试中间件和本地归档保留。若复用该测试环境，应先停服务、核对专用归属标记并按夹具流程重置；不要把本轮数据直接用于下一轮相同 RoleID 的热启动。

本地完整证据在 `/Users/a47/workspace/tx-artifacts/cloud-20260927-review-fixes/`：两轮客户端汇总包、R2 四台资源采样包、解析后的资源 JSON、启动脚本与配置、重置前 etcd 备份。约数百 MiB 的逐请求延迟原始数组未下载，保留在客户端云实例对应 `results/review-fixes-10k-10ps-20260927-r1/`、`results/review-fixes-10k-10ps-20260927-r2/`；若退还实例，这部分原始数组将不可再取。本地汇总与资源样本足以复核上表，但不支持重新计算任意分位数。

结论仅限于当前四机布局的 10k×10/s、1:1、180 秒：按现阶段 99.99% 完整处理率目标通过，P99 也低于此前讨论的 60 ms，但不能从三分钟短轮推断长期容量或 20/50 不对称负载。Agent 平均约用 4.68/8 核，接入机仍有 40.73% 空闲；本档没有增租第二台 Agent 的资源证据。下一步维持用户要求的三分钟窗口，先让正式业务 Ping 链路能生成可配置的下行条数，保持多在途负载与完整下行计数，再用现有四机测试不对称负载并观察 Agent、MsgQ、Game 和客户端各自的压力，届时决定扩容位置。现有 `--extra-down` 仅平均为每次 Ping 再增 1.5 条下行，而且与 `max-in-flight > 1` 互斥，不能直接代表 20/50 目标。
