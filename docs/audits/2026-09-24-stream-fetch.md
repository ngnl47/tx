# 四机 Agent→MsgQ 下行流回测

## 问题与改动

四机 10,000 会话不对称 Ping 负载下，Agent 从 MsgQ 读取下行的 `FetchSome` 已配置 `fetchBatch: 16`，但长轮询在第一条下行到达时立即返回。独立 `txbench` 计数按正式窗口对齐后，约 1,124,812 条下行对应 1,079,600 次成功 Unary `FetchSome`，其中 1,034,396 次（95.81%）只返回一条。逐批重建 gRPC 调用是实际成本；把上限从 16 调高无法解决，等待凑批会增加下行延迟。

MsgQ 新增 `StreamFetch` 服务端流，复用原 `FetchSomeRequest/Response` 和进程内邮箱读取；Agent 对远端 MsgQ 每个 Session 建立一条流并持续接收，同进程客户端仍使用原本地读取。原 Unary `FetchSome` 保留给既有客户端。流不增加等待时间、不更改出队、Seq/Ack 或 `Restore`：旧连接取消后，新 ConnectionID 仍按 Ack 重置游标并重发未确认下行。真实 gRPC 测试覆盖发送两条、确认第一条、断流重连后仅重放第二条及其后新消息。

新增 gRPC 方法要求分批升级时先部署 MsgQ、后部署 Agent；若新 Agent 先连接旧 MsgQ，`StreamFetch` 会返回未实现错误并使该会话失败。本轮四机 A/B 均使用同版服务二进制，未验证混合版本滚动升级。

## 测试口径与结果

四台同 VPC Ubuntu 24.04、8 核 16 GiB 机器分别承载 Login×2+Agent×2、MsgQ×2 与依赖、Game×2、四进程 TCP 客户端。Agent `GOMAXPROCS=4`，MsgQ/Game 为 2；10,000 个 Session 以 500/s 建连，预热 2 秒后开始正式窗口。Agent→Game 保持 Unary 直连，Game 每次 Ping 按 Seq 生成 1 或 2 条额外下行及一条 Pong；客户端逐条校验，完成率、未发送与 P99 均基于客户端结果。批次计数在独立 `txbench` 构建中记录，采集钩子已从最终代码移除。以下 P99 均包含旁路系统采样的影响，不与没有同类采样的旧轮混算。

| 下行传输 | 会话 | 每会话上/下行目标 (/s) | 窗口 | 上行完成 | 下行处理 | 未发/失败 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Unary `FetchSome` | 10,000 | 2.25 / 约 5.625 | 20s | 450,000 | 1,125,306 | 0/0 | 74.27ms |
| `StreamFetch` | 100 | 1 / 约 2.5 | 5s | 500 | 1,300 | 0/0 | 1.44ms |
| `StreamFetch` | 10,000 | 2.25 / 约 5.625 | 20s | 450,000 | 1,125,251 | 0/0 | 53.60ms |
| `StreamFetch` | 10,000 | 2.5 / 6.25 | 20s | 500,000 | 1,250,000 | 0/0 | 62.49ms |
| `StreamFetch` | 10,000 | 3 / 7.5 | 20s | 600,000 | 1,500,000 | 0/0 | 112.44ms |
| `StreamFetch` | 10,000 | 2.25 / 约 5.625 | 60s | 1,350,000 | 3,375,088 | 0/0 | 50.38ms |

同口径 20 秒档两台 Agent 的 `pidstat` CPU 样本均值合计从约 530% 降至 416%（约 -21%），两台 MsgQ 从约 304% 降至 251%（约 -17%）。Agent 每实例 RSS 约从 259 MiB 增至 299 MiB；60 秒正式窗口内分别约从 320/318 MiB 降到 309/311 MiB，未观察到持续增长。流式窗口内约 1,123,060 个发送批次里 1,122,851 个仅含一条，说明收益并非来自延迟合批。上述 CPU/RSS 为逐秒样本均值或端点值，不是严格的分配源归因；本轮没有采集 heap allocation profile，不能声称已经找到全部 `mallocgc` 来源。

按零失败、零未发、P99≤60ms 的当前门槛，万连 2.25/约 5.625 的 60 秒档通过；2.5/6.25 的 P99 仍略超门槛，3/7.5 更明显。最终目标 20/50 远未达成，现有结果仅覆盖轻量 Ping、单次 60 秒和这套四机拓扑，不代表 MMO 广播、战斗计算或长时间运行容量。2.5～3 档的分段资源诊断与结果见下文；不应仅因下行流收益而继续叠加推测性缓存或合批。

原始客户端结果、四机 `pidstat`/`vmstat`、批次 JSONL 和旁路编排器在 `tx-artifacts/cloud-20260924-fetch/` 及 `tx-artifacts/cloud-20260924-fetch-run.py`。试验后四机服务二进制均恢复为 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，客户端恢复原源码；八服务停止后重建专用夹具和角色，再运行 100 会话普通 Ping/Pong：500/500 完成，零失败、零未发，P99 1.18ms。

## 后续诊断：Game 执行预算

从上述三档的同窗口系统采样看，3/7.5 档的两台 Game 每实例约 172% CPU，接近当时的 `GOMAXPROCS=2`；Agent 每实例约 254%，宿主机平均仍有约 33% 空闲。客户端时间戳抽样显示请求到 Game 生成 Pong 的区间长尾增长更明显，但该区间使用跨主机时钟，只用于定位线索，不作为精确分段延迟。磁盘等待和虚拟机抢占均约为零。为隔离变量，在相同四机部署、`StreamFetch` 二进制、10,000 TCP 会话、4 个客户端进程、500/s 建连、2 秒预热、20 秒正式窗口及 3/7.5 每会话每秒负载下，仅改变两台 Game 的 `GOMAXPROCS`。每组均先停止八个服务，重建专用测试夹具，按 MsgQ→Game→Login/Agent 顺序启动；没有在活跃槽位上直接切换参数。

| Game `GOMAXPROCS` | 窗口 | 上行完成/计划 | 下行完成 | 失败/未发 | P50 | P95 | P99 | Game 每实例 CPU |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 2 | 20s | 600,000/600,000 | 1,500,000 | 0/0 | 28.50ms | 92.51ms | 123.31ms | 约 170%/171% |
| 4 | 20s | 600,000/600,000 | 1,500,000 | 0/0 | 3.95ms | 30.42ms | 46.24ms | 约 253%/254% |
| 4 | 60s | 1,800,000/1,800,000 | 4,500,000 | 0/0 | 4.46ms | 32.49ms | 50.09ms | 约 255%/254% |

Game 放开执行预算后，每实例实际多用约 0.8 核，而 Agent 两实例仍各约 255% CPU；60 秒档 MsgQ 各约 149%，客户端四进程事件循环利用率约 50%，全部计划槽位均发出。因而 `GOMAXPROCS=2` 是该负载下的主要长尾限制，4 核组连续 60 秒达到当前 P99≤60ms 门槛。这是部署容量参数的实验结论，不是要求全部 Game 实例固定使用 4 核，也不代表 20/50 的最终目标已达到。

诊断过程还暴露两个无效样本：首次复测误用 2 个客户端进程，事件循环利用率约 84%，且漏发 64/600,000 个计划槽位；直接重启 Game 改参数后，下一轮建连因 `discovery: slot runtime is unavailable` 失败。两者均未用于上表。原始结果和四机采样保存在 `tx-artifacts/cloud-20260924-fetch/game-procs2-client4-10000x3/`、`game-procs4-client4-10000x3/`、`game-procs4-client4-10000x3-60s/`。下一步在同一 4 核 Game 配置下逐级提高上/下行速率，观察新的 P99 拐点及 Agent、MsgQ、Game 的各自 CPU 余量，再决定扩实例还是优化具体热点。

诊断结束后，四机服务二进制均恢复为 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，客户端恢复原源码；重建专用夹具后，八服务均为 active。100 会话普通 Ping/Pong 冒烟完成 500/500，零失败、零未发，P99 1.08ms，角色租约全部释放。该恢复结果保存在 `tx-artifacts/cloud-20260924-fetch/restore-game-procs-smoke-100/`。

## 后续诊断：生成命令解码的栈帧

继续在 Game `GOMAXPROCS=4` 的同口径下上探，旧生成代码在 3.5/8.75、4/10 次/会话/秒两档分别出现 P99 110.84ms、190.31ms，并漏发 10、33 个计划上行槽位。诊断版四机 CPU profile 显示，Game 的 `commandActor.execute` 累计占约 54%～56%；其中 `DecodeBONCommand` 约 25%，其采样主要落在 `runtime.newstack`。反汇编确认旧生成函数栈帧为 `0x2e30`（11,824 B）。CPU profile 会扰动长尾，仅用于定位，不以其 P99 评估容量。

根因是生成器为每个命令类型重复生成 `bon.DecodeValue`、错误包装和返回语句，约 500 个 switch 分支使整个函数的栈帧膨胀。`txgen` 模板现只在各分支创建对应类型，分派后统一解码和返回；已重新生成 `txgen` 夹具与 `txgame` 的命令注册表，不手改产物。新函数栈帧为 `0x1c8`（456 B）。已知命令正文非法仍保留 `cmd: decode <name>:` 错误前缀。

本地 Intel i9-9880H、Go 1.27.0、`GOMAXPROCS=4` 的新协程首次解码基准，旧版 5 次运行的中位数为 30,915 ns/op，新版为 3,069 ns/op，约快 10.1 倍；两版均为 880 B/op、11 allocs/op。该微基准专门度量新执行协程的栈成本，不等于完整业务吞吐。`txgame/server/gen/cmd/cmd_registry.go` 净减 2,039 行；加上保留的 20 行基准，`txgame` 本轮净减 2,019 行。

云端只替换 Game 的生成代码，Agent/MsgQ 保持此前的 `StreamFetch` 诊断版；四机拓扑、10,000 TCP 会话、4 个客户端进程、500/s 建连、2 秒预热、额外下行和 20 秒正式窗口保持一致，每档重建专用夹具。下表旧版与新版不是同时运行的严格配对实验，但使用同一机器配置和采样口径；CPU 为正式窗口内每台 Game 的 `pidstat` 均值。

| 每会话上/下行目标 (/s) | Game 代码 | 上行完成/计划 | 下行完成 | 失败/未发 | P99 | Game 每实例 CPU |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 3.5 / 8.75 | 旧生成代码 | 699,990/700,000 | 1,749,970 | 0/10 | 110.84ms | 277%/274% |
| 3.5 / 8.75 | 新生成代码 | 700,000/700,000 | 1,750,000 | 0/0 | 52.56ms | 225%/225% |
| 4 / 10 | 旧生成代码 | 799,967/800,000 | 1,999,934 | 0/33 | 190.31ms | 294%/292% |
| 4 / 10 | 新生成代码 | 800,000/800,000 | 2,000,000 | 0/0 | 86.54ms | 239%/239% |

新代码再以 3.5/8.75 连续运行 60 秒：上行 2,100,000/2,100,000、下行 5,250,000，零失败、零未发，P99 56.72ms，Game 每实例约 226%/228% CPU。因此当前四机轻量 Ping 口径的已验证 60 秒容量提升至 3.5/8.75，仍远低于最终 20/50 目标；4/10 虽完整交付，P99 仍未达到 60ms。没有继续搜索更细的阈值。原始结果与四机采样在 `tx-artifacts/cloud-20260924-fetch/game4-10000x3p5/`、`game4-10000x4/`、`game4-decoder-new-10000x3p5/`、`game4-decoder-new-10000x4/` 和 `game4-decoder-new-10000x3p5-60s/`。

本轮测试后，三台服务机的服务二进制均恢复为 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，客户端恢复原源码，八服务均为 active。首次冒烟因重建夹具后尚未预创建角色而收到 Login HTTP 403，补齐 100 个专用角色后，普通 Ping/Pong 完成 500/500，零失败、零未发，P99 1.17ms，角色租约释放；结果在 `tx-artifacts/cloud-20260924-fetch/restore-decoder-smoke2-100/`。

不再细分速率阈值。沿用上述 Game 新生成代码、Agent/MsgQ `StreamFetch` 诊断构建、四机拓扑、10,000 TCP 会话、4 个客户端进程、500/s 建连、2 秒预热和 20 秒正式窗口；每轮停止服务、重建夹具并预创建角色。只改变两台 MsgQ 的 `GOMAXPROCS`，Game/Agent 均为 4。下表 CPU 为正式窗口内每个进程的 `pidstat` 均值；主机空闲为 `vmstat` 均值。

作为部署漂移对照，上文同构建的较早 2 核样本为 800,000/800,000、P99 86.54ms。两次 4 核样本的 P99 均低于本次 2 核配对样本，但差异不是固定的：客户端事件循环利用率从约 0.71 降到约 0.66–0.69，也可能贡献部分波动。MsgQ 每实例多实际使用约 0.6 核，说明原 2 核执行预算限制了这条链路；4 核仍未稳定满足零未发与 P99≤60ms。当前不能把该短轮当作已通过容量，更不能外推为 20/50 目标。

上行代码按 `Agent → MsgQ.Rec → Game Actor.Call` 串行执行，每条 Ping 约对应一次 Unary `Rec` 和一次直连 Actor 调用；本档约为 4 万条上行/s。约 10 万条下行/s 经已建立的 `StreamFetch` 流进入 Agent，再写入 TCP。旧版 3.5 档两台 Agent 的 CPU profile 均将 gRPC `ClientConn.Invoke` 列为累计热点；它覆盖 `Rec` 和 Actor `Call`，与两者各自的累计开销不能相加。本轮没有采集 MsgQ 逐函数 profile，不能将全部 CPU 归因于某个方法。Game 主机仍约 38%–41% 空闲，客户端主机约 55%–58% 空闲；两台 Agent 各占约 3.1 核，接入机仅约 19% 空闲，且三轮均无显著 I/O wait 或虚拟机 steal。

下一步优先给 Agent 增加**独立宿主机上的计算容量**，保持 4/10、MsgQ `GOMAXPROCS=4`、同版构建及相同客户端口径做对照。现有接入机再加 Agent 进程会与两台已占约 6.2 核的 Agent 竞争 8 vCPU，不能作为扩实例收益验证。若扩 Agent 后仍受 MsgQ 或逐消息 RPC 限制，再采同档 Agent/MsgQ profile，评估 `Rec` 或调用路径改造；不预先改变 Seq/Ack 契约。原始客户端结果与四机采样在 `tx-artifacts/cloud-20260924-fetch/msgq2-paired-10000x4/`、`msgq4-paired-10000x4/`、`msgq4-repeat-10000x4/`。

对照结束后，三台服务机均恢复原二进制 SHA-256 `7383373535c1999c876a7332d14aaf60483b7b8d6c5fefcccbebeb8c52281e47`，客户端恢复原源码，八服务 active。补齐 100 个专用角色后，普通 Ping/Pong 冒烟完成 500/500、零失败、零未发、P99 1.10ms，角色租约释放；结果在 `tx-artifacts/cloud-20260924-fetch/restore-msgq-eval-smoke-100/`。
