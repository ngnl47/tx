# 20/50 下行帧到达边界复核

本轮延续[排队位置复核](2026-09-28-uplink-downlink-queue-location.md)的同版服务二进制、六机拓扑和 60 秒万连 20/50 负载，仅在 `txclient` 的诊断模式增加原始下行帧到达时间与逐秒 Node 事件循环采样。未改变 Seq/Ack、流发送或合批策略。帧到达记录仅对 `roleID % 32 == 0` 的会话启用；正式请求每 64 条采样一条，因此帧阶段约占请求的 1/2048。跨机器阶段使用 Unix 毫秒墙钟，仍不能判断亚毫秒差别。

专用夹具必须在服务启动前 `prepare`。第一次误先启动服务，使专用 Mongo DB 生成了 17 个空集合，且角色准备因缺少 ownership 标记被拒。停止全部业务进程，确认这些集合的文档数均为 0 且无 owner 标记后，仅重置 `txgame_cluster_e2e`，重新 `prepare` 并启动；此时角色准备成功。16 会话、8 秒冒烟完成全部 2560 个请求。正式窗口结束后按 Agent/Login → Game → MsgQ 顺序停止服务并执行夹具 `cleanup`；中间件容器未停。

| 客户端 | 已完成 / 计划上行 | 未发送 | 上行完成 P99 | 已收下行 | 请求失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 5,954,382 / 6,000,000 | 45,618 | 138.37ms | 14,886,320 | 0 |
| B | 5,987,288 / 6,000,000 | 12,712 | 97.32ms | 14,968,288 | 0 |

两个客户端的程序状态均为 `failed`，原因是未达到 99.99% **计划发起/完成率**，不是已发请求超时。此轮不能作为容量达标证据；仍可用于定位已完成请求的时间段。新增诊断采样可能增加客户端负担，不把它与无此探针的历史窗口直接做吞吐因果比较。

| 客户端阶段 | A P99 | B P99 | 解释 |
| --- | ---: | ---: | --- |
| 计划时刻→请求开始 | 92.02ms | 47.66ms | 客户端发生器排程延迟；不属于服务端排队 |
| 请求开始→本地 socket 写入 | 0.048ms | 0.041ms | 本地调用开销很小 |
| `Pong.ServerTime`→原始下行帧进入 `onFrame` | 95ms | 71ms | 含 Game 发布、MsgQ、Agent、TCP 和客户端事件循环唤醒 |
| 原始 Pong 帧进入 `onFrame`→请求完成 | 0.042ms | 0.037ms | 客户端帧解码、额外下行完成判断等；此段并非几十毫秒长尾 |

前两段的样本分别约 9.3 万条/客户端；帧到达阶段的样本数分别为 2825、2950。`Pong.ServerTime` 是 Game Handler 返回前的时间，额外下行已先被发布，不能视为 Game 刚开始处理的时间。帧到达与完成之间的测量使用同机单调时钟；服务端到帧到达使用毫秒墙钟，P99 精度受时间同步及采样数限制。

两台 Agent 的上行共享流 `sendMu.Lock` 等待 P99 桶上界均为 40ms，均值为 1.76/2.08ms，而底层 `Send` 的 P99 桶上界仅 0.05ms。Game Actor 邮箱等待 P99 桶上界为 20ms。下行的 MsgQ 共享流发送队列 P99 桶上界为 2ms，Agent 会话接收队列为 10ms，Agent socket 写入调用为 0.25ms。这些是**不同请求的分位数**，不能相加解释端到端 P99。它们表明：上行发送锁仍是已测得的明确排队点；下行已埋点队列和写调用未单独出现 71–95ms 的 P99。

逐秒事件循环 P99 的中位数在 A/B 为 27.94/23.92ms，这些逐秒 P99 值的 P95 为 124.32/52.10ms。帧到达延迟最慢 1% 的样本，其所在秒的客户端事件循环 P99 超过 40ms 的比例在 A/B 均约 86%；全体帧样本所在秒的对应比例分别只有 27%/15%。按样本的逐秒聚合计算，帧到达延迟与同秒事件循环 P99 的 Pearson 相关系数约 0.40/0.45，与计划发起延迟约 0.54/0.41。这支持客户端调度可能参与长尾，却不能证明它是唯一原因，因为 `onFrame` 在客户端事件循环被唤醒后才记录时间；服务端发出→客户端内核收到之间尚无可关联时间戳。

下一步若要准确拆开这个剩余区间，应只对少量 `SessionID + 下行 Seq` 记录 Agent 实际 socket 写入前后的时间与客户端原始帧回调时间，并同时校准两机时钟；或者用操作系统侧收包时间戳作交叉验证。先验证探针对 20/50 负载的影响，再决定是否优化 Agent 下行或客户端发生器。不要据本轮相关性直接调合批阈值。

原始数据、前后 Prometheus 快照及可复算脚本位于 `tx-artifacts/cloud-20260928-dual-client/frame-stage-20260928/`，`summary.json` 是其汇总。
