# JetStream 强同步分层对照

## 范围与执行计划

在既有同步策略对照之后，固定 `sync_interval=always`，区分有界并发窗口、拉取预取和 Actor 适配的影响。不修改生产接口与 Worker，不以降低同步保证换取吞吐。全部采集沿用独立测试入口；用户要求串行执行、不提交 Git，保留此前未提交的同步策略报告。

- 原生路径保留相同任务 JSON 信封、发布函数（Marshal + SDK Publish/WithExpectStream）、解码和内存计数，直接 DoubleAck；移除 Processor 的 Actor Call 与续期适配。它是匹配负载的 SDK 任务闭环对照，不是纯 Broker 发布峰值。
- 五组依次为 native4、actor4、native32、native32batch、actor32batch。前两组发布者/消费回调均为 4、PullMaxMessages=1、MaxAckPending=4；native32 为 32/32/1/32；最后两组为 32/32/16/512。native4→native32 同时扩大两端并发，不能单独归因于发布侧；native32→native32batch 同时扩大拉取预取与待确认窗口，不是将业务确认合并为一次。
- 所有组保留同样两个框架服务及 32 个预热 Actor，原生路径测量时不调用 Actor。每条消息仍独立等待 PubAck 与 DoubleAck，没有异步发布批量接口、AckAll 或人为重试。
- 不设置 TX_TASK_RATE，回到闭环 1000 条任务；每组 R1/R3 各三轮，合计 30000 条。因此不能与上一轮 200 条/s 的固定到达 P99 直接作加速比比较。
- 先运行 native32batch / actor32batch 的 race 检查，再采集五组非 race 数据，最后运行全量回归及 Ponytail review。沿用任务唯一性、投递次数、业务计数与源流清空断言。

停止条件是解释主要差距及判断是否值得改生产适配，不扫描更多参数、不追求官方跑分。本轮只增加测试 profile 开关；默认 actor4 与原基线一致。

## 采集结果

基于 `c68a876` 加本轮测试 profile 改动；Go 1.27.0 darwin/amd64、GOMAXPROCS=4、NATS 2.14.6、nats.go 1.53.1。新建同机三容器，文件存储为容器可写层 `/data`，三个节点均为 always，非生产持久卷或三个物理故障域。启动前验证元数据 API 可用；32 个角色预热，256B 业务 payload 外仍有 JSON 信封。性能测量期间不并行执行全量测试。

[原始 30 窗口 JSON](baselines/2026-09-20-jetstream-task-layers.json)。表中吞吐及 P99 为三轮窗口指标的中位数，最后一列保留完成吞吐范围；不合并 P99 样本。

| --- | --- | ---: | ---: | ---: | ---: | --- |
| native4 | R1 | 232.25 | 173.49 | 37.16 | 2130.69 | 143.8–279.2 |
| native4 | R3 | 83.21 | 83.17 | 75.87 | 209.76 | 41.9–107.5 |
| actor4 | R1 | 432.87 | 258.72 | 13.93 | 1554.20 | 234.9–285.8 |
| actor4 | R3 | 99.96 | 98.16 | 62.55 | 264.70 | 98.1–103.9 |
| native32 | R1 | 451.71 | 299.81 | 102.23 | 1349.58 | 296.0–313.9 |
| native32 | R3 | 100.19 | 100.19 | 445.77 | 460.17 | 92.6–109.8 |
| native32batch | R1 | 496.46 | 315.32 | 116.21 | 1677.64 | 314.8–326.8 |
| native32batch | R3 | 116.01 | 115.98 | 394.85 | 392.32 | 109.0–117.8 |
| actor32batch | R1 | 492.06 | 280.40 | 93.08 | 1922.75 | 275.5–290.7 |
| actor32batch | R3 | 106.37 | 106.09 | 385.75 | 426.04 | 102.6–125.0 |

原生路径没有恢复到万级或百万级；增大并发/预取后 R3 仍为百条/s。native32→native32batch 的中位完成吞吐从 100.19 增至 115.98 条/s，局部收益存在，但不足以解释与宣传数字的量级差距，也不值得据此立即修改生产 Worker。

相同大窗口下，Actor 组 R3 为 106.09 条/s，原生组为 115.98 条/s，三轮范围有重叠；小窗口 Actor 组反而高于原生组。因此不能用两组相减宣称 Actor 固定增加了多少耗时，也不能宣称 Actor 没有成本。这是固定顺序、共享宿主资源下的短样本，对细小性能差异没有足够分辨力。

结合 [同步策略 A/B/A 对照](2026-09-20-jetstream-task-sync.md)，证据支持强同步与本地存储环境是当前限制的重要因素，而不是 Actor 封装造成数量级损失。扩大窗口也会拉长在途等待：原生 R3 PubAck P99 从 4 并发的 75.87ms 增至 32 并发的 445.77ms，并发数不能直接换算成吞吐倍数。

本轮没有单独测磁盘 fsync、只发布/只消费或跨物理机，因此无法区分宿主存储、复制、确认状态写入各自的贡献；也未测试 SDK 批量发布接口，不能以本轮否定其收益。所有结果都不是 Core NATS 纯转发能力、生产容量或长时间稳态结论。

## 复现与验证

独立三节点显式配置 always、元数据 API 就绪后，在 tx 根目录依次改变 profile 运行：

```sh
TX_TASK_BASELINE=1 TX_TASK_PROFILE=native32batch \
TX_ACTORTRIAL_NATS_URL='nats://127.0.0.1:<隔离端口>' \
TX_ETCD_ENDPOINT=127.0.0.1:2379 GOMAXPROCS=4 \
go test ./internal/framework -run '^TestJetStreamTaskBaseline$' -count=1 -v
```

本轮不设置 `TX_TASK_RATE`；设置该值会切到原有固定计划到达模型。省略 profile 保持 actor4。修改预取只影响本性能入口；生产 Worker 仍每次拉取 1 条，每回调完成其业务后逐条确认。

- 两组 race 验证 native32batch / actor32batch 分别通过（25.91s、35.34s），共 12000 条，不进入性能样本。
- 五组非 race 测试分别通过（63.47s、42.99s、41.37s、37.14s、39.37s），共 30000 条，逐条核验投递次数为 1、无重复完成、计数匹配、源流最终清空。
- `go test ./... -count=1` 全量通过；未显式启用的外部依赖测试仍按约定跳过。数据一致性与 `git diff --check` 通过。交付前正确性检查及 Ponytail review 未发现需要修改的问题；测试复用现有入口，不增加生产抽象。
- 本轮隔离网络 `tx-task-baseline-wv8t1rnq`、三个容器和临时配置已清理；此前同步对照失败现场及共享服务保持原样。

## 收口与下一项

分层定位到此收口，不扩大参数矩阵，不调整生产并发、批量或同步默认值。已证明原生匹配负载同样受限，当前没有足够证据支持对 tx 热路径进行微优化。后续性能工作应等待目标 Linux/存储条件明确后复测，再进入真实业务和长期负载验收。

下一项建议回到 T5 的示例接线与真实业务任务验收，具体场景尚需按当前示例代码评估；生产同步策略与可接受故障窗口继续待决策，不阻塞与其无关的功能建设。
