# BON 整数位宽与符号复核

## 复现与原因

- Go BON 原先将 uint32 转为 int32 编码；`2147483648` 再解码时得到 `-2147483648`，连 Go 自身的 uint32 目标也拒绝接收。
- 两客户端只检查 JavaScript 安全整数，允许 int8=128、uint16=-1 等与生成 scalar 不匹配的值。发送 map key 时还存在直接转字符串、绕过类型校验的路径。

## 当前实现

- Go uint32 在 int32 正数范围内使用既有 32 位编码，上半区使用既有 64 位编码。无协议版本或新类型，不推测修复旧负数载荷。
- 两客户端分别维护整数校验函数，正文编码、解码、map key 和表单复用；同时检查 Go 标量范围与 JavaScript 安全整数范围。int/uint 保持当前 64 位服务端部署的安全整数契约，32 位目标的机器整数不在本轮支持范围内。
- schema 已携带 int8/uint32 等类型，不需要增加 txgen 注解、配置或元数据。无额外 I/O，map key 校验与原写入遍历合并。

## 验证

- Go 新增一个 uint32 往返回归，覆盖 0、int32 上界、上界加一及 uint32 最大值；先复现失败，修复后通过。
- 每客户端新增一个整数边界测试，集中验证有符号/无符号边界、别名、负数、越界与 map key；复用表单测试验证范围错误。没有按每个边界拆分测试函数。
- 临时真实交叉探针 `/private/tmp/tx-null-contract.ZhMwqe/uint.go` 与 `uint.ts`：Go 编码 `4294967295`，两客户端解码正确并重新编码出相同字节；分别交回 Go，均得到 `4294967295`。
- 该载荷为 `CAIFAWMFBVByb2JlBQFiCAEFAW4C/////wAAAAA=`，对应命令 Probe、字段 n、uint32 最大值。
- tx 全量 Go 测试通过；txclient 78 项、txclientslg 98 项测试及构建通过。本轮没有运行真实多进程集群，也没有扩大到浮点数与任意精度整数设计。
