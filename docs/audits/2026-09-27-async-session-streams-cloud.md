# 异步会话流四机云端复测

## 测量范围

2026-09-27 在四台 8 核、16 GiB 腾讯云实例上复测已部署的异步流候选版：接入机运行 Agent P8 与 Login×2 P4，存储机运行 MsgQ×2 P4，游戏机运行 Game×2 P4，客户端机运行 8 个 worker。业务路径使用 TCP `System_Ping/Pong`，目标为 10,000 个 Session、每 Session 上下行各 10/s、180 秒测量窗。候选二进制 SHA-256 为 `04b6692c692c051f32966df15c4cf19b26824743c7bf99dd26382cc479ec1448`；各服务使用 `assets/recstream` 配置，启用 Agent→Game 无逐项响应的 `CallStream` 入队、Agent↔MsgQ `MailboxStream`、Game→MsgQ 异步 `PublishStream`。

## 准备阶段发现的失效状态

最初启动时，专用 etcd 前缀中有 1,024 个角色槽位仍指向旧 Game InstanceID `txgame-2145-38947` 和 `txgame-3044-38944`，Agent 报 `discovery: slot runtime is unavailable`。完整槽位快照保存在工程外的 `tx-artifacts/cloud-20260926-mailbox-streams/diagnostics/role-slots-before-reset-20260927.txt`。按专用测试环境流程，在服务停止且 MsgQ Redis role/session 归属为零后，清除了该槽位前缀并冷启动服务。

随后 100 Session 冒烟完成 5,000/5,000，上下行各 500/s，失败和未发送均为零，P99 0.480 ms。紧接着使用同一组 RoleID 扩展至 10,000 Session 时，MsgQ 记录 100 条 `role binding changed: session has changed`。冒烟会话释放后，MsgQ 为重登录生成了新的角色归属代次；Game 侧 `RoleRouter` 仍缓存冒烟时读取的旧代次。当前 Game→MsgQ `PublishStream` 不逐项回报拒绝，因此 Game 不能据此失效缓存；本轮 worker0 的 `System_Pong` 超时，正式窗口没有开始。

此错误不能归咎于旧 Game 槽位：当时槽位已经冷分配到运行中的新 Game。它是跨会话重用 RoleID 时的角色归属缓存失效问题。详细拒绝行保存在 `tx-artifacts/cloud-20260926-mailbox-streams/candidate-20260927-r4/role-publish-errors-before-r4.txt`。正式复测前停止了测试进程、备份并清除专用槽位、清除 DB12 中本轮 `txgame:msgq:session:*` 邮箱，再启动全新候选进程；没有先运行冒烟，以免再次用同一批角色污染路由缓存。正式窗口期间未出现新的 `one-way role publish failed`。

## 正式候选结果

| 版本 | 计划 | 完成上行/下行 | 业务失败 | 未发送 | 完成吞吐 | P50/P95/P99 | 最大延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 基线，2026-09-26 | 18,000,000 | 各 16,853,324 | 0 | 1,146,676 | 93,629.58/s | 307.76/534.10/610.36 ms | 1,050.63 ms |
| 异步流候选，2026-09-27 | 18,000,000 | 各 17,999,926 | 0 | 74 | 99,999.59/s | 0.83/24.02/31.33 ms | 119.30 ms |

两轮的最终 `status` 都为 `failed`，原因是压测器对未发送计划槽位采用严格零容忍，不是业务请求失败。候选完成吞吐比基线高约 6.8%；未发送从 1,146,676 降到 74；P99 从约 610 ms 降到约 31 ms。候选已接近 100,000 次/s 的供给目标并满足讨论中的 P99≤60 ms，但由于 74 条计划未发送，不能记为严格通过；目前也只有一轮有效候选，不能把结果外推为多次运行的稳定容量。

180 秒正式窗口中，候选 Agent 平均约 5.21 核，基线高负载 Agent 约 7.48 核；MsgQ 每实例从约 1.86 核降至 1.08 核，Game 每实例从约 2.35 核降至 1.57 核。Login 两实例均接近空闲。数据与减少逐消息 RPC 等待和封装开销的方向相符，但单次不同日期运行不是严格随机化 A/B，不能仅据此分配所有收益给某一条流。

## 验收边界与后续决策

异步流在冷路由状态下完成了近满速 10k×10/s 的真实四机链路测试；但跨会话复用角色暴露出旧 `RoleRouter` 代次会让异步下行持续遭拒的功能边界。当时需要决定如何反馈旧归属拒绝；后续已增加仅回报明确拒绝的控制消息，见下文修复和补测记录。上表的旧候选不能视作具备完整重登录行为的完成版。

候选客户端汇总、8 worker 阶段计时与宿主机采样归档于工程外 `tx-artifacts/cloud-20260926-mailbox-streams/candidate-20260927-r4/`。逐请求延迟原始数组约 392 MiB，保留在客户端实例路径 `/home/ubuntu/tx-perf/results/mailbox-stream-candidate-10k-10ps-20260927-r4/`；当前本地归档保留聚合统计和阶段计时，按需可再下载原始数组。

## 后续修复状态

上述云端吞吐数据来自修复前的候选版。随后按确认的边界，将 `PublishStream` 改为双向流：MsgQ 只在旧角色归属明确拒绝且未向任何邮箱投递时，异步返回该请求携带的完整归属版本；Game 仅删除仍与该版本匹配的缓存。成功发布没有逐项 ACK，被拒的业务载荷不自动重投。已增加真实 gRPC 回归，覆盖同一 RoleID 换 Session 后首条旧归属发布遭拒、后续发布读取新归属且旧载荷未重发。此修复没有计入上表二进制和性能数据；功能短测记录如下。

针对该边界另做了云端短测：Game 与 MsgQ 同版二进制 SHA-256 为 `b5fb1335054999d58ef470dbf336338d474f911b8563156a554465160160ec3e`。七个测试服务全停、Redis DB12 角色/会话归属均为零时，备份专用角色槽位后仅清除旧 Game 的 1,024 个 `role` 分区归属，再依次启动 MsgQ、Game、Agent/Login。100 个 Session × 5/s × 10 秒预热完成 5,000/5,000，零失败/未发送，P99 0.501 ms。

随后 RoleID `480100` 重新登录为新 Session：首条 `System_Ping` 在等待 1 秒内没有 Pong，MsgQ 日志确认旧代次 `a26dd60d-...` 被拒、当前代次为 `8618b4fe-...`；第二条 Ping 收到一个 Pong，客户端探针输出 `afterFirst=0, pongs=1`。这说明被拒载荷未重发，异步反馈使下一条下行重新寻址成功。测试后 Agent/Login×3、Game×2、MsgQ×2 均保持 active。槽位备份、客户端预热报告、探针与拒绝日志保存在工程外 `tx-artifacts/cloud-20260926-mailbox-streams/{diagnostics,role-feedback-20260927}/`。该次短测只验证功能恢复；随后本地补了发布流关闭竞争的回归与修复，含此修复的正式补测见下文。

## 反馈修复版正式补测

2026-09-27 在相同四机配置上补测了含发布流关闭修复的版本。Game×2 与 MsgQ×2 使用相同的 Linux 二进制 SHA-256 `b9e0f4c281b6f116adf9b6c8295d8fd89bc0554036dc22a58c544e316a7c58d6`；Agent P8、Login×2 P4 继续使用上表候选版。测试前七个业务单元全部停止，确认专用 Redis DB12 的角色和会话归属键为零，将专用 etcd 角色槽位前缀中的 94 条旧分配同时备份到云端和本地后清除。按 MsgQ→Game→Agent/Login 启动，没有先用正式 RoleID 做冒烟。客户端准备屏障确认 10,000 个 Session 后，执行同样的 TCP `System_Ping/Pong`、每 Session 10/s、上下行 1:1、180 秒测量窗。

| 版本 | 计划 | 完成上行/下行 | 业务失败 | 未发送 | 完成吞吐 | P50/P95/P99 | 最大延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | ---: |
| 修复前候选 | 18,000,000 | 各 17,999,926 | 0 | 74 | 99,999.59/s | 0.83/24.02/31.33 ms | 119.30 ms |
| 反馈修复版 | 18,000,000 | 各 17,999,987 | 0 | 13 | 99,999.93/s | 0.69/18.58/24.59 ms | 71.70 ms |

补测的 13 条未发送全部落在客户端计划计数中：worker 0、4、6 分别为 2、9、2；所有实际发出的 17,999,987 条上行均完成并收到了下行。按压测器的未发送零容忍规则，最终状态仍为 `failed`。这轮证明修复版在该单次窗口中维持约 10 万次/s、P99 低于 60 ms，不能据此宣称稳定容量或把单次 P99 差异归因于拒绝反馈。它也不是 20/50 不对称目标的验收。

180 秒窗口内 Agent 平均约 4.70 核，MsgQ 两实例分别约 1.12 核，Game 两实例分别约 1.62 核；三台宿主机平均空闲分别为 38.53%、64.75%、55.88%，steal 均为零。Game/MsgQ 的压测窗口内未发现 `ERROR`。测量结束约 31 秒后，客户端集中断开期间两个 MsgQ 共记录 9,752 条“Session 已离线时收到 Ack”，发生在正式窗口外；它不影响本轮吞吐统计，但需另行核对会话结束与 Ack 的排队顺序。

测后 MsgQ 两实例仍为 active，专用 Redis DB12 的角色和会话归属键均回到零。汇总、8 个 worker 结果及宿主机采样归档在工程外 `tx-artifacts/cloud-20260926-mailbox-streams/feedback-throughput-20260927-r1/`，槽位备份在同级 `diagnostics/role-slots-before-feedback-throughput-20260927.json`。约 412 MiB 的客户端原始延迟数组仍保留在客户端实例 `/home/ubuntu/tx-perf/results/feedback-10k-10ps-20260927-r1/`，本地只保存聚合统计与资源样本。
