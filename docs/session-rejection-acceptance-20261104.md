# 接入拒绝修复与持续流量补验（2026-11-04）

本轮修复 WebSocket 接入拒绝传递，复用现有正式包与集群入口补验两组 MsgQ 恢复、SLG 完整持久化。全部在本机执行，保持完整计划分母，不重投请求、不跑云测试、不提交。此前失败原始证据保留，见[修复前报告](session-rollout-acceptance-20261104.md)。

## 修复及职责边界

1. Agent 对 MsgQ 路由不可用此前只关闭连接，WebSocket 看到传输错误；客户端又把 Ready 前普通关闭与网络错误包装成 `HandshakeRejectedError`。因此此前 TCP 的恢复通过也不足以证明明确应用拒绝。
2. 新增 Frame v4 的 `HandshakeRejected = 9` 空控制帧，只拒绝本次接入；`SessionEnded` 保留永久失效语义。Agent 不泄露内部错误文本，初始化取消不发送新的拒绝结果。未收到结果帧的网络失败仍是结果未知。
3. 两组客户端只从明确结果帧生成应用拒绝错误，保留原始网络错误；结果之后的关闭不能覆盖已收到的结论。没有新增自动重投、新登录或正常消息确认。新增控制帧要求前后端同步更新。
4. 验收工具检查明确拒绝、原票据恢复尝试、同角色新 SID、owner/CID 与服务端拒绝证据；不再通过“有没有断线”推断拒绝。

```text
有效握手 → Agent 验票、查询 owner、等待 MsgQ 接纳
             ├─ 接纳成功 → Ready
             ├─ 本次未获接纳 → HandshakeRejected
             └─ 明确永久失效 → SessionEnded
没有结果帧的断线或网络错误 → 接入结果未知，不自动重投
```

## SLG 持久化补修与最终读回

首轮 SLG 三窗恢复均通过，最后 40 个角色也收到最终改名响应，但停服后的 Mongo 仍为初始值。独立读取确认这 40/40 个最终标记全部在 Redis；前两窗 80 个角色已在 Mongo，World 最终坐标 (31,32)、版本 2 也已保存。

原因是工具过早停止 Fusion 消费进程。WriteBack 按 GD mode 写入；Fusion 排水保证 Redis 写入和持久化任务发布，不承诺延迟 Mongo 消费完成。本轮只修验收编排，不改变框架存储契约：

```text
固定流量结束 → 最终改名确认、World 双路径及移动确认
  → 保持正式 Fusion 消费进程在线，最多等 45 秒让 Mongo 追上全部角色标记
  → 全部服务正常排水退出
  → 再读 Mongo：120 个角色 + 最后 World 单位
```

等待只轮询读取，不人工写库、不缩短生成延迟；旧值超时、身份不符和数据库错误均失败。排水后仍保留原来的严格最终读回，不能用等待阶段成功替代它。

最终 `session-rollout-persistence.json` 通过：120/120 角色的名称、RoleID、OriginServerID=1001 一致；世界 1、桶 7、单位 1001 的坐标为 (31,32)，文档版本 2。独立 Docker/Mongo 读取再次核对 120/120。World 直达与 Role→World 两条完成通知都来自预期宿主。

首轮失败记录没有改判为成功，原始窗口、Mongo 读回与 40 个 Redis 最终值均已归档；后续按 ownership 规则重建专用验收范围后重跑 SLG。txgame 没有重复运行。
