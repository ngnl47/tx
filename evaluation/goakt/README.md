# GoAkt 运行时收敛评估

本目录只属于 `feature/goakt-runtime-evaluation` 的实验，不是 tx 公共 API，不由 Bee/Ant 装配。独立 go.mod 固定 GoAkt v4.5.4，主模块依赖和生产实现不变。项目间不增加引用关系。

## 目的与范围

验证把邮箱调度、空闲钝化、请求等待交给 GoAkt 后，tx 能否减少需要自行维护的并发机制。不得把“实验代码较少”等同于“完整替换已完成”。

当前最小适配由 `role.go`、`delivery.go` 和 `drain.go` 组成：

- 以数值 RoleID 作为 Grain 名称；Session 身份只随消息透传，不参与实体寻址。
- 使用官方泛型 `GrainOf`，不使用已标记弃用的工厂激活 API。
- 通过 ActorSystem Extension 注入本进程加载函数；每次激活创建一个 Handler，不把 GD/Store 放进 Actor 运行时。
- 使用内建有界 Grain 邮箱和空闲钝化；每次解析都携带容量和钝化选项。
- 使用 AskGrain 关联请求/响应；复用现有 protobuf Delivery/Result 数据结构，并复制跨调用边界的消息。
- 不维护本地实体 PID 表、自定义邮箱、空闲 timer、响应 Actor 或 pending 请求表。
- 复用 tx 的 `lifecycle.Ingress` 关闭本地调用准入，在进入持久化收尾前执行邮箱完成确认。

## 四种投递入口

| 入口 | 成功返回表示 |
| --- | --- |
| Tell | 本地准入成功，已复制消息并安排投递；后续失败记录日志 |
| TellAccepted | 目标已从邮箱取出消息，不代表业务完成 |
| CallFuture | 本地准入成功，返回独立等待对象 |
| Call | 等待业务结果，保留业务错误码 |

GoAkt 原生 TellGrain 也等待接收端确认，外部调用方没有可直接替换现有 Future 的同形接口。因此本适配使用原生 Ask 关联消息，以有界等待协程提供四种入口，不维护全局请求关联表或响应 Actor。每个未结束的 Ask 占用一个 `maxPending` 名额；满时立即拒绝。这个容量不是 Session 数量，也不是目标邮箱容量。

单次 Await 超时不撤销 Future；原始请求期限限制整个 Ask 等待。Tell 使用 GoAkt 默认的 5 秒请求等待期限。业务 Handler 使用启动时传入的生命周期 Context，不随调用方取消等待而取消；项目应自行给业务 I/O 设置期限。这不是持久化必达机制，也不自动重投超时消息。

RPC 不承诺服务异常时必达。投递、接收确认和执行结果用于表达不同完成阶段，不是持久化可靠投递；需要异常后必达的业务应使用持久化 MQ。本评估不引入 MQ，也不增加自动重投或去重结果库。

消息在提交返回前复制，业务响应在离开 Handler 时复制，多次 Await 也不共享可变结果。复用 protobuf Delivery/Result/Acceptance 数据结构，但 RequestId 清零，关联交给 GoAkt；不声明与原运行时的关联协议互通。

## 已验证

四个关键测试各运行三轮通过，另一次 `-race` 完整运行通过：

1. Session 1、2 并发向 RoleID=1001 各次发放 100，总计 20 次，余额为 2000，加载一次。Handler 保留每条请求的 SessionID。
2. 邮箱容量 1，首个处理阻塞时再投递 20 条：一条排队，19 条明确返回 ErrMailboxFull，最终只执行两条。
3. 请求开始执行后等待超时，Handler 仍保持执行，直到受控释放；证明调用等待结束不能代表业务结束。
4. 内建空闲钝化后再次访问相同角色，重新执行加载边界。

另增加三个排水契约测试，全部七个用例以 `-race -count=3` 运行通过：

1. 两个 Call 已超时，但一个 Handler 仍执行、另一个请求仍排队时，关闭返回超时且不得调用持久化收尾；两个业务都完成后排水成功。排水期间新 Call 返回 `lifecycle.ErrDraining`。
2. Grain 的加载函数仍在运行时，不能因当前活跃目录尚未包含它而宣布排水完成。
3. 持久化回调返回错误时，GoAkt 系统仍运行且准入关闭；再次收尾成功后才停止系统，成功关闭后不重复执行收尾。

四种入口新增四个关键用例，全部 11 个用例以 `-race -count=3` 通过：接收确认后取消等待不取消业务且排水仍等待；Tell 不等待激活且消息所有权独立；Future 单次等待超时、容量拒绝和结果隔离；业务错误码保留。

这里的余额是加载函数创建的实验内存状态；持久化失败采用回调注入，不是生成 GD、Mongo、WAL 或 checkpoint 验收。上述 11 个用例覆盖本地行为；下面的独立双进程场景验证本适配的真实远程通道。

```sh
cd evaluation/goakt
go test -tags=hashicorpmetrics ./... -v -count=3 -timeout 30s
go test -race -tags=hashicorpmetrics ./... -count=3 -timeout 60s
go test -tags=hashicorpmetrics ./... -run '^$' -bench '^BenchmarkLocalRoleCall$' -benchmem -count=3 -benchtime=300ms
GOAKT_EVAL_ETCD=127.0.0.1:2379 go test -race -tags=hashicorpmetrics ./... -v -count=3 -timeout 120s
```

在 tx 根目录执行 `go test ./...` 不会遍历本独立模块，必须另行执行上述命令。初始基线 `go test ./modules/actor ./modules/rpc` 和主模块 `go test ./... -count=1` 已通过；外部依赖专项用例是否运行仍由它们各自的环境开关决定。

本地 Call 基准（Intel i9-9880H、darwin/amd64、256 B 请求和响应载荷、共享 deadline、三轮各 300ms）对比：

| 评估实现 | ns/op | B/op | allocs/op |
| --- | --- | --- | --- |
| 上一阶段直接 Ask + 排水准入 | 10,533–10,613 | 4,560–4,562 | 67 |
| 本阶段四种入口 + 有界 Future | 22,257–24,042 | 5,186–5,188 | 72 |

本阶段单独重跑基准，避免与回归并行竞争。相对上一阶段历史测量，延迟约为 2.1–2.3 倍，每次多 5 次分配；包含新增异步等待、结果隔离和校验，不是仅测 GoAkt 调度。这明确不满足“性能无回退”的替换门槛。两次测量不是同时执行的严格性能统计，但足以阻止据此宣称低成本替换。基准不含网络、业务解码或数据库，且尚非与生产 Messenger 的等价对照。

## 单进程排水方案

`Shutdown(ctx, flush)` 按下面的顺序执行：

1. 关闭 Ingress，拒绝四种入口的新调用。
2. 等待已准入调用的激活、投递和响应等待阶段返回。此时业务仍可能执行，不能开始 flush。
3. 读取 GoAkt 的进程内 Grain 目录，对每个 Grain 发送普通 FIFO 邮箱确认消息。确认消息不进入业务 Handler，不走优先系统消息。
4. 所有确认返回后才执行项目传入的 flush。排水失败或 flush 失败均保留运行时，允许上层按既定有限次数重试；成功后才调用系统 Stop。

例如 A 在执行奖励操作、B 的奖励消息已排队，二者的 Call 均超时：第 2 步可以结束，但第 3 步必须排在两条奖励消息之后。因此业务完成时间与客户端等待时间不再混同。

该方案没有增加请求结果表，只借助已有入口闸门和 GoAkt 自己的队列顺序。目录遍历和邮箱确认发生在关闭路径，不是每条消息都遍历；当前没有查询或扫描 Redis/etcd。

约束：所有业务必须通过本进程这四种入口进入；没有 Grain 定时器、异步继续投递的后台任务、跨节点新入站或 Actor 间再投递。当前未经这些路径的验收，不得接入生产关闭流程。启用集群后 `Grains` 可能查询集群目录，不能照搬此实现为“本地快照”。

确认消息也受普通邮箱容量和 deadline 限制；满队列或超时会使本次关闭失败，不能跳过。活跃实体很多时，逐个确认的关闭耗时需要评估。它不是通过重写热路径邮箱实现的通用排水算法。

## 双进程投递与排水缺口

`cluster_test.go` 只在显式设置 `GOAKT_EVAL_ETCD` 时启动两个独立操作系统进程；每轮使用唯一 ActorSystemName 隔离 etcd 发现，动态本地端口和独立临时工作目录。HTTP 仅控制探针，业务由 Runtime 经 GoAkt 集群通信，不经 HTTP 代替远程 Actor 通道。不读写 Redis/Mongo 业务数据。

实验配置 replica=1、minimumPeersQuorum=1、partitionCount=17、发现租约 TTL=5s，仅用于双节点功能验证，不是生产配置。本轮没有验证异常宕机、网络分区或归属交接。

实测结果：

- A 先激活 RoleID=1001，B 使用另一 Session 调用该角色；响应 PID 指向 A，确认没有退化为 B 的本地执行。
- Tell、TellAccepted、CallFuture、Call 正常远程入口可用；业务错误码 17 和错误消息能够回传。这里没有扩大为所有模式在网络故障下的完整契约验收。
- 未加保护时，A 的 Drain 返回成功后，B 的请求仍在 A 执行，观测 `targetPID=19613`、`callerPID=19620`、后续响应 `19613:6`。
- 第二个失败断言进一步确认：原 Shutdown 会执行持久化回调后停止系统，输出 `err=<nil> flushed=true running=false`，不能证明回调期间没有新的远端业务。

根因是当前 Ingress 只记录本进程发起的请求。B 的请求进入 A 的 Grain，不经过 A 的 Runtime.submit。FIFO 确认只能证明前面的消息已经处理，不能阻止确认之后的新消息；此外 GoAkt 的 Grains 在集群模式聚合远端目录，并非本地快照。

当前保护：集群模式下 Drain 先关闭本地发起入口，然后返回 `ErrClusterDrainUnsupported`。Shutdown 不进入持久化回调、不停止系统。**这是阻止错误宣布排水成功，不是接收端排水实现；远端业务仍能执行。** Raw Stop 仍仅用于实验资源清理，不能拿来绕过持久化关闭策略。

加入保护后，11 个本地用例和一个双进程场景以 `-race -count=3` 运行通过；两个子进程均正常退出并检查退出码。测试辅助入口在父进程中跳过，实际在两个子进程中运行。双进程场景确认未执行持久化回调、运行时保留且远程调用仍到达同一 PID。

下一项需要设计接收节点的业务准入与执行完成边界，覆盖激活和已排队工作，同时保留本地已验收语义；不通过 RPC 自动重投解决，不增加持久化 MQ。这一方案确定并通过后才能移除上述限制。

## 尚不能得出的结论

- 不支持直接替代现有 Messenger：四种入口完成本地和正常双进程投递验证，归属变化、异常网络及接收端排水尚未验收。
- 有界等待协程是新增成本；减少关联表不等于减少总资源消耗。原生 Ask 等待结束释放容量，也不代表业务已经完成。
- Runtime.Stop 仅用于实验清理；评估关闭使用 Shutdown。系统停止仍不能作为持久化成功的证明。
- Factory 只是存储衔接位置，不是落库实现。不能在 OnDeactivate 中直接保存后就当作已有失败保留、重试和最终关闭能力。
- 不做 Session 身份鉴权；输入假定来自可信分派层。不会以 SessionID 拆分角色，但角色授权仍由现有项目 SPI 负责。
- 尚未证明 GoAkt 性能不回退。本阶段不做不同 API 范围的行数或吞吐比例承诺。
